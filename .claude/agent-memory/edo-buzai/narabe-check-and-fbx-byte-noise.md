2026-09-21・類型共用の附属屋3点(`Typ_Komegura`/`Typ_Umaya`/`Typ_SakujiKoya`)で踏んだ。

## ① 「在庫と見分けが付くか」は単体レンダでは判定できない

部材単体の立面・斜め・背面・妻の4枚を見て「土蔵らしい」と通したが、`Eg.Kura` と一列に
並べて焼いたら **長手の大壁が 7.3 × 3.1m の一面の白**で、意匠の無い箱に見えた
(`Eg.Kura` は妻に窓・扉・庇・棟飾りが付く)。丈と足形比を数値で出しても、この抜けは出ない。

**Why:** 見分けは**相手との差**なので、比べる相手が画面に無いと読めない。丈 +0.72m も
足形 1.18:1 対 1.07:1 も、数値では差に見えて実物では読めなかった。

**How to apply:** 既存の在庫や兄弟部材の**代わり**として起こす部材は、`narabe` のような
**並べ比べの枝**(書き出さず、在庫を ES 倍して一列に置き、立面と目の高さの2枚を焼く)を
生成器に持たせて、それを見るまで完了にしない。⛔ 単体4枚で通さない。
`build_typ_fuzokuya.narabe()` が実装。obj の在庫は `bpy.ops.wm.obj_import` + ES=1.818 倍。

## ② 既存型に引数を足したときの回帰は **バイトで見ない**

`dozo` / `nandokoya` に既定値が従来と同じ引数を足したあと、焼き直した FBX が
既存と **2,333 バイト**違った。⛔ ここで「式の組み替えで float がずれた」と決めつけない —
実際は式は**ビット一致**していて、幾何は全く動いていなかった。

**Why:** Blender の FBX 書き出しは**同じソースを2回焼いても 179 バイト違う**
(CreationTime・FileId・UID)。差分のバイト数は run ごとに揺れるので**回帰の指標にならない**。
さらに出荷済み FBX は古い Blender で焼かれているので、サイズが数百バイト違うのは既定。

**How to apply:** 引数追加の回帰は **① 実寸(W/H/D)② 面数 ③ 頂点集合**で見る。
③は両方の FBX を読んで world 座標を丸めて sorted 比較するのが確実
(`VM.import_fbx_abs` → `matrix_world @ v.co` を 1e-9 で丸めて集合比較)。
⭕ 既定を保つ引数追加のとき、**ビット一致させたいなら括弧の位置を合わせる** —
`EAVE - 1.97` を `EAVE - (1.50 + 0.47*mado)` と書けば mado=1.0 で一致する
(`1.50+0.47` は 1.97 の最近傍 double と等しい)。`EAVE - 1.50 - 0.47` でも一致した。

## ③ 土蔵の水切りは通しで回すと観音扉を横切る

既存3点(`Matsudaira_Dozo`/`Doi_Kura_3x8`/`Doi_Kura_3x3`)は**その姿のまま据わっている**ので
既定は変えない。`dozo(mizukiri_tooshi=False)` で額縁の幅ぶん切って回す枝を足してある
(切り口は x=−hw で止めれば額縁の裏に隠れて小口が出ない)。
