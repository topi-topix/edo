# Blender 部材パイプライン

在庫キットに無い建築部材を **Village Kit / Japanese Castle の部材から江戸間で起こして** FBX に書き出す。
Blender は GUI を開かずヘッドレスで回す — 指図の寸法が変わったら作り直せるようにするため。
各スクリプト冒頭の docstring に「なぜ新造するか」の典拠と使い方がある。

パスは `vklib.REPO`(このファイルの位置から導出)起点。**sparse worktree では Assets が来ないので回らない** —
メインのチェックアウトで `edo_session.py start <屋敷> --blender` を打ってから回すこと。

⚠ **門番は「他セッションが `assets` を claim 中は blender の起動そのもの」を拒否する**
(`Tools/Session/edo_session.py cmd_check_bash`)。出力先 `Assets/Edo/Models/` が共有だからで、
**`BUZAI_OUT` で staging へ逃がしても拒否は解けない**。⛔ 迂回しない — 待ち行列に並ぶこと
(`edo_session.py claim --resources assets`。空くと先頭に15分の予約が出る)。

⭕ **`BUZAI_OUT=<dir>` を立てると全生成器が書き出し先をそこへ差し替える**(`vklib.out_dir`)。
**Unity が走っている最中に `Assets/Edo/Models/` へ書くとドメインリロードが起きて、
検査中の `execute_code` が壊れる。**⇒ 部材方は第1段で staging へ焼いて実寸とレンダを検め、
呼び出し元の合図で第2段に `Assets/` へ移す。⛔ 既定を staging にしない
(合図なしで staging に落ちると誰も Assets を見に行かなくなる)。

以下は御殿系(`build_goten_*`)の詳細。

```bash
blender --background --python Tools/Blender/build_goten_parts.py
GOTEN_ONLY=Koran blender --background --python Tools/Blender/build_goten_parts.py  # 一部だけ作り直す
blender --background --python Tools/Blender/build_goten_roof.py -- <桁行W> <梁間D> <名前>
blender --background --python Tools/Blender/build_goten_roof.py -- kirizuma        # 渡廊下の屋根を定尺で一括
blender --background --python Tools/Blender/build_goten_roof.py -- rebuild         # 既存の屋根を全部作り直す
# 確認レンダを出す場合
GOTEN_PREVIEW=/path/out.png blender --background --python Tools/Blender/build_goten_roof.py -- 14.5 9.1 Test
```

**屋根は寸法ごとに1本**なので、棟や妻の作りを変えたら `-- rebuild` で全数を焼き直すこと
(`Roofs/` にある `Goten_Roof_Irimoya*.fbx` の名前から間数を読んで同じ寸法で作り直す)。

書き出したら Unity で **Edo ▸ 御殿 ▸ 新しい御殿FBXのマテリアルをremap** を走らせる。
FBX にはマテリアル名しか入っていないので、remap しないと白い模型になる。

## なぜプレハブでなく部材から起こすのか

Village Kit の `Prefabs/House` 等は**壁で閉じた一軒家**で、入側(廊下)から見ると壁が見える。
御殿は廊下に面して障子・襖が並ぶので構造が合わない(→ `unity-buke-yashiki` SKILL.md)。
ただしこれは**プレハブの組み方**の問題で、`Meshes/` には障子・白壁・縁・柱・畳・瓦が
**単体の FBX 部材として425点**ある。閉じた箱を壊すのではなく、部材から組み直す。

## 寸法

Village Kit は **2.0m/間**。江戸間は 1間 = 6尺 = **1.818m**。
→ **一律 ×0.909**(`vklib.S`)で端数なく一致する。

| | キット原寸 | ×0.909 |
|---|---|---|
| 畳 | 1.0 × 2.0 | **0.909 × 1.818** = 江戸間の畳 |
| 柱 | 0.20角 | **0.182角**(六寸角) |
| 建具高 | 3.0 | **2.727** |
| 障子(door wall A) | 2.0幅 | **1.818** = 一間2枚建て |

## 書き出しの規約(Unity 座標で言う)

- 幅 = X / 高さ = Y / 厚み = Z、**表(入側から見える面) = +Z**(Village Kit の facade 規約と同じ)
- ⚠ **`export_fbx` は Blender +Y を Unity の −Z へ写す。**
  `axis_forward='-Z', axis_up='Y'` の帰結で、**論理座標のまま組むと「表」が反対側に出る。**
  ⛔⛔ **同時に `Unity X = −(Blender X)` になる。**(右手系→左手系は行列式 −1 の写像で、
  `Unity Z = −(Blender Y)` と組めば X の反転が決まる。⛔「Blender +X = Unity +X」は誤り。)
  ⚠ **左右対称な部材では絶対に気づけない。**帯割りの屋根 `4-5x10ken_v` はここを辿り切らずに
  鏡像で焼かれ、Unity に据わるまで捕まらなかった(2026-09-07)。
  自前でメッシュを起こすとき(`build_matsudaira_*.py` の `Mesh` クラス系)は、
  書き出す直前に**厚みを反転し、面の巻き順と UV も一緒に反転**すること
  (`Mesh.to_object` にその実装がある。巻き順を戻さないと法線が内向きになり、
  外から見ると箱の内側が見える)。
  ⚠ **前後対称な部材では絶対に気づけない。** 表門(冠木門)は対称なので3日ぶん見逃し、
  番所を据えて初めて「出格子と唐破風が敷地の内側を向いている」と分かった(2026-08-25)。
  非対称な部材を1つ作ったら、**Unity で据えてから正面を1枚撮る**。
  `V.imp()` でキットの部材を読んで並べる作り方(`build_goten_parts.py` など)はこの影響を受けない。
- ピボット = **一間の中心・床レベル**(濡縁だけは Y 最小 = 建物側)
- マテリアル名は Village Kit のまま(`wall C` `door wall` `wood` `roof` …)。
  Unity 側の `Materials/*.mat` と同名なので **Search & Remap で既存マテリアルが当たる**。
  新しいマテリアルを作らないこと — リアルさが既存建物とズレる。

## 屋根の作り方

瓦は**実ジオメトリ**(桟瓦の凹凸がモデリングされている)。テクスチャ板に置き換えると質が落ちるので、
`roof 2x2` を流し葺きに並べ、屋根面の平面ポリゴンで切る。
**棟(大棟・隅棟・袖瓦)もキットの `roof top x1`**(冠瓦+熨斗瓦2段+紐が彫ってある 0.909m)を継ぐ。
新造するのは **破風・妻壁・木連格子・懸魚** だけ。

- 流れ方向のピッチ = 瓦5段 = **1.785m**(段ピッチ0.357)。1段重ねると継ぎ目で段が通る
- **棟は箱で作らない**。断面を押し出した箱にアトラス一点のUVを貼ると無地の板になり、
  瓦場だけ実ジオメトリなので浮く(ユーザー指摘 bookmark 2026-08-15 #2)。
  `ridge()` が `roof top x1` を **実長/整数** に伸ばして継ぐので、斜めの隅棟でも継ぎ目は出ない
- **瓦の実体は名目平面より 0.15 ほど上にある**。これを見落とすと妻まわりが全部おかしくなる:
  - 袖瓦は **0.22 持ち上げて**通す(埋めると見えない)。入れないと瓦場を切った断面と
    破風板の天端が白い筋になる(bookmark #3/#5)
  - 破風板は `drop=0.55`(板の45%を屋根面より上へ)。低いと**天端を瓦の波形が食って
    木ではありえないグニャグニャの縁**になる(ユーザー指摘 2026-08-15 第2回)
  - 妻壁の足元にも **横一文字の水切り板**を打つ。無いと寄棟面の瓦の口が直接壁と組子に当たる
- 妻飾りは二条城二の丸御殿に倣って **木連格子(1尺ピッチ)+ 蕪懸魚 + 六葉**。
  桁隠しの懸魚は付けない — 妻の下端は隅棟と軒がすぐ下にあって板が瓦を突き抜ける
- 妻壁の厚みは **内側だけ**に付ける(SOLIDIFY は両側に出る)
- 勾配比 0.5456(≒5.5寸)は `roof 2x2` の実測から来る。変えるとモジュールが使えない
- 入母屋の作図は `build_goten_roof.make_irimoya` の docstring 参照
- **入母屋も棟の寸法ごとに1本**。名前は `Goten_Roof_Irimoya_<桁行>x<梁間>ken`(間数)で、
  Unity 側は `EdoAssets.Goten.RoofIrimoya_(w, d)` で引く。岡部邸は13棟で11種になった。
  **大棟は桁行に架かる**ので必ず 桁行 ≧ 梁間 で生成し、外形の長辺が棟のローカルX に来るよう
  Unity 側で yaw を与える(`EdoOkabeYashikiBuilder.BuildMune`)

### 雁行する棟の取り合い = 渡廊下の低い切妻(`make_kirizuma`)

**ユーザー裁定(2026-08-14): (a) でやる。** 谷や隅は生成せず、各棟は独立した入母屋のまま置いて、
その**軒下を渡廊下の低い切妻がくぐる**。福井図・二条城も同じ形。

高さの予算(棟の床を 0 として。`EdoGotenKit` が同じ数値を定数で持つ):

| | 値 | 出どころ |
|---|---|---|
| 棟の軒先 | **2.577** | `Mune` が屋根を置く高さ = 建具丈2.727 − 0.15 |
| 渡廊下の軒先 | 1.55 | `ROKA_EAVE` |
| 渡廊下 軒先→大棟天端 | **0.953** | 軒の出0.60 → (0.909+0.60)×0.5456 + 棟の座0.13 |
| → 渡廊下の大棟天端 | **2.503** | 棟の軒先より 0.074 低い。ここが成立条件 |

- 屋根FBXは**両端が 0.30 長い**(`ROKA_END`)。棟の軒の出0.90と合わせて1.20重なるので、
  **廊下の端は棟の壁面に突き付ける**。離すと取り合いに隙間が出る
- 瓦の繰り返し(流れ1.785 / 桁行2.004)は江戸間と割り切れない。だから**1間モジュールを並べる
  ことはできず**、長さごとに1本ずつ作る(`ROKA_KEN_SET` = 2/3/4/5/6/7/8/9間)
- **1間の渡廊下は作れない**。両端が棟の軒と1.20ずつ重なるので、重なりの合計2.40mが
  廊下の長さ1.818mを超える。指図で2m程度の隙間は**2間(3.64m)へ広げる**
- **妻壁は既定オフ** — 端は棟に突き付いて見えない。片端が外に出る廊下だけ `tsuma=True`
- **破風板は入母屋の寸法(幅0.60・厚0.22)のままだと渡廊下では巨大**に見える。
  `gable(bw=, bt=, drop=)` で小振り(0.22/0.06)にし、大半を屋根面より下へ垂らす
- 大棟の座は瓦の頂点から **0.13 下げて食い込ませる**。棟幅0.36の端では屋根面が0.098下がるので、
  頂点に載せると棟の脇に隙間が抜けて見える

## 踏んだ落とし穴(再発防止)

- **FBX のマテリアルは Alpha=0 で読まれる**(Unity の TransparencyFactor)。直さないと
  「オブジェクトはあるのに何も写らない」レンダになる → `vklib.hook_textures()` が 1.0 に戻す
- **`bpy.ops.transform.rotate` は正の値で時計回り**(ギズモの符号)。屋根面が90°ずれる。
  回転は `vklib.rotate_z()`(行列)を使う
- **ブーリアンは瓦場に使えない**。重なり合った非マニフォールドなので EXACT ソルバが
  「中身が詰まっている」と誤判定して**型そのものを返す**。平面 bisect で切る
- **bisect は面を持たない頂点・辺を残す**。消さないとバウンズが嘘をつく
- **新造ジオメトリのUVを複数面の平均で決めない**。アトラスの別領域(腰板など)に落ちる。
  最大面1枚から取る
- **FBX を親(Empty)ごと読んで `o.location` を触らない**。親の回転・スケール込みで飛ぶ。
  `vklib.imp()` が親を外して焼き込む
- 同じ FBX を何度も読むと `floor.001` のような複製マテリアルができる。
  join の前に `vklib.dedup_materials()`
- **書き出した FBX を読み直して並べる確認スクリプトの落とし穴**(組み上がりのプレビューで踏む):
  - `bpy.ops.object.transform_apply()` は **location の既定が True**。回転だけ焼くつもりで
    呼ぶと位置まで焼かれ、そのあと `o.location = 目標` を入れると二重にずれる。
    `transform_apply(location=False, rotation=True, scale=True)` と明示する
  - 読み込み直後のメッシュには Y-up→Z-up の回転と親スケールが object 変換に残っている。
    先に焼かないと **`o.scale.z` が世界のZに効かない**(柱を縮めたら横に伸びた)
  - ピボットは FBX ノードの平行移動として入っている。`parent_clear` 後の `o.location` が
    それ。**加算でなく代入**しないとピボットが効かない

## 建具・座敷飾り(build_goten_fittings.py)

キットに無いので新造。内法高は **1.818(6尺)**、その上の欄間が **0.909(半間)** で、
合わせて 2.727 = 障子・柱の高さ。格子に乗る。

襖 / 筬欄間 / 雨戸(Wall D 1 から) / 上段框 / 床の間 / 違い棚 / 帳台構

- **新造ジオメトリの色はアトラスの明るさで選ぶ**(`vklib.sample_uv_bright`)。
  高さで選ぶ `sample_uv` は当てが外れて襖が真っ黒になった
- **面積のある木部・紙・壁は一点貼りにしない**。`set_uv` はアトラスの1画素を伸ばすので完全な
  無地になり、襖が板に・破風が「木に見えない」茶色の板になった(ユーザー指摘 2026-08-15)。
  `vklib.set_uv_rect` でアトラスの矩形を貼る。**斜めに寝た板は軸投影できない**ので、
  破風板は作図時の頂点の並びから直に UV を決める(`build_goten_roof._uv_by_vertex`。
  長さ→v・幅→u で木理が板の長手に流れる)。矩形は wood が `WOOD_UV` / 漆喰が `WALLC_UV`。
  襖紙は **`wall A` の左半分(u 0.045..0.275)の無地の紙面**。`wall A` はキットに .mat はあるが
  どのメッシュも使っていないので `vklib.named_material` で名前だけ用意する(remap は名前一致)
- **引違いの2枚は前後の溝に分ける**(y をずらす)。同じ面に置くと重なり代が z-fighting する
- **`Balcony/balcony A` は高欄が bbox の最小Y側に付いている**。素直に置くと高欄が建物側に立ち、
  床板 0.89m が高欄の外へ張り出す(ユーザー指摘 bookmark 2026-08-15 #1)。`rot=180` で反転する。
  反転すると隅で高欄が切れるので、半間角の `Goten_NureenCorner`(高欄が二面)で四隅を塞ぐ
- 床の間・違い棚・帳台構は**妻壁を開けて据える**(`EdoGotenKit.Mune` の openBaysEast/West)。
  塞いだままだと壁の裏に隠れる。壁の外へ出る箱なので**底板・天井板・小壁で塞ぐ**(光が漏れる)
- 上段の間は `Mune(jodanFromIx:)` で床ごと 0.15 上げる。框だけ置くと飾りの下に隙間が出る

## 踏んだ落とし穴(2026-09-04 追加。つる3種で踏んだもの)

- ⛔⛔ **多角柱の断面の向きを `direction.rotation_difference()` で毎区間作らない。**

## 帯割りの入母屋(make_banded・2026-09-06)

```bash
blender --background --python Tools/Blender/build_goten_roof.py -- banded 4,5 12 --render <dir>
#   旗: --along u|v / --irikawa <間> / --eave <m> / --noki <m> / --tsuma <m> / --fukizai sangawara|hongawara
```

**なぜ要るか**: 御殿の棟が **梁間10間超(18m超)を一枚の小屋組で飛ばして**いた。現存例で最大の
山脇武家屋敷門ですら梁間 4.7m で、存在しない型(2026-09-06 ユーザー裁定=案C)。⇒ 足形・室割り・
廊下は動かさず、**身舎を帯(2〜5間)に割って帯ごとに入母屋を架け、帯の境を谷にする**。

- ⭐⭐ **「下屋も同じ勾配」(2026-09-06 裁定)を入れると、下屋は別の屋根ではなくなる。**
  身舎の軒桁(z=軒高)から入側の上を通って軒先まで**一枚の平面が続く** — 段も、下屋自身の
  軒も出ない。⇒ 実装は「帯の入母屋に、外周側だけ軒の出 `E = 入側×1.818 + 軒の出` を付けた物」。
  **立面では入側と身舎の境が見えない。**
  ⭕ **これは欠陥ではなく裁定の帰結。2026-09-06 に「一枚の流れのままにする」で確定した** —
  ⛔ **直さない。**「下屋が無い」と見えても勾配を変えないこと。指図の文言のほうを
  「入側は身舎の屋根がそのまま延びた一枚の流れで覆う。段は付けない」へ寄せてある。
  ⚠ **御殿の庇の勾配は【U】**。[西川1959]**A** に「庇の軒高9尺1寸勾配4寸5分」(本家は6寸)が
  あるが、あれは**長屋の構造の節**の値で、御殿の庇へ当てるのは外挿。⛔ 手掛かり止まりにする。
- ⭐ **谷は水平になる。** 隣り合う帯はどちらも境で軒高まで下りてくるので、谷線は軒高の水平線。
  両端で妻側の流れ(下屋)へ落ちる。⛔ 谷を勾配で下げない — 帯の棟が傾く。
- ⚠ **妻側(桁行の両端)の流れは、隣り合う帯どうしで完全に同一平面**。帯ごとに切って並べてよいが、
  **瓦の格子の原点を帯ごとに取ると桁行方向にズレる**(帯幅 4間=7.272 は瓦の桁行ピッチ 2.004 の
  整数倍でない)。⇒ 妻側の瓦場は**全帯で共通の原点**から葺くこと。
- ⚠ **谷では瓦場を左右 0.10 引いて、谷樋を実体(中の詰まった断面)で入れる。**板を1枚渡すだけだと
  瓦の切り口と樋のあいだに光の筋が出る。樋の天端は瓦の名目平面より 0.04 下(瓦の実体は
  −0.03〜+0.15 でうねるので、その下へ潜る)。
- ⚠ **ピボットの z が既存と違う。** `make_irimoya` / `make_yosemune` は **z=0 が軒先**で、
  Unity 側(`EdoGotenKit` の `Put(..., floor + H − 0.15, ...)`)が軒先高に置いている。
  `make_banded` は**軒高を引数に取る以上 z=0 は床**にするしかない。⇒ 据えるときは
  **棟の床の高さにそのまま置く**(軒先高を足さない)。XY は既存どおり足形の中心。
  ⭕ この警告は `EdoAssets.Goten.RoofBanded()` の XML コメントにも入れてある(2026-09-06)。
  **足すと 3.4m 浮く。**
- ⭐⭐ **`bands` の先頭は、`along` が u でも v でも「across 軸(帯の並ぶ向き)の小さい側」**。
  ⇒ **指図の `ws` をそのまま渡す。**土井の奥棟(across=u・u の小さい側から 4 → 5)は
  **`-- banded 4,5 10 --along v`**、名は `4-5x10ken_v`。
  ⛔⛔ **`bands` を生成器の中で並べ替えてはいけない。**中身は帯を常に Blender +Y へ並べ、
  `"v"` なら最後に `rotate_z(+90)` する。この回転は Blender 空間では `(x,y) → (−y,x)` で
  並びを裏返すが、**書き出しの `Unity X = −(Blender X)` がそれをちょうど打ち消す**。
  ⚠ **2026-09-06 に「+90° で裏返る」とだけ見て `bands[::-1]` を入れたのが誤り**で、
  `4-5x10ken_v` が鏡像で焼かれ、Unity に据わって初めて捕まった(2026-09-07 に撤去)。
  **軸の鎖を Unity まで辿らずに符号を決めない。**
- ⭐ **軸の鎖(帯割りに限らず効く)**
  1. 書き出し(`V.export_fbx` は `axis_up='Y' / axis_forward='-Z'`):
     **Unity X = −(Blender X) / Unity Y = Blender Z / Unity Z = −(Blender Y)**。
     ⚠ 右手系→左手系は**行列式 −1** でしか繋がらない。「Blender +X = Unity +X」は誤り —
     `Unity Z = −(Blender Y)`(この README の「書き出しの規約」章・`build_ishigaki_saka.py` の
     実測)と組にすると **X も反転する**ことが決まる。
  2. 据え付け: 屋根は `roofYaw = DeltaAngle(muneYaw, yawU)` で格子へ戻すので
     **モデル局所 +X = 格子の +u / 局所 +Z = 格子の −v**(`EdoDoiBuilder` の註)。
  ⇒ 帯 i の **across 座標(across の芯からの相対・m)= `ym − D/2`**(`ym` = 内部 +Y の帯の芯)。
  `along` が u でも v でも同じ式になる。
- ⛔⛔ **非対称の帯を焼いたら、その場で「天端から 0.02m 以内の頂点を集めて across 座標へ落とす」
  検算を必ず回す**(`_verify_band_order()` が `make_banded` の末尾で自動で回し、ズレたら止まる)。
  ⚠ **帯の並びは立面から見えない** — 上から見ないと帯が見えないので、
  **`--render` の立面(02/03)でも、Unity 側の足形・棟高の数値QAでも素通りする。
  足形も棟高も左右対称で合ってしまう**(2026-09-07 棟梁の所見)。
  ⭕ 対称な帯(`4-4` `5-5` 単帯)は鏡像が無害だが、**対称だから正しいとは限らない** —
  大棟の向きと谷の位置は別に測ること。
  ⭕ 同じ検算は Unity 側にもある(`EdoDoiBuilder` の `TopRidgeGrid` が指図の `bands.at` と
  突き合わせる)。**部材と据え付けの両方で測るのが正しい** — 片方だけだと鏡像を素通しする。
- ⭕ **`_v` は別体を焼く**(棟梁に 90° 振らせない)。据える棟は江戸間格子の yaw を持つので、
  そこへ更に 90° を足させると取り違えの温床になる。⇒ **モデル局所 +X = 格子の +u** に統一し、
  棟梁が振るのは**格子の yaw だけ**(2026-09-06 部材方の判断)。
- ⛔⛔ **この関数の高さはすべて「床上」。「地盤上」と取り違えない。**
  既定で軒先の先端は **床上 1.917m** だが、御殿の床は地盤より
  `const.gotenFloor` = **0.62m** 高いので **地盤上 2.537m**。⭕ 立位の眼高
  `const.eyeStand` = 1.45 に対し 1.09m の余裕があり、**江戸の軒として低くない**。
  ⚠ 2026-09-06 に部材方も普請奉行も床上のまま「軒先が低いのでは」と読み違えた。
  ⇒ **軒の出 0.90 も軒高 3.4 も動かさない**(同日裁定)。
- ⚠ **本瓦(`fukizai="hongawara"`)はまだ焼けない。** Village Kit の瓦材は `roof`(桟瓦)の**1種だけ**で、
  もう1つの `Roof B` は瓦ではなく**板葺・茅のアトラス**(2026-09-06 実測)。本瓦の当てがあるのは
  `Japanese Castle/Meshes/Exterior/Roof Castle 6x8.fbx`(材 `Roof Castle A` / 8×6 キット単位 /
  **勾配 0.500**)だが、勾配が `RATIO` 0.5456 と違うので**葺材ごとに勾配とモジュール寸法を
  分ける改修**が要る。⛔ 黙って桟瓦で焼かない — 生成器は例外で止める。
- ⛔ **`gable_frac` 0.45 と谷樋の材(木)は「部材の既定値」で、指図の欄にしない**(2026-09-06 裁定)。
  妻の丈は 4間帯で 1.09m = 既存の入母屋と同値。**御殿の妻を強調する典拠が無い**ので、
  指図の摘みにすると根拠なくいじれる値が増える。谷樋も**銅にしない**(2.3万石の御殿には過ぎる。

  確度を積まない。
- ⚠ **`tile_field` は升ごとに FBX を取り込む**ので、27×22m 級では取り込みが律速になる。

## 平入り+庇 と 渡廊下の下屋(2026-09-20・松江松平の奥向の棟4棟+厩と渡廊下6本)

blender --background --python Tools/Blender/build_matsudaira_dewa_roofs.py -- --geya --render
# 単発:
blender --background --python Tools/Blender/build_goten_roof.py -- hirairi 22 5 2.744 --omit v1 --render

- ⭐⭐ **勾配は瓦モジュールの素の 5.5寸(`RATIO`)ではない**(本 6寸 / 庇 4寸5分 / 下屋 4寸)。
  `_tile_field_k` が **瓦の形を変えずに面ごと傾ける** — 軒先の線まわりに Δθ だけ回し、
  葺きの進みも同じだけ回して送る。⛔⛔ **z を縮めて勾配を作らない**(4寸で起伏が 27% 潰れ、
  実ジオメトリの瓦を使う意味が消える)。⚠ 送りの**平面上の**進みは `step.x` に縮むので、
  格子の枚数はそちらで数える(`STEP_RUN` で数えると足りない)。
- ⭐ **`_tile_field_k` は位置を `+=` で置く**(⛔ `=` で上書きしない)。格子の原点は (i0,j0) の駒に
  在るので、代入すると格子が i0·送り ぶんずれてポリゴンを覆い損ねることがある。
- ⭐⭐ **平入り+庇のピボットは `make_banded` と同じ「z=0 が床」**。平面は**足形(庇を含む)の中心**。
  ⛔ **bbox の丈をピボットからの高さに使わない** — 実体は z 1.399..5.519(軒桁 2.744 の版)で、
  **破風が軒先より下へ垂れ、大棟の座と瓦の起伏が上へ出る**。
- ⚠ **bbox は呼び寸 + 軒の出×2 より更に片側 0.14 大きい**(隅棟の角の飛び出し。入母屋の 0.171 と同性質)。
- ⛔⛔ **三方庇(`--omit`)は外形では検算できない** — 庇を断った辺は本屋根の軒が 0.9 出るので、
  **外形が四方庇と対称のまま**になる。⇒ `_verify_hirairi` が**辺ごとに軒先手前 0.3m の天端**を測って
  従属値と突き合わせる(庇 1.601 / 本屋根の軒 2.313 のように 0.7m 違う)。
  ⚠ 瓦は名目平面に対し位相しだいで −0.15〜+0.15 うねるので、許容は下 0.16 / 上 0.30。
- ⚠ **辺の綴りと Blender 軸の対応**: 格子 **+u = Blender −X / +v = Blender +Y**
  (書き出し `Unity X = −BX` `Unity Z = −BY` と据え付け `局所 +X=+u` `局所 +Z=−v` の合成)。
  ⇒ **u0 = +X 端 / u1 = −X 端 / v0 = −Y 端 / v1 = +Y 端**。
- ⛔ **雨押え(水切り)板を省かない** — 本屋根の軒先を庇の頭で切ると、瓦の**切り口が剥き出し**で
  庇の上に載る。⚠ ただし板の天端を瓦の上へ出すと**真上から茶色の帯**に見える
  (見付 0.18 / 丈 0.25 / 天端は軒桁 +0.13 に収めた)。
- ⭐⭐ **下屋(`make_rokageya`)のピボットは「頭」= z=0 が葺き下ろしの線**。床でも軒先でもない —
  頭の高さは廊下ごとの従属値(その端の**当たり** − `roka.clear`)で、部材の中には持てない。
  ⇒ 本体は **z<0 に在る**。
- ⛔⛔ **検証レンダの地面を z=0 に置かない。** 下屋はピボットが頭なので、z=0 の板が屋根を切って
  **大棟しか写らない**。2026-09-20 に「瓦場が焼けていない」と誤診しかけた(実際は 447 面あった)。
  ⭕ 地面は **`mn.z − 0.05`**、画角も**部材の実測から**取る(⛔ 軒高の引数で組まない)。
- ⚠ **当たり(`当たり`)は軒桁ではなく軒先の下端。** 庇のある辺は
  `軒桁 − (庇の間数×1.818 + 軒の出)×庇勾配`、庇を断った辺は `軒桁 − 軒の出×本勾配`。
  ⛔ 軒桁で読むと下屋が相手の軒を突き抜ける。
- ⛔ **渡廊下の床にキットの板(`Goten_FloorBoard_1ken` 厚 0.0636)を敷かない。** 廊下の床は落縁の

### 素通し(穴)の検査のしかた

- ⛔ **世界背景を派手な色にして「その色が出たら穴」とやらない。**背景は同時に**照明**なので、
  影になった面が背景色に染まって**偽陽性**になる。妻壁(漆喰)が抜けていると誤診した(2026-09-06)。
- ⭕ **`film_transparent = True` + `color_mode='RGBA'` で焼き、アルファ 0 の画素を数える。**
  ⚠ **正射影で視線が屋根面と平行になる向き(平の立面など)は、掠める光線が偽陽性を出す。**
  **真上からの正射影(`T2`)が一番効く** — 屋根は空に面した物なので、上から抜けが無ければ穴は無い。
- ⛔⛔ **「列ごとに最上/最下の不透明画素のあいだの透明画素」で数えない**(2026-09-06 に是正)。
  屋根の**四隅は隅棟が軒先より外へ飛び出す**ので**輪郭が凸でない**。最も外の列では
  「隅の出っ張り2つだけが不透明・あいだは全部空」になり、**外の空を穴と誤診する**。
  実測: `Banded_4-4x8ken` はこの数え方で **23,076 px**、実物は真上から見て**穴ゼロ**。
  ⇒ 旧記載の「既存の `Goten_Roof_Irimoya_10x6ken` は真上で 20,760 画素抜けている」も
  **同じ偽陽性**だった(同じ物差しで測り直すと **0 px**。レンダを見ても穴は無い)。
  ⛔ この 20,760 を「既存は穴だらけ」の根拠に引かない。
- ⭕ **正しい数え方 = 「囲まれた透明」**。透明画素のうち**画像の外周へ4連結で繋がらないもの**だけを
  素通しと数える(走査線塗りつぶしで外側を塗り、残った透明が穴)。輪郭が凸でなくても効く。
  ⚠ `scipy` は無く、**Pillow 12 の `ImageDraw.floodfill` は無反応**(2026-09-06 実測。塗らずに返る)
  ので、**numpy だけの走査線塗り**を自前で持つこと(Blender 内でも動く)。
  実測(この物差し): 帯割り 5種とも真上 **0 px**、`Goten_Roof_Irimoya_10x6ken` も **0 px**。
- ⚠ 「囲まれた透明」は**軒先まで開いて外へ繋がる欠け**は捕まえられない。
  ⇒ 数値だけで済ませず、**俯瞰・谷の寄り・妻の立面を必ず自分の目で見る**こと。
- ⭕ **物差しは `Tools/Blender/check_seethrough.py` に置いてある**(2026-09-06)。
  書き出した FBX をそのまま検められる(= ピボットと形が書き出しを通ったあとの姿で測れる):
  ```bash
  blender --background --python Tools/Blender/check_seethrough.py -- <FBX> [<FBX>...]
  ```
  0 でなければ終了コード 1。⛔ 床の板を置かないこと(不透明な背景板があると常に 0 になる)。

## 踏んだ落とし穴(2026-09-07 追加。木の生成器 build_tree.py で踏んだもの)

- ⛔⛔ **`hash()` で乱数の種を作らない。** `build_tree.py` は
  `seed = hash((key, size, vi))` と書いてあり、docstring は「⛔ 種は個体番号から決める
  (時刻や連番で振らない — 焼き直すたびに姿が変わると検証レンダが比較できない)」と
  宣言していたが、**Python の str の hash はプロセスごとに乱数化される**(PYTHONHASHSEED)。
  ⇒ **同じ引数で2回焼くと別の木が出ていた**(実測: `Tree_Teiboku_Mid` の幅が
  2.08m → 1.78m)。**検証レンダで見た木と、その隣の実行で焼いた FBX は別物**になる。
  ⭕ `zlib.crc32(("%s/%s/%d" % (key, size, vi)).encode())` へ替えた(2026-09-07)。
  ⚠ **既存の木(jouryoku / momiji / ume / enoki / mukunoki / keyaki)を焼き直すと
  個体の姿が変わる** — もっとも従来も焼くたびに変わっていたので失う物は無い。
  ⛔ **その種は `size` の綴りそのもの。**⇒ **刻みの呼び名を変えると、丈が同じでも別の姿が焼ける。**
  2026-09-08 に低木を `Small`→`H12` / `Mid`→`H20` と改めた際、6点とも骨格が入れ替わった
  (幅 1.774→1.886m など)。⚠ **`sizes` に鍵を「足す」だけなら既存の鍵の種は動かない** —
  足すのと改める(改名)のは別の話で、ここを混同すると「変わらないはず」と言って変えてしまう。
  ⇒ 改名するときは**焼き直して前後の実寸と三角数を並べ、変わったことを報告に明記する**。
- ⛔⛔ **FBX の「変わっていないこと」をファイルの md5 で確かめられない。**
  FBX のヘッダには **CreationTime と書き出し先の絶対パス**が埋まるので、
  **まったく同じ形を焼き直しても md5 は必ず変わる**(実測: 同サイズ・差分 123 バイト、
  最初の相違は offset 292 = `CreationTime`)。⇒ **幾何の指紋**を採ること —
  読み直して 頂点座標・面の構成・UV・材質名 を丸めて sha1 する
  (2026-09-08 に低木 H16/H24 の不変を確かめた方法。12点とも sha1 一致・md5 は全点不一致)。
- ⚠ **`wh`(樹冠の幅 ÷ 丈)は「出来上がりの幅」ではない。** `wh` が決めるのは
  **誘引点の雲の幅**で、葉のカードは枝先から更に `2.2 × leaf_scale × 丈` だけ外へ散る。
  低木(丈2m)で `wh=0.95` と書いたら実測 2.48m = 1.24 になった。
  ⇒ **指図が樹冠を要求する部材は、焼いて測ってから `wh` を決める**(低木は 0.72 で実測 0.9 台)。
- ⛔ **葉のカードは地面より下へ沈む。** 散らしの下振れ(`rnd.uniform(-0.7, 1.1)`)が
  枝先の高さを食うので、**樹冠が地面に届く低木では「地面に落ちた葉の房」が焼き付く**
  (近景レンダで実測)。`add_leaves` に `c.z = max(c.z, s * 0.75)` を入れた。
  高木は樹冠が地面に届かないので無効(既存の木の姿は動かない)。
- ⚠ **`--var <n>` は効いていない。** `args` は `--` 始まりを落としたあとなので
  `"--var" in args` が常に偽で、**個体数は常に 3**。⛔ 直していないので当てにしない
  (数字だけの引数は `sizes` に混ざって KeyError になる)。
- ⭕ **低木は `seg_bias` で枝の断面を粗くする。** 葉に埋もれて枝が見えないので、
  `LOD["seg"]` に 0.62 を掛けて三角数を落としてある(既定 1.0 = 従来の木は不変)。

  **AgX** で、明部を圧縮し**彩度を強く落とす**。実測: アルベド V76.5% / S7.7% を貼ったら
  レンダは V73% / **S1.1%**(彩度が 1/7 になった)。⇒ 受入値(レンダの H/S/V)に
  合わせ込むには **焼く → レンダ → 測る** を回すしかない。3巡で入った。
  ⭕ 測る道具を `Tools/Blender/check_color.py`(`--preset shaden`)に立てた。
  ⚠ 矩形は 0..1 の比で持ち、**カメラを動かしたら選び直す**。
- ⛔ **同じ材でも「陽の面」と「陰の面」で 15ポイント開く。** 社殿の亀腹は縁が 0.90m
  持ち出しているので**上段が縁の陰**に入る。⇒ ⛔ 片方だけ測って合否を出さない。
  実測: 下段(陽)V59.2% / 上段(陰)V43.1%。**8ポイント幅の受入帯に両方を入れる
  アルベドは存在しない。**
- ⭕ **タイル貼りのテクスチャは「等方な粒」に均してから貼る。** 素(`jsw_diffuse.jpg` =
  石垣)には**縦の筋**(雨だれ・割れ)が残っており、0.30m 刻みで貼ったら基壇が
  **コーデュロイ**になった。⇒ ①低周波をぼかしで割る ②**列の平均・行の平均でも割る**
  (1次元の縞を構造として消す)③繰り返しの寸法を**段の丈と同じにしない**(0.30 → 0.44)。
- ⛔ **段の丈を「天端 ÷ 段数」の余りで決めない。** 本殿 0.383m / 拝殿 0.214m と
  **棟ごとに段の丈が違い**、考証方に「上下段で丈が違い目地も通っていない」と読まれた。
  ⭕ **天端の側**を段の丈の整数倍へ丸める(懐の下限を割るなら段を1つ減らす)。
- ⛔ **突き付けの目地の見え幅は「面取り×2」。** `CHAMFER` 0.015 のままだと V 溝が
  **30mm** になり、庭方の受入値「目地 ≤ 15mm」を倍で外す(⇒ 亀腹だけ 0.007)。
- ⛔⛔ **舞良戸に `door wall` の“紙の矩形”を貼らない。** 舞良戸は**板戸**。紙の矩形を
  貼ったので近景で**障子の桟のような格子**に焼け、考証方に「全面が連子窓＋腰板・
  舞良戸に読めない」と判定された。⭕ **材は替えず、同じ `door wall` アトラスの中の
  腰板(縦板)の帯へ矩形だけ移す**(実測 RGB(56,45,41) H16° S26.8% V22.0%)。
  ⛔⛔ **材を `wood` に替えると `check_front_east(door_east)` が同時に壊れる**
  (あの窓は「`door wall` の面の重心が東」で向きを見ている)— 実際に壊して鳴らせた。
  ⇒ **見えを直すときは、その見えを測っている検査の窓を先に確かめる。**
- ⛔ **引きの立面で「建具が無い」と判定しない。** 本殿は列の**西端**なので、
  `east_elev` にも `south_elev` にもまともに写らない(東は拝殿に隠れ、南は 9.2m 先)。
  ⇒ 面の可否は**面を名指しで撮る**(`honden_south_near` / `honden_west_near` /
  `heiden_south_near` を足した)。⚠ 近景は**軒の出 1.72 + 縁 0.90 の外**まで引くこと —
  11.5m では軒の中へ入って何も読めなかった。
- ⭕ **建具の有無は目でなく数で確かめられる。** 舞良子は「壁面の外へ出た薄い水平の板」
  なので、**内法の帯の中で壁面に貼り付いた頂点の Y のまとまりの数**を数えれば入っているか
  分かる(本殿 15 / 幣殿 10 / 作り合い 1 = 壁なし)。
- ⚠ **指図の `const` に「式の文字列」が入ることがある。** 指図方が規則4(同じ量に二つの数を
  作らない)で `shadenHondenFloor` を `"shadenFloor + shadenHondenStepM"` へ書き換え、
  `float()` が落ちた。⭕ `const_num()` が `+`/`-` で繋いだ**鍵と数だけ**を解く(⛔ `eval` は使わない)。

## 踏んだ落とし穴(2026-09-09 追加 その3。松江松平の差し戻し5件で踏んだもの)

- ⛔⛔ **書き出した FBX を測り直すとき、生ローカル座標を Unity 座標と思わない。**
  `V.export_fbx`(`bake_space_transform=True`)で出した物を Blender へ取り込み直すと、
  生の `v.co` は **cm** で、**`Unity ローカル = (−生X, +生Y, +生Z)`**。
  ⭕ 往復の実測で確定した(Blender (1,0,0)→生(100,0,0)/(0,2,0)→生(0,0,−200)/(0,0,3)→生(0,300,0))。
  ⚠ **Y と Z は素直なのに X だけ反転する**ので、`+生X` を Unity X と読むと
  **左右対称でない部材だけが鏡像に見える**。2026-09-09 に帯割りの屋根 2 種
  (`3-3-4-4x12ken_v` / `4-5-5x12ken_v`)を**正しいのに不良と判定しかけた**。
  ⭕ 迷ったら `axis_probe` と同じことをやる — 非対称な四面体を1つ往復させて刷る。
- ⛔⛔ **`Renderer.bounds` / 生メッシュの投影幅を、指図の呼び寸法と直に比べない。**
  番所は指図 `gate.plan.bansho.w`=4.25 が**躯体**の幅(継ぎ目 `J_Bansho_*` が
  「番所**躯体**の東端」と面を名指ししている)で、メッシュの走り方向の実寸は
  **躯体 + 0.40m**(切石基壇 +0.18 / 側面の出格子 +0.22)。⇒ 何をしても 0.40 過大に出る。
  ⚠ 同じ棟の `d`=3.6 もメッシュでは 4.70(軒 0.55×2)。**`w` と `d` は同じ意味(躯体)**で、
  片方だけ「外形」と読むのが誤り。**検査は測る集合を先に確かめる**(CLAUDE.md 規則19)。
- ⛔ **帯割りの屋根は入側(下屋)を四周同じにできない。** 指図の `bands`/`spanKen` は
  `munes[].roof.irikawa`(**軸ごとに [手前, 奥]**)を辺ごとに引いた**身舎**なので、
  スカラ1つを四周へ当てると `irikawa` が [1,1] でない軸で **1間ずつ過大**になる。
  松江松平の表向4棟が隣どうし **3.18間(5.78m)**重なり、真上から見ると4棟が1枚の
  巨大な屋根に融けていた。⭕ `make_banded(irikawa=...)` は
  `1` / `{"u":[u0,u1],"v":[v0,v1]}` / `(u0,u1,v0,v1)` を受ける。
  ⚠ **辺ごとに出が違うと隅棟は短い方の軒先線で尽き**、長い方の面がその先へ張り出す
  (二平面の交線は必ず 45°)。隅を1点で済ませると斜辺が 45° を外れて隙が開く。
  ⭐ **ピボットは「身舎+入側」= 棟の外形の中心**にした ⇒ 屋根の外形は常にピボットについて
  対称(棟の外形の各辺に軒の出が一様に付くだけ)。⚠ 入側が四周同じなら身舎の中心と一致
  するので、**既存の屋根のピボットは1mmも動かない**。
- ⛔ **入側・幅のような「同じ名前で幾何が変わる」摘みは、必ず名前へ埋める。**
  松江松平の表向(入側 u=[0,0])と土井(四周1間)はどちらも `4-4-4x10ken_v` になる。
  ⇒ 既定と違うときだけ `_i<u0><u1><v0><v1>` を付ける規約にした。番所も
  `Matsudaira_Bansho_W4.25.fbx` へ改め、寸法の入らない旧名は**消した**
  (残すと実装が旧寸を引き当てて静かに 0.83m ずつはみ出す — 実際にそうなっていた)。
- ⚠ **`V.set_origin` を通した部材は FBX ノードに location が残る**(帯割りの屋根は
  例: `4-4-4x18ken` が (16.362, 10.908, 0))。メッシュ**データ**はピボット中心に
  正しく載っているので Unity 側の据え付けは合っているが、**測るときは
  `matrix_world` でなくメッシュのローカル座標を見る**こと。
  ⚠ `Mesh` クラス系(番所・袖塀・根石)は location 0 で出るので混同しやすい。
- ⭕ **玉石(河原石)は「土台を縮める」だけでは丸みが足りない。** 1.5m の転石の 3cm の
  丸みは 0.5m へ縮めると 1cm になり、受入値「凸の稜に 2〜6cm」(ユーザー指摘 2026-09-06)を
  **相似縮小なので必ず割る**。⇒ `bmesh.ops.smooth_vert` を回してから寸法へ嵌め直す
  (玉石は水に洗われた石なので、全体を丸めるのは形の由来として正しい)。
  ⭕ 丸みは目でなく数で見る — 稜の折れ角 θ と面の差し渡し L から
  **局所の丸み半径 r = L ÷ (2·tan(θ/2))** を出し、**下位5%**を受入値と比べる
  (`build_neishi.curvature_report`)。実測 0.020〜0.045m。
- ⚠ **丸い石は「外接寸法」で突き付けない。** 地盤線での差し渡しは外接の **92〜96%**
  なので、外接どうしを並べると地盤線の高さで石のあいだに空が抜ける。
  ⇒ 芯々は地盤線の差し渡し(または外接の 0.93 倍)で詰める。
- ⛔ **カメラを決め打ちの座標に置いたまま部材の寸法を変えない。** 番所の幅を 5.5 → 4.25 に
  詰めた回、5.5 用のカメラ座標のままで焼いて**唐破風と出格子が画面の外へ切れた**
  (危うく見ずに合格にするところだった)。⇒ カメラは bbox から引く。

## 踏んだ落とし穴(2026-09-10。松江松平の差し戻し3件)

- ⛔⛔ **棟の外形が接する棟へ、四周一様に軒を出さない。** 松江松平の表向4棟は
  `munes[].u1` = 次の棟の `u0` で**外形が接して**いる。そこへ軒 0.90m を四周へ出すと
  隣どうしが **1.80m 食い込む**。普請検査の寄りのレンダでは「二つの軒先の間から空が透ける /
  桟瓦の列が空中で途切れる / 軒先が何にも載らず宙に浮く / 目の高さで軒線が **X 字に交差**」
  という姿になった。⭕ `make_banded(noki=(u0,u1,v0,v1))` で**接する辺の軒だけ落とす**
  (身舎・入側は 1mm も動かさない ⇒ **ピボットも棟の外形も不動**)。
  ⭕ 落とした辺には**半分の谷樋**(`_valley_gutter(half=±1)`)を出す — 両隣が半分ずつ出して
  線の上で**一本の樋**になる。⛔ 両方が全断面を出すと重なって z ファイティングになる。
  ⛔ **落とした外周の辺で瓦場を `VALLEY_GAP` 引くのは、樋を出すときだけ**。樋なしで引くと
  左右 0.10 ずつ = **0.20m の空が抜け**、直そうとした不良に戻る。
  ⛔ **妻側(大棟の両端)は落とせない** — 破風・懸魚・妻壁が付く辺なので、軒だけ落とすと
  板が宙に浮く。生成器が例外で止める(形の問題なので指図方へ差し戻すこと)。
- ⛔⛔ **「四辺とも軒が 1.071 出ている = 入側が効いていない」ではない。** 呼び寸法 0.900 に
  対する +0.171 は **隅棟(`ridge` の断面 w=0.40)の冠瓦の見付**。隅棟は軒先の隅から 45° で
  立つので、**隣り合う二辺の出が等しい隅**ではその半幅が**両方の辺**の外へ出る
  (出が違う隅では短い方の辺にしか出ない)。⇒ 長局南 `_i1110`(EX=EY=2.718)だけ四辺に出て、
  `_i0011`(EX 0.9 ≠ EY 2.718)は妻側だけに出る。**入側は正しく効いていた。**
  ⭕ `_verify_eaves()` を足して**辺ごとの軒の出を焼いた直後に実測して刷る**ようにした
  (測る集合を先に確かめる。CLAUDE.md 規則19)。
- ⛔⛔ **`o.location` を書いた直後の `matrix_world` は古い。**依存グラフが回るまで反映されない
  ので、二棟を並べた検証レンダで**据える前の座標のまま画角を決め**、二棟が画面の隅に寄った
  画を焼いた。⇒ `bpy.context.view_layer.update()` を挟む。
  ⚠ 継ぎ目の寄りは**ピボットの中点で代用しない** — 棟の丈が違うと線から外れる(0.9m 外した)。
  ⭕ **共有する外形の線**そのものを指図から出してカメラを向ける。
- ⭕⭕ **「石が角張って見える」に `smooth_vert` を足しても悪化することがある。**
  `bmesh.ops.smooth_vert` は頂点を寄せるだけなので、**面が痩せて L が縮み**、
  局所半径 r = L ÷ 2·tan(θ/2) が**下がる**。実測(NM の小石8個体):
  14回 0.031〜0.052 → 44回 **0.016〜0.042** と反対へ動いた。
  ⭕ 効くのは **Catmull-Clark を1段**(`SUBSURF`)。増えた面は **Decimate 0.40** で戻す
  (平らな所から潰れるので稜まわりの L はむしろ広がり、丸みは落ちない)。
  実測 **下位5% 0.0395〜0.0597 m / 三角 407〜855**(従前 284)。⚠ UV は細分でも collapse でも保たれる。
- ⛔⛔ **土台の大きさが桁違いなら、材より先に土台を替える。** 根石(丈 0.30〜0.40m)に
  Waldemarst の**庭石**(1.25〜1.99m)を縮めて当てていたので、**丸みが相似で必ず痩せる**。
  ⭕ NatureManufacture の `s_rock_01..06`(**0.28〜0.55m**)は最初から根石の寸法で、
  材 `M_photoscanned_rocks_01` を FBX が元から持つ(⛔ 新規マテリアルではない)。
  ⭕ テクスチャの実測で選んだ: `T_FJG_Rock_Dark_001_Albedo` **V14.9% / 粒 14.2** に対し
  `T_Photoscanned_rocks_01_BC` **V40.8% / 粒 9.1**(明るく肌理が細かい)。
  ⚠ 「粒」= 512px 切り出しを σ4 でぼかした差の平均。⭕ **候補の材は数で並べてから選ぶ。**
- ⚠ **小さい部材の受入レンダは「その部材だけ」を撮らない。** 根石は板塀の足元に並ぶ物なので、
  塀を立てずに石だけ見ても合否が出せない(差し戻しは『板塀の足元の汚れ・ひびに読める』だった)。
  ⇒ `build_neishi._itabei_mock()`(検証レンダ専用の板)を足し、**目の高さから足元を見る**画を撮る。
