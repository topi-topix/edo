## 切絵図の記号と門の向き

- **屋敷名の文字の頭(書き出し)が表門の方角**([[kiriezu-reading-conventions]])。
  ⭐ **「頭」は縦組み・横組みの両方で読む**(2026-08-31 山王坂3邸の対照実験で確定)。
  同一図の中で家によって**文字の組み方が割れるのは作図の癖ではなく、門の向きの記号**として効いている:
  **横一行・頭が右 → 東向き**(丹羽・京極)/ **縦一列・頭が上 → 北向き**(内藤)。
  ⛔ **縦組みを見て「上=北だから北」と即断せず、横組みの家が同じ図にあるかを必ず見る** —
  片方の組み方しか見ていないと、90°ずれた向きを全邸に一律で当ててしまう。
  **ただし道の有無が優先** — 土手・水際で道があり得ない辺には門を向けない。
  溜池沿いの横田・土岐は北が溜池土手で道が無く、切絵図でも文字の天は南向き=南の東西通りが表だった。
  **地形(土手・水際)を見て「その辺に道があり得るか」を必ず確認してから文字向きを適用する。**
- **尾張屋版の記号**: 家紋の丸(中身が空でも)= **居屋敷(上屋敷)**、**■=中屋敷**、**●=下屋敷**。
  ⛔ **記号は CODH のデータには入っていない** — 閲覧ページ側の表示で、`owariya.csv`(2025-07-23 版)を
  8,788 件悉皆で当たると `(紋)` `■` `●` は **0 件**、prefix/suffix 列は全件空(2026-09-21 実測)。
  **記号の判読は NDL の IIIF 原画像でしか付かない。**⚠ 「CODH で記号を確かめる」と書いた宿題は空振りする。
  同一屋敷が隣接2絵図に同記号で載ることがある。
- **板年次で当主表記が変わる**(内藤能登守→右近将監、林式部少輔→圖書頭)。
  ユーザー指定の人名が実見板と違っても別板由来の可能性が高い —
  **区画の同定は位置関係で行い**、表記の相違はコミット/メモリに記録して整合させる。
- **切絵図では長屋か塀かの描き分けは無い**(屋敷絵図・錦絵・古写真が必要)。
- **袋小路の突き当りに大名門**(下書きの区画ノッチ=門前の湾)という構図がある。
  湾口(8m)より長屋門(22.5m)が広い場合、**門の両翼は敷地内で塀の背後に隠れる置き方が成立**する
  (番所は物理的余地が無ければ0でよい)。

## 方位は方位盤を信用しない

外桜田永田町絵図(NDL 1286657)は方位盤が「北=上」に見えるが、**実内容は絵図の上=シーンの東**だった。
IIIF判読を任せたエージェントの「北」「南」報告をそのまま使うと街区の並びが90°化ける
(「永田馬場沿いの列」の実体はシーン東の南北道沿いだった)。

**正解手順**:
1. シーンの `Assets/Edo/OldMap/oldmap_center.png`(ジオリファレンス済ベイク)から該当街区を PIL で切り出す。
   クアッド頂点(`OldMapQuad.asset`: x[-3314,2690] z[-2417,3579] ⇔ UV[0,1]²、PNG行=北が上)で
   `scene(x,z) → pixel` を線形変換:
   ```python
   def px(x): return (x + 3314) / (2690 + 3314) * W
   def py(z): return (3579 - z) / (3579 + 2417) * H
   ```
2. 0.51〜0.68px/m で文字は読めないが**区画形状・家紋ブロブ・道の形は読める**ので、
   NDL 高解像画像を回転させて照合し、対応(絵図pxベクトル ⇔ sceneベクトル)を2-3組取って回転を確定する。
3. その後は NDL 画像を `PIL rotate(-90, expand=True)` 等で**シーン方位に直してから判読する**
   (文字の頭=門もシーン方位のまま読めて事故らない)。

CODH翻刻(記号■/紋+名前)と IIIF 原画像の**文字の回転を座標回帰**で解くと方位±10-15°で出る
(切絵図の一般則をデータで適用できる)。

## 家紋か植栽かの判定

**「木立のような黒点の円環」は家紋(九曜紋等)のことがある。**
CODHベイク(0.51px/m)では家紋がドット群に潰れて植栽に見える。
判定は必ず **NDL の IIIF 原画像**で行う:
```
https://www.dl.ndl.go.jp/api/iiif/<pid>/R0000001/<x>,<y>,<w>,<h>/full/0/default.jpg
```
九曜紋と確定できて屋敷格・門格式(k_mon)が全部変わった実例がある。

## 下書きストローク(EdoSketch)

`UserData/Sketches/<scene>.unity.json`。パレット([[sketch-strokes-reading]]、
`Assets/Edo/Scripts/Editor/EdoSketch.cs` の `Palette` 配列が正):

| color | 色 |
|---|---|
| 0 | 赤 |
| 1 | 黄 |
| 2 | 水色 |
| 3 | 緑 |
| 4 | 桃 |
| 5 | 白 |

**隣接屋敷の輪郭ポリゴンが色分けで残っていることがある。**

- ⚠ **「敷地の外=街路」と決めつけない。** 安部邸の西縁の外側を「三べ坂(街路)」と思い込んでいたが、
  実際は**渡辺備中守邸との隣地境界**だった(赤ストロークの起点が安部ポリゴンの頂点と1m以内で一致し、
  本物の三べ坂は59m北西の別線だった)。
  **下書きの座標と自区画の頂点を突き合わせれば確定できる** — 数m以内で一致すれば同一境界。
- 「街路」と「隣地境界」では扱いが変わる: 街路側は表構え(表門・表御殿・白洲)を向ける対象、
  隣地境界は長屋の裏(盲・無窓面)を向ける対象。前提を取り違えると格式判断そのものが狂う。
  ただし**なまこ面の向きは敷地重心基準で見れば同じ**なので、判定を間違えても即座に建て直しが
  要るとは限らない — まず現況を実測してから直す範囲を決める。
- **下書きの区画間の隙間 ≠ 街路。** 切絵図実見で「短冊列は大屋敷と背中合わせ(間に街路なし)」と
  判明し、下書きで4-7m空いていた境界を共有線に締めた実例がある。
  逆に堀沿いは「区画と水面の間に堀端通りあり」で、下書きがすでに天端線から10-15m内側に引かれていた
  (**ユーザーの下書きは道の有無を反映していることが多い**)。
  **隙間を街路と解釈する前に必ず絵図で街路の有無を確認する。**
- **下書きJSONは Python でパースしてテキストに変換 → C# へ渡す**のが速い
  (C#側の正規表現JSONパースは空白差異で壊れやすい)。
- **検証レンダに写る「空中の黒い折れ線」は EdoSketch の下書きストローク** —
  電線・破損ジオメトリと誤診しない。

## 区画ポリゴンの決め方

- 区画境界は**ビルダーの実測ポリゴン(`V_*` 頂点)またはユーザーのブックマーク/下書き**から取る。
  **古地図から再導出しない**([[parcel-layout-from-bookmark-corners]]: 0.51px/mでは街区内部の
  割り線は読めない)。
- 新設区画は**ユーザーのトレース点に直線辺を最小二乗フィット**し、面積が文献坪数に合うよう
  非基準辺を一様インセットで解く(汐見坂の実在縁石ラインなど、実ジオメトリのある辺は固定辺にする)。
- 共有塀の所有は「上位の格 / 高い側の屋敷」が一本化して持つ。**測量で決める**(`perimeter.md`)。

## 史料ファイルの後始末

**取ってきた実体ファイル(HTML・PDF・画像)をリポジトリに残さない。** 残すのは
`sources.md` の典拠エントリだけで、ファイルそのものは調査が終わった時点で必ず消す。

### 落とす場所

保存先は**スクラッチパッド**。リポジトリ直下・`docs/`・`Assets/` に落とさない。
リポジトリに置くと、後から素性の分からない巨大ファイルとして発掘される
([[documentary-fetch-cleanup]]: 東京都公文書館のトップページ534KBが `toa.html` として
直下に残り、中身を調べ直す羽目になった)。

### 二分岐 — 参照したか、しなかったか

| | 何をするか |
|---|---|
| **設計の根拠にした** | `sources.md` に `[ID] 確度X` のエントリを起こす → **そのうえでファイルを消す** |
| **結果的に使わなかった**(空振り・目次やトップページに着いただけ) | **そのまま消す。** `sources.md` にも書かない |

「あとで使うかもしれない」で残さない。使うときに取り直す方が、素性不明のファイルを
抱えるより安い。**取り直せないものだけが例外**(下記)。

### 典拠エントリに何を書くか

ファイルを消しても後から検証できるだけの情報を、`sources.md` の既存の書式で残す:

- `[ID]` と **確度**(S/A/B/P/U)
- **URL と取得日**。原URLが404なら Wayback のスナップショットURL
- **本文が述べていること** — 引用ではなく要点。ここが実体ファイルの代わりになる
- **依拠する記述** — この典拠をどのスキル/指図のどの記述が使っているか
- 外挿してはいけない範囲があれば警告(石高・年次・地域)

指図の文章の部(`docs/Sashizu/<屋敷>_kosho.md`)からは `[ID]` で引く。
**URLを指図に直接書かない** — 典拠の所在は `sources.md` に一本化する。

### 消してはいけない例外

**原本が消えつつあるもの**(原URLが既に404で Wayback 頼み、リンク切れが予見される個人サイト)は、
ファイルを残すのではなく **`sources.md` に要点を厚く書き写す**ことで代替する。
それでも実体が要るとユーザーが判断した場合だけ、置き場所と理由をユーザーに確認してから残す。
