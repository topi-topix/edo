## QAチェックリスト(レンダ前に数値で)

屋敷を建てたら、または大きく触ったら、この順で通す。**全項目を数値で報告する。**

1. **境界** — 全建物の OBB 輪郭点が区画ポリゴン内。辺距離が種別閾値以上
   (主要建物 ≥8m / 蔵・厩・中間長屋 ≥6m。`buildings.md`)
2. **接地** — OBB 輪郭9点で 埋 / 浮。目安 **埋≤1.0 / 浮≤0.7**(斜面では緩めてよいが必ず値を出す)
   ⚠ **埋 ≈ |浮| が同値なら「地形だけ動いて建物が置き去り」の指紋**(`site-grading.md`)
3. **建物間** — メッシュ実距離 ≥2.0m。**御殿複合は0.6m狙いなので対象外**
4. **外周長屋の被覆率** — 辺ごとに2m刻みでサンプルし、内側4mに長屋があるか
   (渡辺 21%→57%。SKILL.md §B-2 が守れているかの指標)
5. **建蔽率** — shoelace の敷地面積 ÷ OBB底面積合計。**敷地全体ベースのみ**(SKILL.md §A-4)。
   `estate-types.md` の史料値と突き合わせる
6. **長屋の継ぎ目** — ⚠ **「ピッチ差=0」だけでは不合格を通す。** 一様に間違ったピッチは
   一様なまま通ってしまう(2026-08-23 松江松平で、全継ぎ目が 0.252m 重なったまま
   この検査を合格していた)。**部材を実行時に測って、継ぎ目が壁の実寸と一致するか**を見る:

   ```csharp
   // ① 部材の「壁」の走り方向の範囲を測る(屋根・棟・鬼は端で出るので除く)
   float mn=1e9f, mx=-1e9f;                      // prefab を identity 回転・ES 倍で置いて
   foreach (var r in go.GetComponentsInChildren<Renderer>()) {
       string n = r.gameObject.name.ToLower();
       if (!(n.Contains("wall")||n.Contains("namako")||n.Contains("dodai"))) continue;
       mn = Mathf.Min(mn, r.bounds.min.x); mx = Mathf.Max(mx, r.bounds.max.x);
   }                                             // knagaya01c → 8.065m / 妻 l,r → 7.910m
   // ② 建てた各部材の「壁」を run 方向へ射影し、隣との継ぎ目を測る
   //    合格: |次の lo − 前の hi| ≤ 0.02m(面一)。重なりも隙間も不可
   ```

   **ピボット間隔で判定してはいけない** — 妻部材はピボット位置が違うので間隔は
   7.239 / 8.065 / 7.910 とばらつくが、それで壁は面一。**見るのは壁の実体の継ぎ目**。
   あわせて Y幅=0(天端が段になっていない)・ry幅=0(run 内で向きが揃う)も見る。
   → 直し方は `perimeter.md`「ピッチは壁の実寸」
7. **面の裏表** — namako の射影で数値判定(`perimeter.md`)
8. **門の取り合い** — `空隙=0 ∧ 屋根との t 重なり=0 ∧ 袖塀差込≤0.3` の3点セット
9. **地形の副作用** — 造成前バックアップと diff し、**変わるはずのない領域の raised/lowered=0** を確認
10. **池** — 中心の地面 = `waterY−depth`、各輪郭頂点から外向き法線で汀線が立ち上がる
    (`gardens-ponds.md`)

## 検証レンダ

オフスクリーンの一時カメラで撮る(`unity-surface-authoring` にレシピ):
- **真上の正射投影**(パースに惑わされず継ぎ目・格子ズレが見える)
- **門の外からの斜め**(見付の確認)
- **庭の目線**

注意:
- プレハブの樹木・水は一発 `Camera.Render()` で描画される(地形の detail 草は描画されない)
- `read_console` でエラー確認(temp-camera の GUI assertion `!m_InsideContext` は無害)
- **`Shot()` の top-down は LookAt のロールが不定**(up が世界-x になった実例)。
  真上撮影は rotation を明示指定する。方位はランドマーク(池・既知の建物)で確認してから読図する
- 保存 → ファイル mtime 確認 → 屋敷ごとに記述的メッセージでコミット
- **一時オブジェクトは必ず消す**: `scene.GetRootGameObjects()` を走査して `TEMP_` 接頭辞で一掃
  (`GameObject.Find` は同名が複数あると1個しか返さないので削除漏れする — 383個消し残した実例)

## 失敗事例集(再発防止)

### スクリプトの罠
- **`Group(root, "Garden/Trees")` のスラッシュ名バグ(重大)**: `Transform.Find("Garden/Trees")` は
  パス探索するが、**見つからない時に `new GameObject("Garden/Trees")` を作るとスラッシュ入りの名前の
  オブジェクトが root 直下にできる**(Garden の子の Trees にならない)。結果、生成されるが親が不正で
  毎回重複し、`Find("Garden").childCount==0` になって「0個」に見える。
  **階層生成ヘルパは必ず `child.Split('/')` で1段ずつネスト**する。
  既存の不正物は `name.Contains("/")` で一掃してからやり直す。
- **同名オブジェクトを2個作ると、名前キーのQA辞書が衝突して片方が未検査になる**
  (`Ido ⇔ Ido = 0.00` は自己比較の指紋)。合成物は必ず一意名を付ける。
- **同名グループを2回作ると `Find` が1個しか返さず削除漏れする**(検証マーカー383個の消し残し)。

### 探索・配置の罠
- **庭の空き地探索で外周長屋/石垣を obstacle に入れると全滅する**: 45°回転長屋の world-AABB が膨張し、
  外周132枚のAABBが敷地内部を覆い尽くして全候補点が reject される(配置0個)。
  正解は **obstacle = 建物+門のAABBのみ**、外周は**辺への距離マージン**で避ける
  (長屋辺=8.5m / 築地塀辺=3.0m、最近傍辺の種別でマージンを変える)。
- **合成コンテナ(Umaya/井戸/稲荷)の pivot が原点にある**ことがある(子を世界座標で置く実装)。
  `transform.position` 基準で動かすと絶対座標分すっ飛ぶ。**移動は子バウンズ中心→目標点の差分**で。
- **20m高度グリッドの列読みは間違えやすい**(1列ズレで「平坦」の位置を60m誤認)。
  建物を置く前に対象ゾーンを4m刻みで再サンプルして表を出す。
- **AABB corner→壁線距離は回転建物で常時誤検出**。⚠が出たら中心距離−実半対角で再計算してから動かす
  (「本当に動かすべきだったのは1件だけ」だった実例)。

### レンダリング・アセットの罠
- **Bloom の白球 = 法線ゼロ→NaN**([[nan-bloom-zero-normals]])。両面化で頂点共有→
  `RecalculateNormals` が打ち消してゼロになる。ブックマークで黒/Sceneで白球はNaNの指紋。
- **CreateAsset を多数 + `SaveAsPrefabAsset` を MCP タイムアウト中にやると GUID が汚染される** —
  metas が再生成されプレハブが stale guid を保持し、**全インスタンスが何も描画しない**
  (renderer bounds がゼロサイズ点、合成 bounds ≈ transform オフセットだけ、が指紋)。
  同じ in-memory オブジェクトを再保存しても stale guid のまま。
  **修正法**: 各オブジェクトを1つの結合メッシュ(`CombineMeshes`、submesh 2つ)として
  **新しいアセット名**で作り直し、`LoadPrefabContents` → 子を単一 "body" MeshFilter に置換 →
  `SaveAsPrefabAsset`。**1回の execute_code でのアセット生成数を絞る。**
- **輸入モデルのスケールは必ず測る**: Blender からの FBX が×54ズレた実例。
  `Assets/Edo/Models/Shiomizaka/*` はルートに補正スケールを持つので `Vector3.one` を渡すと巨大化する。

### 判断の罠(この会話で実際に差し戻された)
- **自分の成果物を基準に目安を作った**(建蔽率20-30%)→ SKILL.md §A-5
- **分母を可建地に替えて低い数字を正当化した** → §A-4
- **石高密度で「疎でよい」と正当化した** → §B-4
- **空地に長屋を並べて建蔽率を上げた**(敷地中央に5組、斜面に34棟)→ §B-3
- **「なめらかな地形だから自然地形」と循環論法で判断した** → §A-6
- **「敷地の外=街路」と決めつけた**(実際は隣地境界)→ `documentary-research.md`
- **スキルに矛盾する記述を両論併記のまま追記した** → SKILL.md 末尾「このスキルの育て方」

### 屋敷の類型を取り違えた例
- **寺社の小規模住坊を「寺」として建てた**([[sanno-jubo-10bo]]): 社僧の坊・里坊・門前の院は
  本堂・山門・鐘楼・墓地なし。**主屋(庫裏一体の方丈形式5〜7間=SmallHouse級)+持仏堂+小土蔵+
  井戸+板塀+腕木門**が正しい類型。板塀は片面ポリなので es_dobei と同様に表裏0.12mペアで置く
  (バウンズ中心合わせ。ピボットは端寄り)。
- **中屋敷に上屋敷の門格式(独立門 k_mon)を適用した** → `historical-layout.md` 門の格式

## MCP・Unity操作の実務

- **MCP タイムアウト後の再送で多重実行が起きる。** 「Timeout receiving Unity response」や
  「No Unity Editor instances found」が返っても Unity 側は実行済みのことがあり、再送すると二重に走る。
  **地形ステージは必ずマーカーで守る。ただしマーカーは active にする** —
  `GameObject.Find` は**非アクティブを見つけない**ので `SetActive(false)` だとガードが毎回すり抜ける
  (2026-08-14 にこれで地形を複数回削った)。冪等でないステージは「実行済みか」を必ず先に確認する。
- **スクリプトのコンパイルが止まることがある。** `Library/ScriptAssemblies/Assembly-CSharp-Editor.dll`
  の mtime とソースの mtime を比べ、**古ければ実行しない**。古いアセンブリで走ると
  「直したのに反映されない」と誤診して同じ修正を繰り返す(2026-08-14 に2回踏んだ)。
  `AssetDatabase.Refresh(ForceUpdate)` を投げてから dll の mtime が更新されるまで待つ。
  それでも動かないときは Editor の再起動をユーザーに頼む(こちらからフォーカスは当てられない)。
- **MCPが高負荷で無応答 → `execute_code` タイムアウト**が頻発する。
  結果を `File.WriteAllText` で scratchpad に書き、Bash の until ループでファイル出現を待つと取りこぼさない。
  ドメインリロード待ちは Unity プロセスの %CPU が <20% を数回続けるまで
  (`ps -Ao %cpu,comm | grep "MacOS/Unity$"`)。
  **`refresh_unity` は失敗しても実際には再コンパイルされる**ことが多い。
  ⚠ **タイムアウト後は、同じ処理を再実行する前に「実行済みか」を必ず確認する**(多重実行事故)。
- **FreeJapaneseGarden の一括インスタンス化は重い**(20分級のハングに見える)。
  プレハブを1個だけ先に Instantiate して地ならししてから本番ループに入ると安全。
- **地形バックアップからの復元**: heightmap を `.bin`(bx0,bz0,bw,bh + float配列)で scratchpad に保存。
  復元は PIP でクリップして敷地内だけ戻せる。
- **シーンからの位置復元**: 直前コミットのシーンを `git show` で取り出し、
  Transform(`!u!4`)と prefab instance(`!u!1001`)の**両方**をパースして名前パス→位置の辞書を作り、
  該当カテゴリの Y だけ書き戻す(114点復元した実例)。
- **`execute_code` の C# は codedom** — `Object` は `UnityEngine.Object` と曖昧になるので
  `UnityEngine.Object.DestroyImmediate` と書く。変数名 `t` はラムダのスコープと衝突しやすい。
  タプル分解の `foreach (var (a,b) in ...)` は使えない。
