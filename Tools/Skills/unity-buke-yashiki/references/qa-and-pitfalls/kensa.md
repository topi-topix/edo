# 検査・検算・地盤の罠(失敗事例集・18 件)

索引は `../qa-and-pitfalls.md`。⛔ 丸読みしない — 索引で当たりを付けて該当節を grep で引く。

## ★ 検査は感度試験とセットで書く

**「検査が 0 件だから合格」は、その検査が反応することを確かめて初めて意味を持つ。**

2026-08-24 の土井邸の指図で、**自分で書いた検査が7つ壊れていた**。すべて
「0 件」または小さい数を返しており、**壊れていることが結果からは見えなかった**。
隣家2軒へ是正を依頼する直前に根拠を検め直して発覚した(依頼していたら、
存在しない欠陥の是正を他人にさせるところだった)。

| 型 | 実例 | なぜ結果から見えないか |
|---|---|---|
| **恒真** | 「区画外へのこぼれ 0件」を、区画外が null のデータで測った | 測れないものは 0 件になる |
| **恒真** | クリップ済みの `graded_y` を自分自身と比べた | 差は常に 0 |
| **恒真** | 辺を持つ側に限定したが、持つ辺には全部 run が載っていた | 対象が空 |
| **死値** | `edgeOwner` を設計値に置いたが、どこからも参照していなかった | 「検査に教えた」は嘘だった |
| **ラチェット** | 開口の幅を既存値で下限に固定した | 大きすぎる開口が縮まない |
| **粗い標本** | 20m 刻みで測り、run の継ぎ目を飛ばした | 0.21m と報告、実際は 5.80m |
| **按分違い** | 天端 `seat0→seat1` を run でなく**辺の全長**で按分した | もっともらしい数値が出る |
| **名と実の食い違い** | 「**共有**辺の地盤」を謳いながら**全辺**を回していた | 隣家の敷地の中の正当な復元まで指摘に化ける |
| **自分自身と比べる** | 石段の側面の地盤に `graded_y`(石段を含む)を使った | **踏面を踏面と比べる**ので常に 0.00 |
| **免罪符** | 儀式の軸の可否を `design_y`(段の上か)で免じた | 段は敷地のほぼ全部にある。**庭を全部消しても0件** |
| **在るべき物の不在** | 「何が在るべきか」を持つ物が無かった | **棟を消しても検査が一つも鳴らない** |

### 書き方

1. **宣言した不変条件には必ず検査を付ける。** 宣言だけで満たしていない例が実際にあった。
2. **検査を書いたら、その場で設計を故意に壊して件数が増えるか確かめる。**
   増えなければ検査が壊れている。
   - 例: 棟を1間ずらす / 段を消す / 面を +3m 上げる / 相手の天端を一律 −2m
3. **逆向きも確かめる。** 明らかに満たす値(相手の天端を +10m)で 0 件になるか。
   片方向しか見ないと、常に指摘を出す検査を合格と誤認する。
4. **反応しなかった検査は、反応しない理由を突き止めて記録する。**
   「設計上そこは壁が要らないから」なら**それを設計値に書いて**、検査の不感を正当化する。
5. **測れないデータで検証しない。** 区画の外が null のグリッドで「区画外へのこぼれ」は測れない。
   **原資料**(世界座標の DEM など)を連続に引く。内挿した格子の**最近傍**は、
   境界を挟んだ ±0.3m が同じセルに落ちて判定が立たない。
6. **隣家の値を読むときは、相手の生成器の読み方を正典にする。**
   `seat0→seat1` の按分は相手の `rseat()` が正典で、こちらの推測ではない。

### 感度試験は**入力側**を動かす

**生成器が毎回作り直す値を後から消す試験は甘い。** 実運用でその状態は起こらない。

2026-08-24、「境界の基壇石垣を全部消す → 4件出た」で検査が効いていると判断したが、
基壇は毎回生成される値なので、**消えた状態は設計からは決して生じない**。
検査本体は「基壇の天端 ≥ 設計地盤」で控除しており、**天端は生成の定義上つねに地盤以上**。
つまり**どんな設計でも0件を返す恒真**だった(段を +3m 持ち上げても通った)。

| 甘い試験 | 効く試験 |
|---|---|
| 生成される値(袖・基壇・算出寸法)を消す | **段の高さを +1m / +3m** 持ち上げる |
| 検査が読むフラグを落とす | **棟を 0.37間 ずらす**(格子を外す) |
| 算出結果を手で書き換える | **区画・地形・棟の位置**という**入力**を動かす |

**動かすのは設計者が実際に動かすもの**(段・棟・区画・石段の位置)だけにする。
生成器の中間生成物を壊す試験は、検査の恒真性を検出できない。

⚠ **算出した値を設計値に置くと偽装できる。** 開口を通る物の span を json に持たせたら、
感度試験でそれを手で広げるだけで検査が通った。**検査が使う量は毎回、実在する物から数え直す。**

### ⛔ 錨の連鎖は、いつか**自邸の外**へ出さないと閉じない

「宣言すれば通る」検査を締めていくと、**免除が一段ずつ外へ逃げる**。2026-08-26 に土井・松平・岡部の
3邸で同じ形を踏んだ:

| 段 | 塞いだつもりの形 | 次に開いた道 |
|---|---|---|
| ① | 区画ごとに雪隠が在るか | **区画の宣言を消す**と0件 |
| ② | 人が居続ける棟は必ず区画に属す | **区画を統合して粗くする**と0件(全部を1区画にすれば雪隠を3室消しても通る) |
| ③ | 区画を裁定として持つ | **裁定を丸ごと消す**と0件 |
| ④ | 共有台帳を最外の錨にする(**存在**だけ見る) | **区画を減らす**と0件(裁定も辻褄を合わせて溶かす) |
| ⑤ | **台帳の役割の「名前」から要求を組み立てる** | 自邸の json をどう書き換えても、台帳から役割を落とさない限り要求が消えない ⇒ **ここで止まる** |

- **自邸の正典の中に錨を置くかぎり、その錨を消す道が必ず残る。**
  止まるのは、錨が**自分では書き換えられない場所**(他邸と共有する台帳・史料の台帳)に出たとき。
- ⚠ **台帳を「読んで空でないことを確かめる」だけでは足りない。** それは台帳の**存在**しか
  錨にしておらず、自邸の側で区画や役割の**粒度**を落とす道が残る。
  **台帳に書かれた名前から要求そのものを組み立てる**(例: 台帳の「別の区画に属す役割」の一覧 ×
  自邸の `program.by` × 自邸の区画分け)と、自邸をどう書き換えても要求が消えない。
- ⛔ **新しく書いた作法は、過去へ遡らない。** 「測れないと言う」形で1本書いても、
  **既にある同型の検査は直らない**。書いたら必ず `grep` で同型を洗う
  (2026-08-26 土井: `_unmeasured` を書いた後に洗って8本出た。松平は2本)。
- ⛔ **そして、その作法で書いた検査の中に同じ穴を作る。**
  ①は grep で拾えるが②は**新しく書いたものを自分で疑い直す**しかない。
  土井・松平とも「測れないものは0件」を直すために書いた検査が、標本点を黙って飛ばしていた。
  ⇒ **飛ばした点を数えて、割合で鳴らす。** 0件は「測って0」か「測らずに0」かを区別できない。
- ⛔ **錨を読めなかったときに空を返さない。** 連鎖を外へ出しても、読み取りが
  「ファイルが無ければ `set()`」だと**そこで全部が素通りする**。
  2026-08-26、この節を書いた当人の実装がそれで、台帳を隠すと違反が完全に隠れた
  (出るのは「表が読めない」の1件だけ)。**例外を起こし、「合格ではなく回っていない」と出す。**
  併せて**健全性の床**を置く(表がN行未満・集合がN個未満なら壊れていると見なす)——
  ファイルは在るのに書式が崩れた、が最も静かに壊れる。
- ⚠ 集合の切り方は**人の別ではなく場の別**にする。書院を「表向とは別」にすると正しい構成まで落ちる
  (2026-08-26 松平)。
- 併せて**独立な量**でも測る(区画の別とは別に「最寄りの雪隠まで何m」)。
- **④ の実装は「台帳を読んで空でないことを確かめる」だけでは弱い。**
  それだと台帳の存在しか錨にならず、**区画を減らす**道が残る(松平で実測: `zones` から
  役割の区画を消して棟を移すと 0 件で通った)。**台帳の役割の"名前"から要求を組み立てる**と、
  自邸の json をどう書き換えても要求が消えない:

  > 役割表のうち **表役所 / 玄関・式台 / 居間・中奥 / 奥向 / 台所・勝手 / 厩** は
  > 互いに別の区画に属す。これを `program.by`(役割→棟)× `munes.zone` で照合する。
  > 書院・局は入れない — 玄関と同じ表向、奥向と同じ奥向に属してよい(**人の別ではなく場の別**)。

  役割の行を落とす道は `program_check` が塞ぐので、連鎖は台帳で止まる。
  松平で感度試験 **9経路すべて**が鳴ることを確認した(2026-08-26)。
  ⚠ この検査は入れた初回に本物を1件出した — **奥台所が「台所・勝手」役割のまま奥向に居た**。
  奥台所の働き手は賄方(男)でなく奥女中なので、役割としては奥向が抱える台所だった。
  宣言の粒度をいじっても距離は動かないので、片方を薄めても他方が鳴る。
- ⚠ この形は雪隠に限らない。`endOpen`(壁の端を開けてよい理由)、`certRulings`(確度の裁定)、
  `program`(在るべき役割)——**宣言で例外を許す仕組みはすべて同じ連鎖を持つ。**

### ⛔ 例外を許す仕組みを足したら、**その例外の上限も同時に決める**

2026-08-26、土井・松平で同じ形を**4度**踏んだ。毎回、免除を足した直後は「これで塞がった」と
思っており、抜け道は**他人に言われて初めて**見えた。

| 免除の置き場所 | 抜け道 |
|---|---|
| 自邸の json(裁定) | 裁定を消せば通る |
| 生成器の tuple | tuple を書き換えれば通る |
| `ishi`(根石)で受けたことにする | `ishi` を大きく書けば通る |
| 「採らなかった役割」へ移す | 必須の役割を移すだけで通る |

- **免除の条件を足すときは、同じコミットでその条件の上限を書く。**
  根石なら「背丈を超えたらそれは基壇」、免除リストなら「必須は免除できない」。
- ⚠ **上限そのものを共有台帳に置く**と、当邸だけでは動かせないので連鎖が止まる。

### ⛔ 分類の網から落ちたものを、**既定値へ倒さない**

語彙で振り分ける欄(`kind` / `要否` / `measure`)は、**知らない値が来ると黙って「その他」に落ちる**。
2026-08-26 の実測:

| 壊し方 | 起きること | 鳴った検査 |
|---|---|---|
| `runs[].kind` を `"Nagaya "`(末尾に空白) | 表長屋が数から消え **建蔽率 23.6%→22.3%** | **無し** |
| `bom[].measure` を誤字 | 石垣の延長が「—」に | **無し** |
| 要否の判定を接頭辞の白名簿で書く | 4つ目の言い回しが増えた日に静かに「任意」へ | **無し** |

- **「分からない」と言わせる。** 語彙に無い値・分類できない欄は、既定へ倒さず**非0で出す**。
- ⚠ **「無い」と「知らない値」を分ける。** 無いのは設計(欄を持たない行が正当なことがある)、
  知らない値は誤字。**欄ごとに任意かどうかを宣言する。**
- これは「例外の上限を決めていない」と同じ根 ——
  **どちらも取りこぼしを黙って安全側でない側へ倒している。**

### ⛔ 台帳を読む正規表現が、**行を黙って落とす**

要否や区分の欄は自然文で書かれる(「上屋敷は必須」「奥向があれば必須」「必須(室として)」)。
先頭一致を要求すると**その行が丸ごと存在しないことになる** — 2026-08-26 土井:
24行の表から2行が落ち、その2役割は錨の外で免除し放題だった。床(10行)も 22行では鳴らない。

- **欄をそのまま取り、分類できない欄は黙って落とさず止める。**
- 床は**実際の行数の近く**に置く(10行の床は 24→22 の欠落を拾えない)。
- ⛔ **ファイルも表も行も在るのに、パーサの都合で存在しないことになる** —
  今日見つかった「静かに壊れる」の中で最も静かな形。

### ⛔ **裁定は確度を上げない**

ユーザーの裁定は「置く/置かない」を決めるのであって、**在ったことを立証しない**。
2026-08-26 松平: 隅櫓を「置く」と裁定されたが、確度は **`?` に据え置いた** — 正しい。

- **裁定と確度は別の軸。** 裁定を確度の根拠に使うと、**自分の決定が典拠に化ける**(規則7)。
- 逆向きも要る: 一度**下げた**確度を後から黙って上げ直さない
  (`certRulings` に裁定を記録し、巻き戻しを検査が止める)。
- ⚠ **「実害が出ないから気づけない」型に注意。** `_pending` の宣言(直っても消えない)/
  `return []`(測っていないのに0件)/ 区画外のはみ出し(クリップされるので害が出ない)——
  どれも**静かである**ことが問題で、**0件という文字列が「測って0」か「測らずに0」か
  区別できない**のが根。**鳴らない検査は、無い検査より悪い。**

### ⛔ 隣家へ是正を求める前に、**自分の検査の適用範囲**を検め直す

2026-08-25、`shared_edge_check` が隣家ごとに**全辺**を回しており、隣家の復元ファイルが
当家の**共有でない辺**に届いているだけで「境界を動かした」と 2 件出していた。
**隣家が自分の敷地の中で正当に復元した値**である。文章にも「⛔ 現に食い違いがある」と書き、
是正依頼の直前まで行った。共有辺だけに絞ると **0 件**。

これは 2026-08-24 の「按分違い」で隣家2軒に誤った是正を求めかけた事故と**同じ型**である。
検査の名前(「共有辺」)と、検査が実際に回す集合(全辺)がずれていた。

- **隣家に何かを求める指摘は、送る前に必ず「その量は本当にその関係を測っているか」を検め直す。**
  自分の検査が出した数字は、自分の検査の適用範囲までしか保証しない。
- **検査の名前・メッセージの文言と、実装が回す集合を突き合わせる。**
  「共有辺」と書いたら共有辺だけ、「白洲か石段」と書いたら白洲と石段だけを通す。
  **文言のほうが強いのに実装が緩い**とき、0 件は「その緩い条件を満たした」以上を意味しない。

⚠ **`2>&1 | head` や `>/dev/null` で例外を隠すと、古い出力を新しいものと誤認する。**
生成が落ちているのに前回の HTML が残っていて「直った」と読んだ事故がある。

### 依頼する前に

**他人へ是正を依頼する数値は、依頼の直前にもう一度、根拠から測り直す。**
自分の検査が壊れている確率は、経験上けっして低くない。

## ⛔ 検証レンダは**外向き法線の符号を検算してから**撮る

`(u.y, -u.x)` と `(-u.y, u.x)` のどちらが外かは、多角形の頂点の回り方で決まる。
取り違えると**内側から撮った絵を街路側だと思って**判断してしまう(2026-08-29 に実際にやった)。
撮る前に「区画線から法線方向へ 10m の点が区画の内か外か」を point-in-polygon で1回確かめる。

**目の高さで撮る。** 俯瞰では塀を越えて中が見えるので、閉じの合否を判定できない。
地形をサンプルして **地盤 + 1.6m** にカメラと注視点を置く。

## ⛔ 裁定で「作る物」が変わったら、**検査の前提も一緒に動かす** ★★

2026-09-04 岡部の S2 実機流しで、**建った物は正しいのに検査が3件も嘘をついた**。

| 検査 | 古い前提 | 症状 |
|---|---|---|
| `ClosureQA` | 「表長屋は次巡」(裁定3=B)なので**練塀だけ**を実装の被覆に数える | 裁定12=A で表長屋が S2 に入った後も、建っている **79.66m を「素通し」**と報告 |
| `CheckScene` | 囲いの名は `runs`/`fences`/`komon` から採る | 表門(`gate` は単数で名を持たない)と汀の潜り(`nishi.saku.kuguri`)を**「孤児の囲い」**と報告 |
| 算出物の検め | 汀線を**当方で引き直して**杭と比べる | 生成器の引き方を再現できず 51/242 本を ✗(⛔ 検査が自分の模型を正典に据えていた) |

⭕ 作法は3つ:
1. **裁定で Stage の受け持ちが変わったら、その Stage を測る検査を必ず読み直す。**
   ⛔「実装だけ直して検査は前のまま」は、次の巡で**赤が出っぱなし**になって麻痺する。
2. **名前を持たない物を検査に教える。**単数のキー(`gate`)や入れ子(`saku.kuguri`)は
   名前の一覧に現れないので、⛔ 教えないと据えた物が全部「孤児」になる。
3. ⛔⛔ **生成器が算出するものを、検査が引き直して合否にしない。**
   汀線・散布点・隅の角度は生成器(算出物)が正典で、実装も検査も**読むだけ**。
   引き直すと「どちらが正しいか」が決められず、⚠ **合わないのは検査の側**であることが多い。
   ⭕ 合否にしたいなら**生成器にその線を焼かせて**、それと比べる。

⭐ 見分け方: **✗ が出たら、まず「建った物」でなく「検査の前提」を疑う。**
上の3件はどれも、シーンを見ると正しく建っていた。

## ⛔ 検査の**失敗が伝わるか**を、検査そのものとは別に試す ★★

検査を足しても、その**失敗が呼び出し元へ伝わらない**なら足していないのと同じ。
2026-09-04 岡部: 算出物の検め `ImplQA` を突き合わせへ繋いだが、呼び出し側の判定が

```csharp
if (report.Contains("✗") || report.StartsWith("★"))   // ⛔ これ
```

だったため、**★ が2行目以降に出る報告を一つも捕まえなかった**。`ImplQA` は
「1行目に見出し / 2行目以降に ★」という書式なので、**繋いだのに永久に鳴らない**状態だった。
目視では見つからない — 報告は正しく ★ を出しており、壊れていたのは**読む側**である。

⭕ 対処は二つで、片方だけでは足りない:

## ⛔⛔ 地形を書くとき、検算は「動かす所」でなく **「動かさない所」** を測る ★★★

**2026-08-31・外堀 00002/00003 の掘り直しで実際に踏んだ。** 設計面を Unity の地形へ書き戻すとき、

**なぜか。** スナップショットは**採った時刻の地形**であって、**いまの地形ではない**。

- 08-26 の溜池の掘り直し
- **08-29 のユーザー裁定で入れた 00001 のフィット(盛土 4,981 m³)**

が生きた地形に乗っていた。矩形を丸ごと上書きしたので、**それらを 08-26 の状態へ巻き戻した**。
⚠ **他家の造成・自分の過去の裁定ぶんを、黙って消す**。工区の中は正しいので、
図も検査も土量も全部合っているように見える。

### 検算がこれを構造的に見逃した

書き込みの前後で検算を回していたが、どちらも

```
if (|des - cur| <= 0.01) continue;   # ⛔ 動かす予定のセルしか見ていない
```

で始まっていた。**「動かさない予定のセルが動いていないか」を一度も測っていない。**
前検算は「maxDiff 0.000 で完全一致」、後検算は「平均誤差 0.0065m」と出て、**どちらも真**だった
— *動かす所については*。⭐ **検査の文言が測っている集合を、必ず声に出して確かめる**
(`check-must-name-what-it-measures` と同じ型)。

### 作法

1. ⭐ **書く範囲をマスクで絞る。**矩形で `SetHeights` するなら、**セルごとに
   「設計が動かす予定か」を判定して、そうでないセルは読んだ値をそのまま書き戻す**。
   「無害なはずだから丸ごと書く」は、スナップショットの鮮度に賭けているのと同じ。
2. ⭐ **施工後の検査は「施工直前の退避 `.bin`」と比べる。**現況スナップショットと比べてはいけない
   — 工区の中では一致していても、**外では最初から食い違っている**(この件では 1,734 セル・最大 8.04m)。
3. ⭐ 検算は必ず **2つの数を並べて**出す:
   **「設計どおり動いたセル数」と「意図せず動いたセル数」**。後者が 0 でなければ合格にしない。
4. 地形を触る前に必ず退避を取る(この件はそれだけで救われた)。⛔ **地形の編集は Undo の外**。

## ⛔ 「床を掘り下げれば根入れが増える」は**逆** ★★

**2026-09-06・土井。**受け石(浸透枡)で「天端は絶対高で動かさず、**床を 0.15m 掘り下げて**
根入れ ≥ 見付の 1/2 を満たす」という指示が来た。⇒ **成立しない**。

天端 `cap` が固定で石が剛体なら、**底も固定**。地盤を `d` 下げると
**見付 = cap − (地盤 − d) は増え、根入れ = (地盤 − d) − 底 は減る**。両方悪くなる。

⭕ 効くのは**石を大きくする**ことだけ。`根入れ ≥ 見付 × k` を満たす石丈は
**`h ≥ (1 + k) × (cap − 地盤)`**(k=0.5・突き出し 0.334m なら **h ≥ 0.501m**)。
⇒ `scale` はこの比から出す(⛔ 目分量で 0.55 → 0.95 と上げても届かない)。

⭕ **`digEach` のような欄は「据え穴の深さの申告」として読む** — 掘り代 < 根入れ なら石が納まらない、
という**別の検査**にする。⛔ 掘り代を地盤の高さと取り違えて `ground − dig` を使わない。

**すべきこと。** 再帰で歩き、**木そのものを名前で見分ける**(`Stage7b` は `<庭>_<役>_<通し番号>` と
名づけるので **末尾が `_数字`**)。木に当たったらそこで打ち切る(⛔ 部材側の `LOD_0`/`LOD_1` まで潜ると
数が 1.5 倍に膨らむ)。⛔ 「Transform 以外のコンポーネントを持つか」で見分けるのも不可 —
LODGroup を持たない部材(下草など)は根が素の Transform なので群と区別できない。

## ⛔⛔ 箱でできた部材の「面」を測る帯は、**頂点のある高さ**に取る — 面の途中に取ると 0 件になる ★★★

**症状(2026-09-09 松江松平で 2 回踏んだ)。**「躯体の面で測れ」という裁定どおりに
腰壁(局所 y 0.55‥1.40)の**真ん中** 0.60‥1.30 に帯を取ったら、**頂点が 1 つも入らず**
「躯体が測れない」と鳴った。次に門柱を 0.5‥3.5 の帯で測ったら、柱の**足元の頂点が落ちて**
扉だけを拾い、柱の外面を **0.42m 内側**と誤読した(継ぎ目が 0.42m の隙間に見えた)。

**原因。** 部材は箱の集まりで、**壁面の頂点は箱の上下の縁にしか無い**。帯を面の途中に置けば空になり、
帯の下端を床から浮かせれば柱の足元が落ちる。⇒ 「見た目に妥当な高さ」で帯を決めてはいけない。

**作法。**
- 帯は**部材の生成器(`Tools/Blender/build_*.py`)の実寸から、箱の縁の高さ**に取る
  (番所なら基壇の天端 = 腰壁の底 0.55)。⭐ 生成器の定数は EdoAssets の doc に**測って**書き写す。
- 下端は**据わっている高さ(敷居)そのもの**から始める。⛔ 「0.5m から」で始めない。
- 同じ高さに**別の部位が同居する**ときは、帯だけでは切れない(番所の y=0.55 には腰壁の底と
  **基壇の天端**が並ぶ)。⇒ **奥行の窓**(`|perp| ≤ d/2 + 0.05`)を併用する。
  実測: この窓で頂点 12 点・走り 4.250m = 指図の `w` ちょうど。
- ⭐ 上端も要注意 — 冠木は柱より **0.35m ずつ長い**。帯を上へ伸ばすと継ぎ目が「めり込み」に化ける。

**⭕ 検算の型**: 測った幅が**指図の呼び寸法とぴったり一致**したら正しい帯を引けた印。
0.40m や 0.42m のような**半端なズレは、たいてい部材の欠陥ではなく帯の取り方の誤り**。

## ⛔ 丸い石の「地盤線での差し渡し」は、帯を厚く取ると過大に出る ★★

**症状(2026-09-09 松江松平・板塀の根石)。** 部材方から「芯々は**地盤線の差し渡し**で詰めよ
(外接の 92〜96%)」と申し送られたので、局所 y=0 の**±0.05m** の帯で実測したら
**外接の 97〜100%** が返り、部材方の値と合わなかった。そのまま詰めると石のあいだに
最大 0.048m の隙間が開く(= 地盤線で空が抜ける、まさに警告された失敗)。

**原因。** 玉石は**真ん中がいちばん太い**ので、±0.05m の帯は「地盤線の差し渡し」ではなく
**近傍の最大**を拾う。⇒ 帯は頂点の輪の厚みぶん(**±0.005m**)で足りる。

| 個体 | 外接 | ±0.005 | ±0.02 | ±0.05 |
|---|---|---|---|---|
| L0.70 | 0.700 | **0.644** | 0.663 | 0.692 |
| L0.58 | 0.580 | **0.534** | 0.549 | 0.566 |

⭐ **合っている印**: ±0.005 の値が部材方の申し送り(0.395/0.414/0.469/0.520/0.534/0.582/0.635/0.644)と
0.007m 以内で一致した。⛔ 「だいたい 0.93 倍」を焼き込まない — **据えるたびに実測する**
(部材が焼き直されたら比も変わる)。

## ⛔⛔ 突き合わせ検査を **Renderer の bbox の芯**で作ると、正しく据えた部材が毎回「ずれている」と出る ★★★

**症状(2026-09-10 山王)。** 指図どおりに据えた社殿・段石・板塀が、新しい突き合わせ menu で
そろって ✗ になった。⭐ **どれも「据え付けは正しく、測り方が違う」**:

| 何 | bbox の芯が寄る量 | 理由 |
|---|---|---|
| 向拝(軒唐破風) | **0.50m** | 軒が東へだけ出る。`munes` の矩形は**柱通り**であって軒ではない |
| 幣殿・作り合い(両下造) | 0.09m | 同上(片側だけ軒が出る) |
| 段石 `Dan_*` | 0.05m | 上の段の下へ潜る差し込み(LAP 0.10)のぶん走り方向に非対称 |
| 板塀(`PanelRun` の表裏2枚) | 0.06m | 裏面を 0.12m 逃がして据えるので、両方を含めると半厚ぶん寄る |

**対処。**
・**据え付け点(`transform.position`)で測る** — 部材の原点がどこかは**部材の生成器の註が正典**
  (例: 「ピボット = その棟の区画の中心・地盤レベル」「踏面の中心・踏面の天端」)。
・**寸法はメッシュの OBB のローカル軸で測る**(`EdoBuild.ObbFootprint`)。
  ⛔ 世界軸の bbox を進行方向へ射影しない — **曲がった坂では必ず大きく出る**
  (実測: 幅 6.36m の女坂の段が 7.32m と出た)。
・表裏で据える部材は**表(`_kf`)だけ**を測る。
⭐ **部材の原点そのものが規約どおりか**は部材方の検算(`check_*`)の持ち分。実装側の検査で
二重に見ようとすると、⛔ 上のように**軒の出を据え付けの誤差として報告し続ける**ことになる。
