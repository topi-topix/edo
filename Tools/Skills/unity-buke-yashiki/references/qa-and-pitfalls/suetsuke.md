# 据え付け・部材・隅の罠(失敗事例集・36 件)

索引は `../qa-and-pitfalls.md`。⛔ 丸読みしない — 索引で当たりを付けて該当節を grep で引く。

## 「面」を測るときは、軒より下の帯の**頂点**で測る ★★

表門と塀の面が揃っているかを見るのに、測り方を3通り試すと**答えが3通り出る**(岡部邸 2026-08-15)。

| 測り方 | 出た値 | 何が混ざるか |
|---|---|---|
| AABB の角を外向き法線へ射影 | 5.36m | 棟が法線から6°ずれているだけで **+1.2m 過大**。角が外へ回り込む |
| renderer bbox 全体の頂点 | 3.86m | **軒の出**が混ざる。躯体の深い門ほど過大 |
| **軒より下の帯(壁の高さ)の頂点** | **3.74m** | 壁面そのもの。これが正しい |

```csharp
// y の帯[y0,y1]にある頂点の、外向き nout への射影の最大 = 街路側の壁面
static float FacePerp(GameObject go, Vector2 nout, float y0, float y1)
```

**面を揃えるときは「測る→動かす」を2回まわす。** 1回だと 0.06m 残る —
物を動かすと帯に入る頂点の行が変わるため。残差をログに出して 0 を確認する。

**天端の QA では面の不具合は出ない。** `PerimeterQA()`(天端の振れ)が合格でも、
街路面が棟ごとに 0.37m の鋸歯になっていたし、門が 3.74m 突き出していた。
**軸ごとに別のチェックが要る**(高さ / 面 / 棟の序列)。

## 門の位置は「下書きのマーク」でなく**外周線の上**に取る ★★

岡部邸の表門は下書き(切絵図トレース)の三角マークにそのまま置いていたが、
そのマークは外周線から **2.25m 内に外れて**いた。run の端点をその点で切ったので

- run の芯が外周線から **1.2°傾く**
- 棟は外周線の方位(yaw)で置く → 傾いた芯の上に平行な棟が並ぶ
- → 街路面が**棟ごとに 0.37m の鋸歯**になり、門へ向かって 1.83m 内へ流れた

**門の点は必ず外周線へ落としてから run を切る。** 門の直交位置(街路からの引き)は
別に、隣の棟の壁面から実測して合わせる。

## 据え・QA の落とし穴 — 2026-08-22 に表門で 6 回連続で踏んだ型

すべて**「部材の実体でなく、代用物を測っていた」**という一つの型。

| 症状 | 測っていた物 | 測るべき物 |
|---|---|---|
| 門が公道へ 6.5m はみ出す | 帯の中の最外(= 屋根) | 鏡柱 `kagami` の面 |
| 番所が 0.45m 内側に入る | `FacePerp` の帯の最外(= 屋根 `kera`) | 躯体 `wall` の面 |
| 接している所を「隙間」と誤検出 | 帯 y13.6〜15.6(門はここに躯体が無い) | **接触面の高さ**(門は小壁 16.056〜16.433) |
| 建っている run を「隙間」と誤検出 | 前方一致 `Hei_E_S_` / `Hei_E_N_` | 接頭辞でまとめる `Hei_E_` |
| 合わせ込んでも 0.219m 残る | 1 回動かして終わり | **収束するまで反復**（回転が絡むと非線形） |
| 矩形が 90° 違う | `localScale.x` を走り方向と思った | `Atan2(dir.x,dir.y)` は **+Z を dir へ向ける** → 走りは**ローカル Z** |

**規則**: 部材を測るときは必ず **部材名で絞る**（`PartFaceO(go, outw, "wall")` の形）。
`FacePerp` のような「帯の中の最外」は、**軒・破風・組物が混ざる**ので躯体には使えない。
QA の帯も「見た目に妥当な高さ」でなく **指図の接触面の y** から取る。

## 部材の「表」がどちらを向いているかを、据えてから1枚撮って確かめる

Blender で自前に起こした部材は、`export_fbx(axis_forward='-Z', axis_up='Y')` が
**Blender +Y を Unity の −Z へ写す**ため、論理座標のまま組むと表が反対側に出る。
詳細と直し方は `<repo>/Tools/Blender/README.md`「書き出しの規約」。

**検査**: 非対称な部材を据えたら、**その部材のローカル +Z の側から1枚撮る**。
そこに正面(格子・障子・扉・鳥居)が写らなければ反転している。

```csharp
var f = t.forward; f.y = 0; f = f.normalized;
Shot(png, t.position + f * 7f + Vector3.up * 3f, t.position + Vector3.up * 2f, false, 0, 1200, 900);
```

⚠ **前後対称な部材(冠木門・塀・櫓)では気づけない。**
松江松平邸では表門が対称だったので通り抜け、番所を据えて初めて
「出格子と向唐破風が敷地の内側を向き、街路からは無地の背面だけが見える」と分かった(2026-08-25)。

## 寸法と食い込みを world の AABB で測らない

回転間グリッドは斜めなので、**world の軸平行バウンズは実寸より膨らむ**。
13.8×8.9m の土蔵の AABB は 16.0×13.1m になり、4.7m 離れた厩と「食い込み」判定が出る
(2026-08-25 に偽陽性5件)。

- **寸法** … 子メッシュ全部を root のローカル系へ写して合成する。
  ⚠ 先頭の `MeshFilter` だけ見るのも誤り。edogoyomi の obj は 30 以上のサブメッシュに
  分かれていることがあり、4.65m の門が 1.24m に見える
- **食い込み** … 水平の OBB を**分離軸法**で測る(4軸で足りる)
- **指図の段階** … そもそも Unity を通さず **(u,v) グリッドの矩形**で総当たりするのが一番確実。
  生成器側に置けば、実装する前に落ちる

## ⛔ 「外周が閉じているか」は、**高さを見ない 2D の判定では測れない** ★★

平面の footprint だけで塞がっているかを見ると、**同じ検査が両方向へ嘘をつく**
(2026-08-29・松江松平邸)。

- **崖を素通しと誤報する** … 西辺(堀端通り=溜池東岸、地盤 8.9m。敷地内は 22.8〜29m)を
  「214m 素通し」と報告した。実際は 14〜20m の法面で、指図も塀ではなく法面で受ける設計。
- **逆に、閉じている門を素通しと数える** … 犬走り(0.30m)ぶん退がった門や塀は、
  区画線そのものの上が自由空間になる。線をまたぐ自由セルを数えるだけの判定は、
  塞がっている門を「12.28m 開いている」と挙げた。

**測り方**: 外の種からフラッドフィルし、**隣のセルへ移れるのは段差が歩ける範囲のときだけ**
にする(0.25m 格子で許容 20〜30°)。区画線から **1.0m 内側**へ入った時点でそのセルを
侵入口として記録し、**そこから先へは広げない** — 記録せずに広げると、一箇所漏れただけで
内部が全部つながり、全辺が「侵入口」に見えて何も分からなくなる。

**閾値は必ず振る。** 20°/30°/40° で回して、答えが変わらない範囲を確かめる。
松平では 20〜30° で 0 箇所、40° でようやく宣言どおり法面の辺だけが挙がった。
一つの閾値の結果だけを報告しない。

地形は Unity から格子で吸い出して `.bin` にしておくと python 側で何度でも回せる
(1256×1153×float32 = 5.8MB)。

## ⛔ 隅部材の「腕」を `joints` にだけ書くと、**実装へ一つも渡らない** ★★

留め継ぎの隅では、隣り合う run の端を隅部材の腕ぶん切って空ける。この腕を
`joints`(取り合い表)にしか書かないと:

- **図の側**は腕を実体として数えるので、閉じの検査が 0 件で通る
- **実装の側**は `runs` しか読まないので、腕は一つも建たず**隅がそのまま口になる**

2026-08-29 の松江松平邸で、隅 P13(辺13 s0〜2.96)と隅 P0(辺14 s123.45〜125.74)が
この形で開いていた。しかも当時のビルダーが長屋の鎖を run の中央へ寄せていたため、
はみ出した駒が**たまたま**塞いでいて発覚しなかった。中央寄せを撤去した瞬間に露出した。

→ **切った腕ぶんは必ず `runs` へ書き起こす**(練塀 run として1本足す)。
→ 検査は「図の上で何かが当たるか」ではなく、**建てる対象の帳簿で覆えているか**で見る。
   全頂点と全辺を走査し、**腕は単独では閉じに数えない**。
   囲いを持たない辺(法面で受ける等)は宣言を置き、宣言を消せば鳴るようにする。

## ⛔ 扉を足す前に、門が**自前の扉を持っていないか実物を見る**

edogoyomi の冠木門は `doorl` / `doorr`(+ `sdoorl` / `sdoorr`)を躯体に抱えている。
その上へ別部材の扉を重ねると、開口ではなく**門の顔を板で覆う**。
2026-08-29 の松江松平邸では、重ねた `Gate Castle` の材がテクスチャを持たないため、
御蔵門・東小門が真っ白な板になり、冠木も扉も見えなくなっていた。

判定は**据えた門の実メッシュの子の名前**で行う。門の名前や指図のキーで決め打ちしない
(⇒ CLAUDE.md 絶対規則5「置いた駒の実メッシュから測る」と同じ原則)。
⛔ 指図の `leaf` は消さない — 消すと閉じの検査が「開口が素通し」と誤判定する。
「躯体が自前で持つ」と読める形(`leaf.by`)で残す。

## ⛔⛔ 部材は「呼び寸法」で置かない。**据えてから見え面を測って寄せる** ★★★

2026-08-29 深夜、ユーザーがブックマーク15枚で外周の不具合を指摘した。実測すると
**4つの別々の欠陥**に分かれたが、原因は全部同じ ——
**推定した値で置いて、実物に当てていない**。ユーザーの言葉は
「根本的に設計の際の考え方を見直さないと解消しない」。

| 何を推定で決めていたか | 何が起きたか |
|---|---|
| 部材の呼び寸法を「壁の長さ」だと思っていた(実は**屋根の全長**) | 隣り合う run の**壁が 0.64m 空き、軒だけが渡る**。両端 0.32m ずつ内側 |
| 駒の箱の向きを**スキルの記述**で決めていた | 実測は `[pos, pos+2.0s]`、記述は `[pos−2.0s, pos]`。石垣が run ごと**丸ごと1駒ぶんずれる** |
| 壁の高さに合わせて駒を**等倍で拡大縮小** | 隣り合う run で石の大きさが **7.3倍**違う。ずれ量も駒に比例するので隙間・重なりが必ず出る |
| 外向き法線を**多角形の重心**で決めていた | 凹みのある区画では成り立たない。1辺だけ 180° 反転し、塀が**隣家側へ 0.95m** 出ていた |

### 守ること

1. **呼び寸法 ≠ 見え面。** 部材を頼む長さは「その部材の**どの面**の間隔か」を必ず確かめる。
   屋根の軒・破風・鬼・反りは端ではない。⇒ 頼む長さ = run 長 + 2×(軒の出)。
2. **ピボットと箱の向きは文書で決めない。**1枚置いて `transform.position` と
   実メッシュの箱を比べ、`[pos, pos+w]` か `[pos−w, pos]` かを**その場で測る**。
   スキルに書いてあっても信じない(このスキル自身が逆に書いていた)。
3. **モジュール部材の大きさは変えない。**端数は**重なりで吸う**、高さは**地中への埋まりで**吸う
   (2026-08-29 ユーザー裁定)。`N = ceil((L − W)/pitchMax) + 1`、`pitch = (L − W)/(N − 1)` と
   すれば pitch ≤ pitchMax が保証され、**隙間は原理的に出ない**(重なりは常に下限以上)。
4. **外向き法線は多角形へ当てて決める。**法線方向へ少し出た点が区画の外かを内外判定で見る。
   重心・面積符号・「たぶんこっち」は使わない。凸多角形でしか成り立たない近似を凹み区画へ当てない。

### 関門(これが無かったから 4 つとも 0 件で通った)

犬走りQA は**外向き d しか見ていない**。**辺に沿う s の端を測る検査**を対にして必ず置く:

- 層ごと(石垣 / 囲い)に**据えた実メッシュから走り方向の端面**を測る
- 指図の s0/s1 に乗っているか / **隣り合う run の端面どうし**に隙間が無いか
- モジュール部材が**実寸のまま**か(scale≠1 を挙げる)

⛔ **壁を部材名で選ってはいけない。** Blender で起こした部材は**単一メッシュ**のことがあり、
`WallFace` のような名前集合に一つも当たらず、**その部材が丸ごと検査から抜ける**
(2026-08-30 に自分で踏んだ。「囲い 31 run」と出ていたが長屋10本は測られていなかった)。
**座から 0.6〜1.4m の水平な薄切り**で取る — 練塀でも一階でも二階でも、この高さは壁の実体しか通らない。
⇒ [[check-must-name-what-it-measures]]

## ⛔⛔ 他邸の「yaw の式」を、**手系を確かめずに**移さない ★★★

**2026-09-06・土井大隅守上屋敷を新造したときに踏んだ。**松平のビルダーの

```csharp
static float YawAlongU() { return Mathf.Atan2(-f.vx, -f.vz) * Mathf.Rad2Deg; }
```

をそのまま持ってきたら、**7棟すべてが 90° 回って**据わった(表役所は設計位置から 18.2m ずれ、
居間は 16間の桁行が u でなく v に架かった)。原因は**回転間グリッドの手系が邸ごとに違う**こと:

- 松平の (u,v) は世界に対して**左手系**(det = ux·vz − uz·vx = **−1**)
- 土井の (u,v) は**右手系**(det = **+1**。指図 `grid._` に「(u,v) は世界と同じ向き」と書いてある)

Unity の local(+X,+Z) は yaw をどう振っても同じ手系なので、**合わせるべき (u,v) の対が違う**。

### 回転の式(実測で確かめること・暗記しない)

Unity の Y 回転は `local +X → (cosθ, −sinθ)` / `local +Z → (sinθ, cosθ)`(x,z 平面)。⇒

| したいこと | yaw |
|---|---|
| **+X(走り)を向き d へ** | `Atan2(−d.z, d.x)` |
| **+Z(見え面)を向き d へ** | `Atan2(d.x, d.z)` |

⛔ **この2つを取り違えると物が 90° 回る。**同じ日に**棟・長屋・垣**の3箇所で踏んだ。
特に `Atan2(dir.x, dir.y)` は「走りへ向ける式」に**見えて** +Z を向ける式である。

### 作法

1. ⭐ **移す前に det を測る。**`det = ux·vz − uz·vx` を1行出せば済む。
2. ⭐ **据えてから「local +X / +Z が (u,v) でどちらへ伸びたか」を実測する**
   (`t.TransformPoint((1,0,0))` を Grid.L で落として差を見る)。式を睨まない。
3. ⛔ **AABB の四隅を回転軸へ投影して「ずれている」と判定しない。** 回転ぶん膨らむので
   10間角の棟が 18.2間 に見える。⭕ **メッシュの頂点**を (u,v) へ落として範囲を取る。
   (この誤診で最初「棟が巨大化した」と読み違えた。)
4. ⭐ 検査側(`EdoSashizuExport.CheckScene`)は既定で松平式のピボットを使う。
   **右手系の邸は `Houses[id].pivot` に自分の式を渡す** — 渡さないと桁行が v の棟が毎回
   「ずれている」と出る(規則19: 検査だけが式を持たない)。

**関連**: CLAUDE.md 絶対規則5 / `buildings.md`(u,v)フレーム

## ⛔ 部材のピボットは「体の中心」ではない — **走りだけでなく梁間も実測して寄せる** ★★

**2026-09-06・土井の厩と家中長屋。**`es_knagaya` の壁は local Z が **−5.37〜−1.07**、
つまり**体が丸ごと −Z 側に寄っている**(ピボットは体の外)。

- 設計矩形の**中心にピボットを置いた**ら、棟が **3.2m** ずれた(厩)。
- 区画線から犬走り 0.30m 控えたつもりが、外面は **1.37m** 引っ込んでいた(表長屋)。

⭕ **走り(X)と同じように梁間(Z)も測り、`ZC = (zLo+zHi)/2` で芯を戻す。**
外面を合わせるときは `zHi`(見え面側の面)を使う: `pivot = 目標面 − outw·(犬走り + zHi)`。

### あわせて — **run の端は「端の駒を端に合わせる」**

端数を等ピッチで中央寄せにすると、端の駒が `(駒幅 − ピッチ)/2` だけ run の外へ出る。
土井では表長屋が**門の開口へ 0.71m 食い込んだ**。⭕ `a_i = s0 + (L − W_i)·i/(n−1)` にすれば
端の2駒が run の端にぴたりと付き、余りは内側の継ぎ目で重なって吸える(⛔ 隙間は作らない)。

⚠ **見え面(+Z)を外へ向けた時点で、走り(+X)の向きは選べない** — `+X = (outw.y, −outw.x)` が
辺の +s と同じ向きか逆かは辺ごとに違う。⭕ `sgn = dot(+X, 辺の向き)` を測ってから
ピボットの s を決める(`sgn>0 → a − lo` / `sgn<0 → a + hi`)。**妻(破風・鬼)を持つ端の駒
`l`/`r` も sgn で入れ替える** — でないと妻が run の中で向き合う。

## ⛔⛔ 厚みが左右非対称な部材の「外」は、**隣の部材の面と突き合わせて**決める ★★★

**2026-09-06・土井の裏木戸(`Own.Kido(1.8)`)。**練塀の中に立つ木戸なので、部材は
**練塀の組と同じ厚み**で焼いてある。ところが `DobeiRun` の組は**芯対称ではない**:

- 外側の1枚は **bbox の中心が run の線**に乗る(±0.576)
- 内側の1枚は そこから **0.20 内へ** ずれる(−0.776..+0.376)
- ⇒ 組の全体は run の線から **外 0.576 / 内 0.776**(合計 1.352)

木戸の実測は local Z が **[−0.576, +0.776]**。指図と `EdoAssets` の註はどちらも
「**+Z = 外(街路側)**」と書いているが、**その向きで据えると練塀と両面 0.20 ずつ食い違う**。
⭕ 正しいのは **−Z を街路へ**向けること(local +Z = 内)。生成器が書き出す前に
Z まわりに 180° 回すので、docstring の「+Z」は Blender 空間の話で Unity では裏返っている。

### 作法

1. ⛔ **docstring の「+Z = 外」を信じて向きを決めない。**厚みが非対称な部材では、
   **どちらの側がどれだけ出るか**を実測し、**隣に立つ物の面と合う向き**を選ぶ(規則5)。
2. ⭐ **据えてから run の線を基準に測って報告する**。土井のビルダーは
   `ProjMesh(go, 外向き法線)` で「run の線から 外 x / 内 y」を必ず1行吐く。
   合っていれば `外 0.576 / 内 0.776` と練塀の組にぴたり一致する。
3. ⛔ 芯(pivot)どうしを合わせない。芯対称でない部材では芯を合わせた瞬間に面がずれる。

## ⛔⛔ 隅の横合わせ:「外向き法線への最大投影」を全頂点に掛けると入隅で外面を取り違える —
**腕ごとに頂点を選り分けてから測る。選り分けは動かす前の1回きり** ★★★

**2026-09-07・松江松平邸(`AlignInubashiri` 再修正・EDO-0147 続き)。** 上の「2辺=2式」解法
自体は正しいが、外面 `best` を測る頂点集合の選び方に2種類の欠陥があった。

① **「辺のどちらの直線に近いか(垂線距離の大小)」で腕を振り分けると、入隅(凹)で破綻する。**
   凹の隅ではもう一方の腕の頂点が幾何的に「反対側の直線」の方へ近寄ることがあり、
   垂線距離だけでは正しい腕に振り分けられない(実測: `Kado_J_P2` の外接箱中心が
   (−608.09,1156.23)→(−612.22,1160.78) と 5.9m 飛んだ)。
   ⭕ **直し方**: 隅の折れ点 P(=辺 e1 の終点=辺 e2 の始点)から、腕 e の**走り方向 t_e**
   (外へ向く単位ベクトル)を作り、頂点 v が腕 e に属するのは
   「`(v−P)·t_e ≥ 0`(その腕の外向きにある)かつ `(v−P)·t_other ≤ しきい値`
   (相手の腕の走りへはみ出していない)」の物だけ、と決める。しきい値は壁厚の程度
   (実測で 0.4〜0.8m の範囲で結果が安定することを確認、`KADO_ARM_THRESH=0.6`)。

② **選り分けを「動かした後の現在位置」で毎パス取り直すと発散する。** 選り分けの式
   `(v−P)·t_e` は補正のたびに全頂点へ一様に補正量が足し込まれる形(線形)なので、
   1回目の補正が大きいと「その腕に属する頂点が1つも d≥0 を満たさなくなる」ことが起こり、
   2回目のパスで `best` が取れず、そこから解がさらに暴走する(実測: P2 で 2 回目に
   「該当頂点なし」→オフセット再計算で 6.15m まで発散、これが①の 5.9m の実体)。
   ⭕ **直し方**: 選り分けは**呼び出し時点(まだ動かす前)の頂点位置で一度だけ**行い、
   選ばれた頂点集合は固定したまま `best1`・`best2` を測って2元1次方程式を解く。
   dot 積は並進に対して線形なので、この方式なら**一発の解で厳密に収束する**
   (パス を分けて再選別する必要が無い。実際に2回目を計算しても残差は 1e-14 オーダー)。
⭐ **一般化**: 「凸のケースで動作確認した選り分けロジック」は凹のケースで別の頂点を
   拾ってしまわないか必ず疑う。selecting-then-measuring 系のアルゴリズムを反復させるときは、
   **選り分けの基準が、反復で動かす変数自身に依存していないか**(依存していれば選り分けを
   1回で固定するか、選り分け自体を並進不変な量で作り直す)を確認する。

## ⚠⚠ 隅(単一メッシュ)と run(前後2枚)は「外面」の測り方が違う —
**近く直線(小さい折れ角)の隅ほど、その差が拡大される** ★★

**2026-09-07・松江松平邸。** 上①②の修正で `Kado_J_P2`(折れ角 87.76°、直角に近い)は
`CloseKadoSeams` の ⚠ が 0 件になったが、**`J_P1`・`J_P13`(折れ角 18.5° 前後、ほぼ直進)**

## ⛔⛔ `MeshBody` の一様な間引き(900点)は、隅部材(単一メッシュ)の**留め継ぎ先端の疎な頂点を

(腕の走り方向がほぼ反対向き)で効かなくなっている」だった。**窓を「腕の中心線 `d_e・cosθ` からの
残差」に直し(θ=両腕のなす角。腕が浅いほど `d_other` が `d_e` にほぼ比例して増えることへの対策)、
しきい値も壁厚の実寸(`dobeiWallT`)から導く**よう直したところ、**選り分けの窓を極端に広げても
(0.6→1.5→∞)`best1`/`best2` の値が全く変わらない**ことが分かった — つまり窓は原因ではなかった。
⭕ **本当の原因**: `MeshBody(tr)` は `int step = vs.Length / 900` で頂点を一様間引きするが、
隅部材(`Kado_*`)は**単一メッシュで 1.6〜1.8万頂点**あり、間引くと留め継ぎの先端(疎にしか
頂点が無い領域)の極値が**間引きの網から漏れて丸ごと消える**。実測: 間引きなし(全頂点)で
測り直すと、同じ隙間が 0.46m→0.19m、0.43m→0.17m まで**半分以下**に縮んだ。
⭕ **直し方**: `MeshBody` に `maxSamples` 引数を追加し(既定 900・他の呼び出し元は無改修で
従来どおり)、**隅部材(Kado)側の頂点取得だけ** `MeshBody(kc, 999999)`(実質間引かない)に
変える。隅は常に数万頂点・数mの小さい範囲なので全頂点でも軽い。相手の run/長屋(数万頂点級)は
従来どおり間引いたままで性能上問題ない(隅×run の最近傍探索は片方が900点あれば十分)。
⛔ **さらに踏んだ罠**: 「外面が揃ったのだから、走り方向で重なっていても run を伸ばして残り
(0.02〜0.13m)を詰めてよいはず」と判定を緩めてみたが、**実測すると隙間はほぼ変わらなかった**
(P0/P1/P3/P13 は直角でない留め継ぎなので、run を**自身の走り軸に沿って**伸ばしても隅の断面には
斜めにしか近づかず、3D 最短距離は縮まない)。⇒ この案は撤回し、判定は「走り方向で重なっていれば
横のずれとして報告するだけ(伸ばさない)」の原型に戻した。
⭐ **一般化**: 「選り分けの窓/しきい値を疑う」前に、**そもそも比較対象の頂点集合が正しく取得
できているか(間引き・キャッシュ・命名フィルタの取りこぼし)を先に検算する**(このスキルの
「検査の原因の見立てを、直す前に必ず自分で検算する」節と同じ教訓の再発)。窓を変えても測定値が
1mmも動かないなら、窓はそもそも効いていない=原因ではない、という**反証実験**が近道だった。

## ⛔⛔ 隅部材(単一メッシュ)の「頂点を辺方向へ射影した最大値」は、腕の全長(≈4.10m)を
返すだけで、指図が言う「腕」(留め継ぎとして使う長さ)には一致しない ★★★

**症状(2026-09-08 松江松平・棟梁の実測依頼)。** `docs/Sashizu/matsudaira_dewa_sashizu.json`
の `kado.parts.Dobei_Kado_88M.armRaw` は「棟梁がUnityで置いた実部材(世界 3.27m)」を根拠に
2.274→1.799 へ直された(632c19fe)ばかりだった。ところが**同じ隅(`Kado_J_P2`)を、この
ファイル自身の `EdgeAlong`/`MeshBody`(間引きなし・全頂点・辺方向への射影の最大値)で測り直すと
4.102〜4.103m** が出る — 「実測 3.27m」と **0.83m 食い違う**。高さ帯(座+0.6〜+1.4m)で
壁体だけに絞る方式(run 端QAで使う方式)で測っても同じく 4.06m 前後で変わらない。しかも
**P0/P1/P3/P13(角度も部材も違う4種)を同じ方式で測っても、すべて 4.06〜4.11m に揃う**
(折れ角 18.5°〜91°まで様々なのに、腕だけがほぼ同一長)。

**原因(暫定)。** 断面幅(辺方向への射影 vs それに直交する幅)を帯ごとに切って調べると、
留め継ぎの「折れ」を表す幅広の断面は隅の頂点から 1.0m 前後で収まり、そこから先(1.0〜4.1m)は
**幅が一定(≈0.016m 刻みで安定)の、ただの直線壁の延長**になっている。つまり `build_kado.py` は
**角度に関わらず一定長の直線壁を隅の先に継ぎ足して**アセットを作っており、「頂点の最大射影」は
その**継ぎ足しの端**(=アセットの外形いっぱい)を返すだけで、実際にどこまでを「隅部材が受け持つ腕」
として使い、どこから先を**別駒の直線材に譲る**かは、**アセットの形状だけからは一意に決まらない**
(1.0m〜4.1mのどこで切っても、切り口の左右で同じ直線壁が続くので見た目の破綻はない)。

**⛔ してはいけないこと。** 「同じやり方(頂点を辺方向へ射影)で測ればP0/P1/P3/P13も検算できる」
と思い込まない。P2 の 3.27m 自体がこの方式の出力と一致しないので、**この方式は『実測 3.27m』の
再現法ではない**(別の作り方 — 例えば隣接 run の据わり位置からの逆算や、目視でのスクリーンショット
判定 — で出された可能性が高いが、その手順は指図にも実装コメントにも残っていない)。

**⭕ すべきこと。** 「隅部材の腕は◯◯m」という数値そのものより、**まず算出手順を指図か
棟梁の作業ログに残させる**(規則19「輪に入っていない値は未検査」)。再現できない実測値は、
それが既に指図に書かれていても**未検査のまま**として扱い、`edo-buzai` に隅アセットへ
run と同じ命名の部材分割(留め継ぎの終端に印を持たせる)を作ってもらうのが根本解(このスキルの
「隅(単一メッシュ)と run は『外面』の測り方が違う」節と同根)。

## ⛔⛔ 御殿の帯割り屋根(`RoofBanded`)は**四方に入側 1 間を足して焼かれる** — `irikawa` が [1,1] でない棟では 1 間ずつ大きい ★★★

**症状。** 指図どおりに `munes[].roof.bands` / `spanKen` で部材を引いて据えたのに、
`[GotenKit] <棟>: 屋根が棟に合っていない` が並び、**隣り合う棟の屋根が食い込む**。
2026-09-09 の松江松平では表向の 4 棟(役所・黒書院・大広間・玄関)の屋根が
**u 方向に 3.18 間(5.78m)重なり**、真上から見ると 4 棟が 1 枚の屋根に融けていた。

**原因。** `Tools/Blender/build_goten_roof.py -- banded <帯> <桁行>` は
**総寸 =(Σbands + 2)間 ×(spanKen + 2)間 + 軒 0.59 間 ×2** で焼く。つまり
**入側 1 間を四方に必ず足す**。ところが指図の `bands` / `spanKen` は
`munes[].roof.irikawa` を辺ごとに引いた**身舎**の間数なので、
**`irikawa` が [1,1] でない軸では部材が 1 間ずつ大きくなる**。
`irikawa` が四方 [1,1] の棟(中奥・大台所)だけがぴったり合う。

**測り方(名前を信じない・規則5)。** FBX の全頂点の X/Z の伸びを間で出し、
`(Σbands+2)` と `(spanKen+2)` に軒 1.18 間を足した値と比べる。
非 `_v` は **X=桁行 / Z=梁間**、`_v` は **X=梁間 / Z=桁行**(90° 回して焼いてある)。

**差し戻し先。** 部材方(`edo-buzai`)— `build_goten_roof.py` に**辺ごとの入側**の引数が要る。
⛔ 棟梁が横に縮めて誤魔化さない(瓦の目と破風が潰れる)。⛔ 指図の `bands` を書き換えない。

## ⛔⛔ 帯割り屋根の**帯順**は焼いた FBX を実測して確かめる — 回転版(`_v`)と非回転版で逆になっていることがある ★★★

⇒ run 全体で1つの向きに決めると下端が裏返る。

**対処。** `runs[].profile` の各点で **見付高 > 0 の点だけ**を使って多数決する
(見付 ≤ 0 の点は⛔そもそも建てない=埋まっている壁)。左右のどちらが「受けている側」かは
**設計面が天端と一致する側**で判る(`const.wallProbeM` の距離で `graded` を引く)。
⚠ **両側とも天端と違う壁がある**(回廊の基壇の4本 — 両面が見える)。この場合は多数決が 0 票になるので、
**同じ接頭辞の壁が囲む矩形の中心から外へ**を落とし穴の無い既定にする。

## ⛔ 地形の節点は 2m・設計面は 1m — **面の縁が丸ごと造成されずに残る** ★★

**2026-09-10 山王。** 算出物 `graded`(1m 刻み・未造成は null)を「4隅がそろったセルだけ双一次」で
書くと、**面の縁の地形節点が全部落ちる**。前庭(16×32m)は縁の比率が高いので
**標本の 20% が許容 0.30m の外**のまま残った(切土 3193m³ という嘘の数も出た)。
⭕ 4隅がそろわないときは **1セル以内の最寄り**で拾う(縁を1節点だけ延ばす)と 20% → 3% に落ちた。
⛔ それ以上は外挿しない — 設計面の外の地形を動かすことになる。
