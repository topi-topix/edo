# Unity MCP・コンパイル・claim の罠(失敗事例集・16 件)

索引は `../qa-and-pitfalls.md`。⛔ 丸読みしない — 索引で当たりを付けて該当節を grep で引く。

## ⭐ Unity を握らずに C# を型検査する — 同梱の Roslyn を直接叩く ★★

**Unity の claim を持っていない間でもビルダーの書き直しは進められる。** Unity のインストールには
Roslyn と .NET SDK が同梱されているので、`Assets` のスクリプトを**エディタに触らずに**
コンパイルできる(2026-09-03 岡部の起こし直しで確立。1,090行の新ビルダーを claim を返した状態で
0 error まで詰めた)。

```
ED=/Applications/Unity/Hub/Editor/<version>/Unity.app/Contents
$ED/Resources/Scripting/DotNetSdk/dotnet \
  $ED/Resources/Scripting/DotNetSdk/sdk/<sdk>/Roslyn/bincore/csc.dll @rsp
```

`@rsp`(応答ファイル)に入れるもの — ⚠ **ここを間違えると本物のエラーが数千件の偽エラーに埋もれる**:

| 入れる | 入れない |
|---|---|
| `-nostdlib+` と `Resources/Scripting/NetStandard/ref/2.1.0/*.dll` | ⛔ `UnityReferenceAssemblies/unity-4.8-api/*.dll` — netstandard と `mscorlib` が**二重定義**になり CS0433/CS0518 が数千件出る |
| `Resources/Scripting/Managed/UnityEngine/*.dll`(モジュール群・173本) | ⛔ `Managed/` **直下**の `UnityEngine.dll`/`UnityEditor.dll` — モジュール版と型が**二重定義**になる(CS0433 の山) |
| `Library/ScriptAssemblies/*.dll`(パッケージ側) | ⛔ `Assembly-CSharp.dll` と `Assembly-CSharp-Editor.dll` — いま自分が作り直している当のアセンブリ |
| `Assets/**/*.cs` を**全部**(Editor 配下も含む) | — |

⚠ **ソースは `find` の結果を応答ファイルへ1行1本で書く。** シェル変数へ入れて渡すと
zsh は語分割しないので「巨大な1個のパス」になり `CS1504 パスが長すぎます` で落ちる。
⚠ 探し漏れに注意 — 当プロジェクトは `Assets/Edo/Scripts` のほかに `Assets/Edo/Editor`(WaterBaker ほか)
にもソースがある。落とすと `CS0103 名前が存在しません` が出て、**自分の書いたコードの誤りに見える**。

⭕ これで捕まるのは型と構文だけで、**据わり方・見え方は捕まらない**(それは普請検査の担当)。
⭕ それでも、Unity を待っている間に「コンパイルが通る状態」までは持っていける。

## ⛔⛔ 長い待ち(コンパイル・重い Stage)のあいだに **unity の claim が失効して他セッションに取られる** ★★★

**2026-09-04・松江松平を建てている最中に実際に取られた。**claim の TTL は 45 分だが、
心拍は**門番のコマンドを打った時だけ**更新される。この日は他セッションが FBX を連続で
書き出していて Unity のアセットインポートが詰まり、**1回のスクリプトコンパイルに 30分以上**
かかった。その間こちらは `find`/`lsof` で dll と 6401 番ポートを見ているだけで、
門番のコマンドを一度も打っていない。⇒ **claim が失効 → 隣が `--unity` を取得 →
こちらは待ち行列の1番へ**。⚠ **建てかけのシーンは未保存・プレハブも未書き戻し**のまま宙に浮く。

### 作法

1. ⭐ **待ちループの中で claim を打ち直す。**`until <条件>; do sleep 5; done` で待つなら、
   同じループで **`edo_session.py start <屋敷> --unity`** も回して心拍を維持する
   (既に持っていれば no-op で、これが唯一の心拍更新手段)。
2. ⭐ **重い Stage の前に、その Stage が何分かかるかを見積もる。**5分を超えそうなら
   先に心拍を打つ。⛔ 「すぐ終わるはず」で待ちに入らない。
3. ⛔ **取られてから慌てて `start` をループで叩かない** — 叩くたびに待ち行列に入り直して
   順番を失うことがある。`status` で自分が何番かを見てから待つ。
4. ⭐ **区切りのいい所でシーンを保存しておく。**取られた瞬間に未保存だと、
   隣のセッションのシーン保存に自分の建てかけが混ざる/混ざらないが運任せになる。

**関連**: CLAUDE.md「Unity は排他」/ `docs/session-coordination.md`

## ⛔ `read_console` は**複数行の1エントリを先頭行しか返さない** ★★

**2026-09-04・松江松平の Stage6 で踏んだ。**ビルダーの Stage は
`Debug.Log("[X] " + StageMethod())` の形で、**戻り値の表(十数行)を1エントリで**吐く。
ところが `read_console` が返す `message` は**その先頭1行だけ**だった
(`format: "detailed"` でも同じ)。⇒ 「石段 K_Mon …」の1行しか見えず、
**その後に並んでいた ★ の指摘(隅櫓が袖塀に 1.49m 食い込む)を危うく見落とすところだった**。

⭕ **対処**: 結果の全文が要る Stage は、メニューでなく
**`execute_code` で static メソッドを直接呼んで戻り値を受ける**。

```csharp
return EdoMatsudairaDewaBuilder.Stage6_Zosaku();   // 表が丸ごと返る
```

⛔ ただし**冪等な Stage に限る**。造成・掘削・盛土は二度流すと壊れる
(下の「MCP タイムアウトは失敗ではない」を先に読む)。

## ⛔⛔ MCP の `Timeout receiving Unity response` は **「失敗」ではない** ★★★

**2026-09-04・御泉水の掘削(`WaterBaker.Recarve`)で実際に起きた。**
`execute_code` が `Timeout receiving Unity response` を返したので一瞬「流れなかった」と読んだが、
**Unity 側では完走していた**。ここで再送していたら **Recarve が二度走り、
先に隆起させた岬と中島が平らに戻る**(しかも地形の編集は Undo の外)。

### 作法

1. ⭐ **タイムアウトは「返事が来なかった」であって「実行されなかった」ではない。**
   非冪等の Stage では、**必ず先に痕跡を見てから**再送を決める。
2. ⭐ 痕跡は **active なマーカー**で見る(`Niwa/_markers/<stage>`)。
   ⛔ `GameObject.Find` は非アクティブを見つけないので、マーカーは必ず `SetActive(true)`。
3. ⭐ タイムアウトのあとは **Unity の %CPU が落ちるまで待ってから**問い合わせる
   (`ps -Ao %cpu,comm | grep "MacOS/Unity$"`)。走っている最中に問い合わせても繋がらない。

## ⛔ dll が更新されないときは、`read_console` でなく **`Logs/Editor.log`** を見る ★★

**2026-09-04。**ビルダーに手を入れて `refresh_unity` を投げ、dll の mtime を
30 分見張ったが**一向に更新されなかった**。`read_console` にはエラーが出ない
(ブリッジがリロード中だと拾えないうえ、そもそも接続が切れている)。
実体は**コンパイルエラーで止まっていた**だけで、`Logs/Editor.log` の末尾に1行あった:

```
EdoMatsudairaDewaBuilder.cs(1425,73): error CS0136: A local or parameter named 'pv' cannot be declared ...
*** Tundra build failed
```

⭕ **対処**: dll の mtime が動かないときは **`tail -40 <repo>/Logs/Editor.log | grep "error CS"`**。
⚠ ログは `~/Library/Logs/Unity/Editor.log` **ではなく**プロジェクト直下の `Logs/Editor.log`
(起動時に「Logs moved to project-relative Editor.log file」と出て移る)。
⭐ 待ちループの終了条件に **「dll が新しくなった **または** Editor.log に error CS が出た」**を入れる。

## ⛔ `Stage0 ハイトマップを退避` は、**既にファイルがあると黙って上書きしない**

**2026-09-04。**メニューを実行しても `退避は既にある(上書きしない): …` と返るだけで、
中身は **2026-08-23 の 12 日前の地形**だった。⇒ 「退避を取った」つもりで進むと、
**復元用として使えない**(それを書き戻すと他邸が 12 日ぶん巻き戻る)。

⭕ **対処**: Stage0 とは**別に、着手時刻を名前に入れた全面スナップショット**を自分で取る。

```csharp
// Library/EdoBackup_YYYYMMDD_<屋敷>_pre.bin — hres,hres,float[] の素の並び
```

⭐ さらに **非冪等の Stage の直前にもう1枚**取る(松江では `_pre6a.bin`)。
こうしておくと「6a **だけ**が動かしたセル」を後から切り出せて、
**区画外の差分が 0 か**を他邸に対して即答できる(EDO-0128 で実際にこれを求められた)。

## ⛔ プレハブの YAML は日本語の名前を `\uXXXX` に**エスケープする** — grep で「無い」と判定しない ★★

**2026-09-04・松江松平邸で実際に誤診した。**書き戻した `.prefab` に据えた物が入っているかを
`grep -c '護岸' Edo_Yashiki_MatsudairaDewa.prefab` で確かめたところ **0 件**。
「石組の護岸 101 石が書き戻されていない」と結論しかけた。⚠ 実際には全部入っていた。

Unity は `m_Name` の非 ASCII を **`m_Name: "護岸_0"`**(= 護岸_0)と書く。
`grep -a` でも `LC_ALL=en_US.UTF-8` でも当たらない — ファイルに日本語のバイトが**一つも無い**。

- ⛔ **日本語名で grep して 0 件でも「無い」ではない。**ASCII 名(`G_NishiNiwa` など)は素で当たるので、
  「ASCII は当たるのに日本語だけ 0」という**非対称**が出たらこれを疑う。
- ⭕ 数えるなら `m_Name:` を全部拾って **`v[1:-1].encode().decode('unicode_escape')`** で戻してから数える。
  44MB・17,777 個の `m_Name` でも python で数秒。
- ⭕ もっと確実なのは、grep でなく **`m_Children` を辿って実際の子の数**を見ること
  (グループの `Transform` の `m_Children` は名前と無関係に必ず ASCII で並ぶ)。

⭐ 一般化: **「据えた物が書き戻ったか」をテキスト検索で判定するときは、まず ASCII 名の物で
検索が効くことを確かめてから**日本語名を探す(検索そのものの感度試験 — 「検査は感度試験とセットで書く」)。

## ⛔ `execute_code` は**完走しても応答がタイムアウトする** — 結果はファイルへ書いて Bash で読む ★★

**2026-09-06・土井の実装第2回。**返す文字列が 3〜4KB 程度でも
`Timeout receiving Unity response` が返り、`get_history` を見ると
**`success: true` / `elapsedMs: 1292` で完走**していた(結果は preview に切られて読めない)。

⭕ **対処**: 長い結果は **scratchpad のファイルへ書き、`return "ok"` だけ返す**。
読むのは `Read`/`Bash`(Unity を経由しないので確実)。

```csharp
System.IO.File.WriteAllText("<scratchpad>/measure1.txt", sb.ToString());
return "ok " + sb.Length;
```

⭐ **長い Stage の完了待ちも同じ手が効く** — Stage が結果ファイルを書くので、
`until [ -f <file> ]; do sleep 5; done` で待てる(⛔ MCP を叩き直して二重実行しない)。
⚠ 既存の「Timeout は失敗ではない」の節と同じ罠の別の顔。**まず痕跡(ファイル)を見る。**

## ⛔ 門番の claim は**セッションID単位** — 同じセッションの別エージェントは調停できない ★★

**2026-09-06・土井。**普請検査(`edo-fushin-qa`)と棟梁(`edo-toryo`)が
**同じセッションID**で並行して起動していた。`edo_session.py` の claim はセッションID単位なので、
`wait --resources unity` は「**空いている(待つ必要なし)**」と返す(自分の claim だから)。
⛔ そのまま C# を触ると、検査役の `execute_code` を再コンパイルで壊す。

⭕ **回避**: `status` の `資源: unity(最終使用 N分前)` を見て、**N が十分大きくなるまで待つ**。

```bash
until out=$(python3 Tools/Session/edo_session.py --session <別ID> status \
      | grep -o "unity(最終使用 [0-9.]*分前"); [ -z "$out" ] || \
      awk -v x="$(echo $out|grep -o '[0-9.]*')" 'BEGIN{exit !(x>=5)}'; do sleep 20; done
```

⭕ **待っている間に手は止めない** — `Assets/` は触らず **scratchpad に写しを作って編集し、
同梱 Roslyn で型検査まで終わらせておく**(この巡は 3ファイルを 0 error にしてから
claim が空いた瞬間に `cp` 1回で入れた)。⇒ Unity を握る時間が最小になる。

## ⛔ 他セッションが同じ Unity を重く使っている間、**dll の mtime を「後から取った基準値」と比べると
永遠に「変化なし」に見える** ★★

**2026-09-07・松江松平の屋根差し替え(EDO-0149)。** `refresh_unity(compile:request)` が
`Timeout` を返した直後に dll の mtime を1回読み、それを「まだ古い基準値」としてポーリングループに
入れたところ、**20分待っても「変化なし」のままだった**。実際にはその基準値を読んだ時点で
**すでに自分の編集を含む新しいコンパイルが完了済み**で、以後 dll は本当に変化していなかった
(比較対象そのものが最新版)。原因は「コンパイル要求 → 応答タイムアウト」の裏で**要求は実際に
処理されており**、基準値を取ったタイミングが**要求後**だったこと。同時に他セッション
(土井の Blender FBX 連続書き出し)が Unity のメインスレッドを 60〜200 秒単位で占有しており、
MCP ブリッジ自体も断続的に無応答になっていた(`No Unity Editor instances found` / `execute_code`
の `ping` すら失敗)ため、「重いから遅い」という誤診をさらに補強してしまった。

⭕ **教訓**:
1. **mtime の基準値は「編集した直後・まだ何もコンパイル要求していない時点」で取る。**
   要求を投げてから基準値を取ると、要求の処理が基準値取得より先に終わっていても検出できない。
2. **`Timeout receiving Unity response` は「失敗」ではなく「わからない」。** ブリッジが無応答でも
   Editor.log(プロジェクト直下 `Logs/Editor.log`)はファイルシステム経由で読めるので、
   MCP が死んでいる間もそちらで `error CS` / `Domain Reload Profiling` の進み具合を確認できる。
3. **他セッションの重い処理と自分の待ちを混同しない。** `ps -Ao %cpu,comm | grep "MacOS/Unity$"`
   が高負荷でも、それが「自分の変更が原因」とは限らない — 共有 Unity では隣のセッションの
   FBX インポート等が主因のことがある。Editor.log の `Untracked: NNNNms`(アセットインポート)や
   複数の `Domain Reload Profiling`(1回 150〜200 秒)が続けば隣が原因と判断してよい。
4. **迷ったら Roslyn 直接コンパイル(本ファイル冒頭「Unity を握らずに C# を型検査する」)で
   現在のディスク上のソースが型検査を通るかを独立に確認する。** dll の mtime や MCP の応答性に
   振り回されず、実際に手を入れたコードが正しいかどうかを即座に切り分けられる
   (今回はこれで「自分の編集は0エラー」と確定してから、dll 側は単に読み違えていただけと判明した)。

### ⛔⛔ 待ちループで心拍を打つのは `claim`/`start` だけ — **`status` では資源の時計が進まない** ★★★
症状: 重い import/コンパイルを `ps` で待つあいだ `edo_session.py status` を回していたのに
unity を取られた(2026-09-07 土井。⚠ 山王を123分待たせた。⚠ 松江松平も同じ形で claim を失効させた)。
原因: 「最終使用」を更新するのは `claim` / `start` のみ。`status` は読み取りで時計を進めない。
既存節「長い待ちのあいだに claim が失効する」は**どのコマンドが心拍か**を書いていないため、
`status` を打って安心する読み方ができる。
対処: 待ちループの中身を **`claim --resources unity`** にする。
⚠ `--note` を付けると呼び出し元の note を上書きするので、返すときに元の文言へ戻す。

### ⭕ 解決済 — 保存時の書き戻しが「解けたままの他邸」を巻き込む件(2026-09-21・EDO-0282②)
**かつての症状。** `EdoYashikiPrefabAutoSave` がシーン保存時に `WriteBackAll()` を呼び、`WriteBackAll` は
「プレハブ資産があるのにインスタンスでないルート」を**無条件に**書き戻していた。
⇒ 解けたまま置かれた邸が、他邸を保存するだけで prefab を上書きされた。
保存1回で **74本・128MB** を書き直し、git 上で実際に変わったのは **1本**(2026-09-21 に実測)。
**直した** — 書くのは「この巡で `EnsureEditable`(= 各ビルダーの `Group()`)を通ったルート」だけ。
⛔ 回避策だった `EdoYashikiPrefabAutoSave.Enabled = false` は**もう要らない**
(off のまま忘れるほうが危ない)。`EdoYashikiPrefab.Convert(new[]{"<自邸>"})` は
`Edo/屋敷/プレハブへ書き戻す(選択中)` として生きている。
⛔ `Edo/屋敷/プレハブへ書き戻す(全部・強制)` は**旧挙動そのもの** — 巻き込むので救出のときだけ。

### ⚠ 書き戻しの台帳は `SessionState` — **Unity を再起動すると「触った」記録が消える** ★★
2026-09-21 以降、書き戻しの対象は `SessionState`(エディタ起動中だけ生存)に控えた
「この巡で触ったルート」。鍵は `scene.path + "\t" + ルート名` の組。
⚠ **エディタを落とすと消える。** 解けたまま置いて再起動すると、保存しても誰も書き戻してくれない。
⭕ 網は3枚 — ①保存時の ⚠(名指し) ②`sceneOpened` の検査(シーンを開いた瞬間に名指しで ⚠)
③`Edo/屋敷/切り出し状況を検査` の「解けたまま」列。
⭕ 拾うのは `Edo/屋敷/プレハブへ書き戻す(選択中)`。

### ⚠ 解けたまま離席すると、**以後だれも書き戻してくれない** ★★
以前は上の「無条件に書き戻す」処理が偶然この穴を塞いでいた。いまは塞がない。
⭐ **中身はシーンが持っている** — `Akasaka.unity` の中には在る(シーンが太るだけ)。
消えるのは「書き戻さずに `Revert All`」「保存せずシーンを閉じる/入れ替える」ときだけ。
⛔ 例外は**作業場**。`Koba.unity` は gitignore なので中身が残らず、`EdoKoba.Open` の掃除は
`DestroyImmediate` で無条件に消す — **本当に失われる**。
だから書き戻していない屋敷が載っていると `Open` は**門を閉じて消さない**(`EdoKoba.cs:110`)。

### ⛔⛔ 隅の継ぎ目を「駒を伸ばして詰める」処理は、上限を緩めるほど run の終端が指図からずれる ★★★

**2026-09-08・松江松平・普請検査差し戻し。** `CloseKadoSeams`(隅と隣の駒の隙間を、駒を走り方向へ
伸ばして詰める処理)の上限が `Mathf.Max(0.60f, len*0.35f)`(駒 pitch≈2.98m なら実質 1.04m まで無条件に
許容)になっていた。これが**隅部材(`Dobei_Kado_88M` など)の腕の実寸不足**(指図は腕≈4.10〜4.15m を
前提にしていたが、実測すると腕は 3.27m しかなかった)を丸ごと隠し、`run` の物理的な端を
**指図の `s0`/`s1` から 0.81〜0.84m ずらして**しまっていた(`RunEndQA` は指図値と実測値を比べるので、
このズレをそのまま「終端が違う」と報告する)。加えて `CloseKadoSeams` は**表(`_?f`)だけを伸ばし、
裏(`_?b`)を置き去りにする**バグも併発しており(表裏が走り方向に最大 2m 食い違っていた)、
壁の厚み方向に裂け目ができていた。
⭕ **切り分け方**: `DobeiRun`/`ItabeiRun` は `pitch = len/n` で `[s0,s1]` を**過不足なく割り切る**ので
駒数の丸めでは終端はずれない。`AlignInubashiri` は法線方向(犬走りの厚み)にしか駒を動かさないので
走り方向の終端もずれない。**終端がずれるなら疑うのは `CloseKadoSeams`(または同種の「伸ばして詰める」
後処理)一択** — 疑わしい処理を一時的にコメントアウトして Stage を再実行し、素の(伸縮前の)終端が
指図の `s0`/`s1` と一致するかを先に確認する(一致すれば後処理側の犯人確定)。
⭕ **直し方**: 上限を「駒ごとの継ぎ目として現実にあり得る小さな誤差」(実測ベースで 0.20m 程度)に
絞り、それを超える隙間は**伸ばさず報告する**(部材の腕の実寸不足は run 側の対症療法では直らない —
部材方が腕を作り直すか、指図側が `s0`/`s1` を実寸へ合わせ直すかの二択)。あわせて、表(`_?f`)を
伸ばす/動かすときは**同じ駒番号の裏(`_?b`)にも同じ scale 係数・同じ平行移動を適用する**(表裏の対応は
`"...Nf"` → `"...Nb"` の名前置換で引ける)。
⚠ **教訓**: 「隙間を詰める」後処理の上限を緩めると、症状(隙間)は消えても**別の実測値(終端位置)が
指図からずれる**形で欠陥が移動するだけになる。上限は「小さな誤差の吸収」用と割り切り、上限を超える
実測は必ず報告に残す(隠さない)。

### ⛔ 石垣QA(`IshigakiQA`)が「run ごとに一直線」を隅の腕(joints[].kado.seat)を含めて判定すると、
**指図が明示的に許容している段を誤検出する** ★★

**2026-09-08・松江松平・普請検査差し戻し。** 石垣基壇は run 本体の `s0`〜`s1` の外側に、隅の留め継ぎの
「腕」ぶんの区間を追加で敷く(`Stage3_Ishigaki` の `armEnd`/`armStart`)。腕の天端は
`joints[].kado.seat` という**run 本体の `seat` とは別の設計値**で、複数の joints の注記
(【申し送り】)が「腕の端に 0.10〜1.12m の段が残る」と明示的に認めている——つまり**意図的な段**。
ところが `IshigakiQA` は石垣の駒を**同じ `r.name` プレフィックス**でバケツに入れて「run ごとに
一直線か」を判定していたため、腕区間と run 本体が同じバケツに混ざり、この意図的な段を
「run 内でばらついている」と誤検出していた(実測: `S_Hei_E1` 0.100m / `S_Hei_W0b` 0.310m /
`NE_Nagaya_1` 0.300m / `S_Hei_Doi_S1b` 1.120m — いずれも `run.seat` と隅の `kado.seat` の差に
**ちょうど一致**)。
⭕ **直し方**: 腕区間の石垣駒には run 本体と別の名前(`r.name + "_arm"`)を与え、QA のバケツ分けを
自然に分離する(QA 側のロジックは変えず、**命名だけ**で「run ごとに一直線」の対象集合を正しく絞る)。
⭕ **教訓**: 「run ごとに一直線」のような一直線チェックを書くときは、**その run に意図的に別の設計値
(隅の座・門の座など)を持つ区間が混入していないか**を先に確認する。混入があれば、チェックの条件式を
複雑にするのではなく、**そもそも別バケツに分ける**(命名で分離する)ほうが後々の可読性・保守性が高い。

### ⚠ 御殿の屋根は**部材の系列によって「軒高」の基準点が違う** — 帯割り(z=0=床)と入母屋(z=0=軒先)を
数値だけ揃えても、同じ「軒下端」を指すとは限らない ★★

**2026-09-08・松江松平・普請検査差し戻し(附属屋の軒高逆転)。** 附属屋4棟(御湯殿・長局北・
奥台所・厩)は帯割り屋根が作れない(`munes[].roof` が無い)ため入母屋(`RoofIrimoya_`)のまま
残していたが、`EdoGotenKit.Mune` の入母屋プレースメントは `floor + H − 0.15`(H=建具高
2.727。旧 `muneEave` の名残)という**指図の軒高 const と無関係な固定式**で軒を据えていた。
これを `const.umayaEave`(2.35)/`nagayaGataEave`(2.80)を直接ローカル Y として渡す形に直すと
(`Mune` に `roofEaveLocalY` を追加)、**厩 < 御殿(帯割り)** の序列は実測で正しくなったが、
**長屋類(2.80) の軒下端が、帯割り屋根の実際の外周タイル最下端より高いまま**残った。
原因を遡ると: 帯割り屋根の生成スクリプト(`build_goten_roof.py`)の `eave` パラメタは
「身舎の軒桁(=壁面の直上)の高さ・床面基準」であって、**タイルの外周(入側1間+軒の出0.9m ぶん
勾配なりに下がった先)の見た目の最下端ではない**(実測: `eave=3.4` に対し、外周タイルの実際の
最下端は床から 1.91m — 差 1.49m ≈ `(入側1間+軒の出0.9m)×瓦勾配 0.5456`)。一方、入母屋 FBX の
`z=0` は(このスキルの他の節にある通り)**軒先そのもの**(外周タイル最下端に近い点)。
⇒ **`gotenEave` と `umayaEave`/`nagayaGataEave` は、同じ「軒高」という語を使っていても、
図面上の異なる基準線(軒桁 vs 軒先)を指している可能性がある**。指図の `_gotenEave` 注記が
別途「軒先 = `gotenEave` − 1間×`ken`×`kawaraKobai`」という**より軒先に近い従属値**を定義している
ことも、この2つが同一基準ではないことの傍証。
⭕ **教訓**: 「軒高」を並べて序列比較するときは、**どの基準点(軒桁/軒先/タイル最外周端)を測っているか**
を先に統一する。帯割りアセットは生成スクリプトのソースを読めば基準点が確定するが、
レガシーな入母屋/寄棟キットの FBX は「z=0 が何を指すか」がコメント以外に検証手段が無く、
**実測(メッシュの最下点)でしか確認できない**。この食い違いは棟梁の実装だけでは埋め切れない
(部材方が入母屋キットの軒の出をどう作ったかを開示するか、指図方が「どちらの基準で比較するか」を
決める必要がある)。

### ⭕ 上の続き: **系列ごとの定数オフセットを諦め、Put 後に実メッシュを測って寄せ直す**で解決した ★★

**2026-09-08・松江松平(上の差し戻しへの対応)。** 系列ごとに `z=0` の意味が違う(帯割り=軒桁付近・
入母屋=タイル最下端に近いが厳密には一致しない)なら、系列ごとの補正定数を決め打ちするのは
CLAUDE.md 規則5 違反になる。⭕ **`EdoGotenKit.Mune` で roofAsset を `Put` した直後に
`MeshFilter.sharedMesh.bounds.min.y`(ピボット→軒下端の実測)を取り、目標
`(floor − NUREEN_DROP) + 指図の軒高` に軒下端がちょうど来るよう `localPosition.y` を
**測ってから**上書きする**形にすると、`roofAtFloor` の true/false を問わず同じ式で系列差を吸収できた
(実測: 厩 2.350 / 長屋類 2.800 / 御殿(帯割り)3.400 — 目標とのずれ 0.000m)。
⚠ **`NUREEN_DROP`(=0.28。濡縁は畳床より 0.28 下がる、という既存の定数)が「軒下端(床上)」の
基準線だった** — 普請奉行の実測「床=27.340」は畳面(floor, world 27.620)ではなく、外から見える
唯一の床の縁である**濡縁面**(floor−0.28)を指していた(mm 単位で一致)。指図の「床上」という語が
どの床を指すか(畳面 or 濡縁面)は、複数の実測基準点の候補があるときは**既存の命名済み定数と
数値が一致するか**を先に疑うと当てられる。
⭕ **教訓**: 「部材の系列によって基準点が違う」と分かったら、**その基準点の差分を推定して定数で
埋めない**(系列が増えるたびに定数が増える)。**据えた後に実メッシュの該当点(この場合は
`bounds.min.y`)を測り、目標値との差だけ動かす**という一段構えにすれば、系列の数だけ生えるはずの
特別扱いが要らなくなる。

## ⛔⛔ `Terrain.SampleHeight` は**世界の Y ではない** — 地形オブジェクトの原点からの高さ ★★★

**2026-09-08・山王社の作り直しの着手前の地形確認。** 指図が「山頂平坦面 h 27.5〜31.6 /
境内の面 28.30」と宣言しているのに、`Terrain.activeTerrain.SampleHeight(new Vector3(-484,0,847))`
は **37.41** を返した。⚠ **「地形が約10m 高い＝地形が壊れている / 指図の Z 較正が地形に効いていない」
と読みかけた。**

**原因**: `SampleHeight` が返すのは**地形オブジェクトのローカル原点からの高さ**で、世界 Y ではない。
当シーンの Terrain は `transform.position.y = -9.94` に置いてあるので、
**世界 Y = SampleHeight + terrain.transform.position.y** = 37.41 − 9.94 = **27.47** ＝ 指図の 27.5 と一致。

⛔ **この誤読は山王では特に危ない** — 山王の実装のドリフトは**実際に 10.0 m**(Z 較正 857→847 に
実装が追随していない)で、`SampleHeight` の 9.94 m と紛れる。「10m ずれている」という同じ言い方で
**別の原因**が2つ並ぶので、片方をもう片方の証拠に使ってしまう。

⭕ **作法**:
1. **地形の高さは `EdoBuild.Ground(x, z)` で採る**(`position.y` を足し込んだ世界 Y を返す)。
   ⛔ `SampleHeight` を生で使わない。
2. ハイトマップを直に読むときも同じ — `H[z,x] * terrainData.size.y + terrain.transform.position.y`。
   `* size.y` だけで止めると同じ 9.94m の穴に落ちる。
3. **確かめ方**: 指図が宣言している自然地盤の帯(山王なら `terrainCheck.plateau.h`)と
   突き合わせて、**一致しなければまず自分の採り方を疑う**。地形の作り直しは 2026-08-22 に
   済んでおり、地形の側が10m 単位でずれていることは考えにくい。

## ⛔ 待ちの見張りを重ねて仕掛けない — 1 本だけにし、仕掛け直す前に古いのを止める ★★

2026-09-08 の松江松平では 6 本たまり、ユーザーが片付けようとして
**生成器の本体まで一緒に止めた**(45 分の計算が消えた)。

**すべきこと。**

- 見張りの間隔は**待つ物の長さに合わせる**(60〜80 分の生成器を 45 秒おきに覗く意味は無い。10 分で足りる)。
- ⭐ **本体と見張りは名前で見分けられるようにする**。一覧に並んだとき、どれを止めてよいか
  ユーザーが判断できることまでが仕事。

## ⛔⛔ `Edo/御殿/…マテリアルをremap` は 1 時間かかり、**MCP のタイムアウト再送で何重にも走る** ★★★

**症状。** `execute_menu_item` で remap を叩くと MCP が `Timeout receiving Unity response` を返す。
実際には走っているが、**MCP 側が再送するので同じ remap が何本も積まれる**。
2026-09-09 の松江松平では 1 回のつもりが **7 回**走り、Unity が 1 時間近く 90〜100% CPU で
埋まって**他のすべての MCP 呼び出しが通らなくなった**(Stage5 以降が丸ごと待たされた)。

**原因。** `RemapGotenMaterials` は `SearchAndRemapMaterials(..., ModelImporterMaterialSearch.Everywhere)`
を **83 本の FBX 一つずつ**に掛け、そのたびに `ImportAsset(ForceUpdate)` する。
`Everywhere` はプロジェクト全体(6.9GB)を舐めるので 1 本あたり 5〜20 秒の
`Asset Pipeline Refresh` が走る。⚠ この `Everywhere` の危険は
`EdoMatsudairaDewaBuilder.RemapFuzokuya` の注記が既に警告していたが、御殿側は直っていない。

**すべきこと。**
- remap を叩いたら**その1本が終わるまで MCP を一切叩かない**。進捗は
  `Logs/Editor.log` の `[GotenKit] マテリアル remap:` の**行数の増分**で数える(⛔ `read_console` を叩かない
  — 叩くこと自体が再送のきっかけになる)。
- 新しい FBX を 1〜4 本足しただけなら、**全部を舐める必要はない**。
  ⇒ 部材方/棟梁への申し送り: 対象パスを引数で絞れる remap に直す。

## ⛔⛔ 「指図と実装を突き合わせる」を走らせると**プレハブが解ける** — 書き戻しは検査の**後** ★★★

**症状。** Stage を流し終えて `EdoYashikiPrefab.Convert(...)` で書き戻し、そのあと仕上げに
`Edo/<屋敷>/指図と実装を突き合わせる` を押すと、**屋敷がプレハブ実体でなくなる**。
気づかずに終えると、シーンには解けたままの 17,000 個の Transform が残り、
次に誰かが `Edo/屋敷/プレハブへ書き戻す(全部・強制)` を押したときに巻き込まれる
(⭕ 2026-09-21 以降、既定の「触った分だけ」と保存時の自動書き戻しは巻き込まない —
名指しで ⚠ が出るだけ。ただし**自邸も書き戻されない**ので、結局ここで解けたことに気づく必要がある)。

**原因。** `Compare()` は `CheckScene`(読み取りのみ)のほかに `InubashiriQA` / `RunEndQA` を呼び、
どちらも `Group("Kakoi")` / `Group("Ishigaki")` を使う。ビルダーの `Group()` は先頭で
`EdoYashikiPrefab.EnsureEditable(root)` を呼ぶので、**読むだけのつもりの検査が解いてしまう**。

**すべきこと。** 手順の最後を **「検査 → 書き戻し → 保存」** の順にする(⛔ 書き戻してから検査しない)。
書き戻したあとに確かめたいときは、`Group()` を通らない読み取り
(`EdoSashizuExport.CheckScene(id)` を `execute_code` で直に呼ぶ / `GameObject.Find` + `Find`)だけにする。
⭐ 終わりに `PrefabUtility.IsAnyPrefabInstanceRoot(root)` と `scene.isDirty` を必ず確かめる。
