# 指図(設計図)の起こし方

**Unity で建てる前に指図を起こし、ユーザーのレビューを受ける。** ユーザー指示(2026-08-14):
「今後も屋敷を作成する時に設計図を作成してから実装するという流れにしていきたい」。

これを飛ばして直接建て、2度全面差し戻された(v1=散在パビリオン / v2=表門軸に合わせて敷地が空地だらけ)。
図面なら数分で直せるものを、Unity で建ててから直すと数時間かかる。

置き場所は**プロジェクトの `docs/Sashizu/`**。屋敷ごとに1ファイル、`README.md` に索引を持つ。
Artifact として publish もして URL を索引に載せる(ユーザーがブラウザで見るため)。

## §0. 指図は**現況だけ**を載せる ★★

**回を重ねると必ず腐る。** 岡部邸の指図は 其一〜其十六 を時系列で積み増した結果、
撤回済みの記述と現行値が同居し「何が正か分からない」とユーザーに指摘された(2026-08-20)。
一枚に 20 箇所の「撤回」「誤り」が残り、最新の 其十五・十七 は指図に無くコードの注釈にしかなかった。

**直し方は三つ。**

1. **過去を本文に残さない。** 「以前は〜だったが」「〜は撤回する」は書かない。
   経緯は**コミットメッセージと `git log docs/Sashizu/`** で追う。図は今の姿だけを語る。
   *(コードの注釈に「なぜこうなったか」を残すのは別の話。あれは再発防止で、指図は現況の記述)*
2. **数値を二重に持たない。** 設計値は `<屋敷>.json` にだけ置き、HTML も文章も**そこから組む**。
   表に書き写した瞬間に二重管理が始まり、片方だけ直る。
3. **順序を守る。**

```
設計(json/md を書く) → 組む → 検図(edo-kosho / edo-kenzu) → ユーザーのレビュー
      → 実装 → **指図を更新** → 突き合わせて 0 件 → コミット
```

⚠ **実装から指図を生成してはならない。** 楽だが、それをやると指図は実装の写しに落ちて
「先に図を描いてレビューを受ける」関門が消える(2026-08-20 に一度その設計へ走ってユーザーに止められた)。
道具が担ってよいのは**突き合わせ**だけ — 「書いた指図と建った物がズレていないか」を数えるところ。

建ててみて指図のほうが誤りだと分かることはある。そのときも**指図を直してから**実装を合わせる。
先に実装だけ直すと、また指図が古びる。

**実装例(岡部邸)**
| 物 | 役 |
|---|---|
| `docs/Sashizu/okabe_sashizu.json` | 設計値の正典。人が書く |
| `docs/Sashizu/okabe_kosho.md` | 文章の部(典拠・決めごと・未解決)。現況形 |
| `Tools/Sashizu/build_sashizu.py <屋敷>` | 上の二つから HTML を組む(全邸共通・1 本)。**実装は読まない** |
| `Edo ▸ 岡部筑前守上屋敷 ▸ 指図と実装を突き合わせる` | 指図と実装を項目ごとに比べ、差分を出す |

## §1. なぜそうなるのか — 建物・廊下・庭は「一つの架構と、その周りに残る面」

**個別の規則を覚えるのではなく、この一文から導く。** 岡部邸で規則だけを書いて
「岡部のレイアウトに特化していて、なぜそうすべきか分かっていないのでは」と指摘された(2026-08-14)。

| | 何であるか | だから何が導かれるか |
|---|---|---|
| **棟** | 架構(屋根と柱割り)の単位 | 部屋は棟の中を**建具で割ったもの**。別々の矩形に離すと別の建物になる(§1b) |
| **入側・縁側** | 架構の**縁**(寝殿造の庇 → 書院造の広縁・入側) | 廊下は棟に**属する**。幅は通行量でなく**柱間(一間)**で決まるので、どこでも一定。棟を並べても足し算されない |
| **外廊下** | 郭の縁を走る入側の**呼び名** | 別部材ではない。隣に重ねたら同じものを二度描いたことになる |
| **渡廊下** | 架構の**外に出る**独立構造物 | 屋根・床・柱を新造するので必要最小限。同じ二棟の間に平行して二本引かない |
| **庭** | 建屋と囲いの**間に残る面** | 独立した矩形として置かない(余りが出る)。**見る場所(入側)とセット**で初めて庭になり、視点のない庭は空地 |
| **土蔵** | **延焼を切る**ための独立建物 | 廊下で繋いだら火が回る。だから入側も渡廊下も付かない |
| **御錠口** | 表と奥を分ける**結界** | 境界は面として閉じていないと意味がない。開口が二つあれば錠は無効 |
| **段差** | 郭の**境界**で起きる現象 | 境界=縁で処理する。中央で起こすと郭が二つに割れる。解消には水平距離が要り、壁の厚みでは足りない |

**入側** = 書院造で濡縁と座敷の間の一間幅の通路(畳を敷けば縁座敷)。起源は寝殿造の庇+簀子縁。
**中廊下型(建物の中央を廊下が貫く)は明治以降の型**。

⚠⚠ **四周に回るかは確度U(2026-08-14 ユーザー裁定)。⛔ 典拠として書かない。**
2026-09-06 まで、この段は「**典拠:**」の見出しの下で **[ID] 無しの断定形**で「客座敷の外側を**取り囲むように**
配された」「二条城…**六棟を取り囲む廊下が一周**する」と書いていた。⛔ `buildings.md` は同じ主張を自ら
「**確度U — 一般知識で、このスキルに典拠を登録していない**」と断っており、**同じ事実に二つの確度**が
付いていた(2026-09-06 考証方・土井が2巡続けて指摘)。

⛔⛔ **反証側のほうが厚い。**台帳にある御殿の確度A 3件は、いずれも**部分的な入側**を示す:
- [高知城懐徳館]A「…納戸、三畳二室、雪隠、**入側**、板間及び縁側より成る」
- [掛川城御殿]A「二ノ間**及び入側**」「三畳**及び入側**」
- [西川1959]A 原文は「書院が上段、二之間、三之間と**片側に入側をもつて一列にならび**」

⇒ **四周に回ることを示す記載は、A 典拠3件のどれからも取れない。**⛔ 二条城の「廊下が一周する」は
**指定書に無い**(国宝指定書の構造及び形式に廊下の記載自体が無い)。⭕ 各邸の四周入側は**ユーザー裁定
として据え置いてよい**が、⛔ **典拠のある型として書かない**。→ `sources.md` [二条城二の丸御殿]A

### そこから出る作図の帰結

- **格子状の通路で敷地を割らない。** 廊下は室群の外周を巡る(九区画割りを描いて差し戻された)。
- **廊下は幅一間(約2m)で一定。** 身舎のまわりに ring を回し、離れた棟へ link を渡す。
  棟の外形どうしを密着させて繋ごうとすると両側の入側が足されて4〜8mになる。
  逆に隙間を空けると別系統に見える。**接するが重ならない**が正解。
- **外廊下は棟の入側と「同じ帯」に載せる。** 隣に別帯を足さない(西縁・北縁で二度やった)。
- **棟と棟をつなぐ廊下は一本。** 外廊下があるのに中央にもう一本引かない。
  ただし棟群を**一周する環**は別(二条城がそうなっている)。
- **土蔵・物置には入側も廊下も付かない。**
- **奥へ入る廊下は御錠口の一本だけ。** 台所から奥へ直結させない。
- **庭は座敷の正面に置き、入側から望む。** 隣り合う庭を分ける理由(建屋・廊下)が無ければ**一枚**にする。
  郭の外に庭園帯があるなら郭の中に庭を重ねない(廊下を挟んで庭が二重になる)。
  庭の形は囲いと建屋を決めれば決まる — **庭から先に矩形で描かない**。
  (四棟で囲んだ中央が坪庭になるのは帰結の一例であって、規則ではない)
- **段をつなぐ石段は郭の端に外廊下として回す。** 中央を突っ切らせない。

## §1b. 棟 →(襖)→ 続き間 — 階層を取り違えない

**続き間を別棟のように離して描いてはならない**(2026-08-14 に一度やって指摘された)。

- **二条城二の丸御殿の大広間は「1棟」** — 式台の西に接して建つ南北棟の建物で、
  **一の間(上段の間)・二の間(下段の間)・三の間・四の間(鑓の間)・帳台の間**からなる。
  仕切りは**襖と帳台構**であって廊下でも壁でもない。一の間48畳・二の間44畳。
  格式は天井で示す(一の間=二重折上格天井、二の間=折上格天井)。
- **二の丸御殿全体は6棟** — 遠侍・式台・大広間・蘇鉄の間・黒書院・白書院。
  接続あるいは渡廊下で結ばれて雁行する。

→ 作図の階層は **棟 →(襖)→ 続き間**:
  1. **棟** = 1つの外形。その外周に入側が回る(外形と身舎の間の縁として描く)
  2. **身舎** = 棟の内側の1枚のブロック
  3. **続き間** = 身舎を**襖線(細い破線)**で割ったもの。室名と畳数はここに書く
  4. 棟と棟は**接続**(直に触れる)か**渡廊下**

「大広間・二之間・三之間」は1棟の中の続き間。別々の矩形として隙間を空けて描くと、
Unity 実装でも別棟になり、福井図・二条城のような一体の御殿にならない。

## §1f. 段差は水平距離を先に確保する

石垣の開口(厚み2.4m)の中では降りられない。蹴上0.30mで、

| 落差 | 段数 | 直線の水平距離(踏面0.45) | 折返しにすると |
|---|---|---|---|
| 6.0m (六尺) | 20段 | 9.0m | **5.0m** |
| 8.0m (八尺) | 27段 | 12.1m | **6.5m** |

→ **断面で段数と距離を出してから平面に戻す。** 平面だけで石段を描くと、
必ず「壁の厚みの中で降りている」不可能な図になる(2026-08-14 に描いて自分で気づいた)。

## §2. 室の粒度 — 御殿は小室のマット

福井藩上屋敷の原図は**数百の小室が壁を共有して連なる一枚のマット**。
Village Kit の 18〜26m 級の建屋を並べる作りとは**粒度が二桁違う**。

Unity 側の現実解(案a):
- 棟を躯体間 0.6m で詰め、軒を重ねて**屋根が一枚に繋がる塊**にする。等間隔の格子に置かない
- マットを**外周長屋の内面まで寄せる**(犬走りに芝を残さない)
- 郭の内側は**白洲(砂利)スプラット**。芝のままだと村に見える
- 棟通りをゾーンごとに揃え、反復で大屋敷に見せる

図面は室単位で描き、Unity 実装では室群を1棟に丸める — **図面の方を実装に合わせて粗くしない**。

## §3. 図面に入れるもの

1. **敷地全体 配置図** — 区画・段(平場)の高さ・石垣・外周長屋/塀・門・庭園
2. **現況図(造成前の地形)** — §3a。**造成のある屋敷では必須**
3. **切盛図** — §3b。同上
4. **主郭 御殿平面** — 室群・室名・入側・渡廊下・庭
5. **副郭の平面** — 段が分かれる屋敷では郭ごとに
6. **断面** — §3c。段差のある屋敷では必須。段のつなぎ方は平面だけでは読めない
7. **動線図** — §3d。門を入ってからどう動く想定かを図と表で示す
8. **格式の判断と典拠** — 御成セットの有無、門の格式、推定で埋めた箇所の明示(§A-3)

## §3a. 現況図 — **造成のすべての出発点を図にする** ★★

ユーザーの要求(2026-08-23)。**面の高さを決める前に、いまの土地の姿を図にして固定する。**

### ★★ 面の高さは設計者が決めない。**地形を測って、自然の平場の高さをそのまま採る**

ユーザー指示(2026-08-23):「盛り土、切土は大事なのですが、**現在の地形をベースにまずは考えるべき**です」
「窪みのところも切土、盛り土で形を変えるのではなく、**その窪みを活かした配置**にしてください」。

やってはいけないのは**面の高さを先に決めて、地形をそれに合わせて削り盛りする**こと。
土井邸ではこれで玄関棟を平均1.65mの盛土に載せ、自然の窪みを埋めて平らにしていた(二度是正された)。

**正しい順序**:
1. 回転間グリッドで自然地形を 0.5間刻みに測る(**測る先は下の「地形は正本から採る」の正本**。
   ⛔ Unity の live terrain ではない)
2. **矩形を総当たりで走査し、(位置, 起伏) の小さい組を探す** — 面の高さは
   その矩形の `(max+min)/2` を丸めた値。**探索が面の高さを教えてくれる**
3. 見つかったベンチに棟を割り当てる。棟が入らないベンチは面にしない
4. 段の数はベンチの数で決まる。「4面にしよう」と先に決めない

```python
# 位置と高さを同時に探す(scratchpad で走らせる)
def fit(u0,v0,u1,v1):          # 区画内のみ。外を含めば None
    ys=[nat(u,v) for u,v in grid(u0,v0,u1,v1)]
    return round((max(ys)+min(ys))/2, 1), max(ys)-min(ys)   # (面の高さ, 起伏)
# 起伏の小さい順に並べ、棟の大きさで走査する
```

⚠ **`(max+min)/2` は外れ値に弱い。起伏の小さい矩形を選んだ後にしか使えない。**
広い区域にそのまま当てると、隅が一つ低いだけで面が下がる — 松江松平で主平面の西
(u−72..−16)に当てたら、隅の近代掘削跡(20.1m)に引きずられて **23.8m** という
無意味な値が出た(その高さでは 100% が不合格)。同じ区域の**中央値は 26.8m で不合格 10%**。
**判定は中央値と併記する。** 手順としては
「走査で起伏の小さい矩形を絞る → その矩形に `(max+min)/2`」の順を守り、
区域全体の代表値が要るときは中央値を使う。

**合格の目安**: 棟が載る所で **|設計面 − 自然地形| ≤ 0.5m**。
土井邸は全7棟が ±0.44m に収まり、盛土は 4,584→3,031m³ に落ちた。
松江松平は改定前(表門の敷居や「石段6段」から面を決めていた)が
表郭 75% / 東上段 48% / 奥郭 49% 不合格で、走査で引き直して**全棟 7.0%**まで落ちた。
**窪みは埋めずに一段低い郭として使い、棟どうしは階段廊下でつなぐ。**

⚠ **「面にできるか」は高さだけでなく区画の形で決まる。** 松江松平の北東には
28.8m の平場が実在したが、区画の北東辺が斜めなので**蔵が入る 22×8間の矩形が
区画内に一つも取れなかった** → §B-1 の「棟が入らないベンチは面にしない」に従って
面から落とし、蔵を主平面へ降ろした。**走査は必ず区画でクリップして回す**
(区画外を1セルでも含む矩形は候補から外す)。

### ★★ 地形は**正本から採る**。Unity の live terrain から採らない

⛔ **`Terrain.SampleHeight` で「造成前の地形」を採ってはいけない。** live terrain は
**自分と他家の造成が乗った作業面**で、**採った時刻によって値が変わる。**

2026-08-24 に edo-unity で発覚した事故: 4邸(岡部・土井・松平・山王)が同じやり方で
live から「造成前の現地形」を吐いていたが、**松平が朝 08:54 に造成を流した5時間後に
岡部・土井が採った**ため、両家の DEM が松平の造成を「自然地形」として取り込んだ。
土井の DEM は松平区画内セルの **68%(3,438/5,061)が正確に 27.0 = 松平の主平面の設計値**、
近代掘削跡は **6.9m 埋まった状態**で固定されていた。
**どのセッションもやり方は同じで、違ったのは採った時刻だけ** — 個人の落ち度では防げない。

**正しい採り方**(edo-unity では `docs/Sashizu/base_dem.json` が正本):

1. **造成を一切含まない参照面を1枚だけ持つ。** 出自は実世界の DEM(edo-unity では
   国土地理院 DEM5A/10B からジオリファレンスを合わせた参照ハイトマップ)。**確度P**
2. 各屋敷の `<屋敷>_dem.json`(`{x0,z0,step,nx,nz,h[[…]]}`・世界座標2m刻み)は
   **その正本からの切り出し**として生成器が書く。**手で編集しない・Unity から採り直さない**
3. **区画(`parcels.json`)を動かしたら生成器を回す。** 担当区画が切り出しの外へ出ていたら
   止めて、使うべき範囲を数値で出す — でないと**欠測と「造成しない」が図の上で区別できない**
4. 生成器は**冪等**にする。再実行で1セルも動かないことを毎回確かめる

⚠ **正本は「現代の地面」であって江戸の地面ではない。** 近代造成(校庭の盛土・ビルの掘削跡)を
含む。江戸期の地盤が要るなら**正本からの復元レイヤ**を別に持ち、**自分の区画でクリップする**
(区画外へ滲むと隣家の設計を勝手に持ち上げる。岡部で実際に33セル漏れた)。
⚠ **隣家と接する屋敷は、境の地盤を必ず同じ面から読む。** 片方が live・片方が参照だと、
同じ境界線の地盤を最大3m違う値で読み、埋没検査が両家で食い違う。

- 上のようにして得た `<屋敷>_dem.json` を指図の隣に置く。**確度P**
- **段彩(2m ごとの色帯)+ 等高線(2m、10m を太線で数値入り)** で描く。
  段彩の色は地図の記号なので**明暗テーマに関わらず固定**にする(紙の地形図と同じ読み方をさせる)
- **隣の屋敷の区画も色を変えて重ねる** — 境の地形は隣と一続きなので、自分の区画だけ描くと
  尾根と谷がどこから来ているのか読めない
- 表門・断面の切り位置・世界座標の目盛・スケールバー・方位を入れる
- 切盛図(§3b)はこの地形と設計の差なので、**現況図と切盛図は対で読ませる**

## §3b. 切盛図 — **どこを盛り、どこを切るかを図で示す** ★★

ユーザーの是正(2026-08-23、松江松平と土井で二度)。**面の高さの表だけでは造成が読めない。**
「1〜4mに収まる」と文章で書いても、それがどこなのかは図でしか伝わらない。

- **造成前の現地形を固定する。** 回転間グリッドの格子(1間刻み)で
  `<屋敷>_terrain.json`(`{grid,u0,v0,step,nu,nv,h[[…]]}`、区画外は null)を書き、
  指図の隣に置く。**確度P**。生成器はこれを読む — 実装を読むのではない。
  ⛔ **種地は §3a の正本**(`base_dem.json` の双一次)。**Unity の live terrain から採らない**
- **Δ = 造成後の地盤 − 造成前の地形**をセル塗りにする。
  **暖色=盛土 / 寒色=切土 / 無彩=±0.3m以内(実質さわらない) / 地の色=造成しない**。
  段は 0.3/1/2/3m で色を濃くする
- **段ごとの土量表**(面積・盛土量 m³・最大盛土・切土量・最大切土)と**総量の差引**を添える。
  差引が正なら土が足りない(客土が要る)
- **法面も土量に含める** — §3b の法面規則で段の外へこぼれる分は本物の土工

**法面(バッター)の規則**: 段の縁のうち**土留めの無い辺**は、法面で現地形へ摺り付ける。
盛土 1:1.5 / 切土 1:1 を既定とし `const.batterFill` / `const.batterCut` に持つ。
**段の縁に垂直の段差を残さない** — 残っていたら、そこは土留めを置くか法面で均すかの
どちらかが抜けている(2026-08-23 に断面で発見された)。土留めのある辺からは法面を出さない。

⚠ **法面には三つの関門が要る。**(2026-08-23 松江松平で実装して初めて出た。図だけでは見えない)

1. **縁そのものが盛土になっていること。** 地山と同高の縁には支える土手が無いので法面も要らない。
   これを落とすと、**「縁は地山と同高だが外は崖」という所に土手が生える**
2. **縁から `const.featherCap`(既定 12m)以内。** それ以上は土手でなく崖・石垣の領分
3. **その勾配を cap まで延ばして現地形に着地すること。** 崖が法面より急だと永久に着地しない

(1)(2)(3) が無いと、1:1.5 より急な斜面で法面が宙に伸び続ける。松江松平の西斜面
(溜池東岸)で**最大 9m の土手**ができ、切盛量が 4,443m³ 過大に出た。
逆に一律の幅で摺り付けるのも駄目で、段差の小さい縁では要らぬ土をいじり、
大きい縁では崖が残る(同日ユーザー指摘:「盛り土と無造成部分との境目は均さないと変な段差が残る」)。
**勾配で決めて、上の三条件で打ち切る。**

⛔ **2026-09-19 山王で (2)(3) は撤回された(ユーザー裁定=案A)。** 三条件は**法面を「縁の一点ごとに
外へ降ろす一本の ray」で作る**ことを前提にしており、その前提が間違っていた。ray は土留めのある向きを
**丸ごと消す**ので、消えた向きと消えなかった向きの境に**段が立つ** ── 土の面は横へは消えない。
山王では法尻に段が 56 枡・11 条・最大 0.83m 残り、cap を 12→40m へ広げても**段は増える**だけだった
(448→521 枡)。⭕ 代わりに**距離場の「広がる一枚の土の面」**を使う:

```
設計面 = min( max(現地形, 面の高さ − 距離/batterFill), 面の高さ + 距離/batterCut )
```

距離は**土留めを障害物とした測地距離**、盛の円錐は**縁の盛厚が正の区間からだけ**出し
(= 条件 (1) は生きている)、**現地形に沈んだ所で止める**(= (3) は打ち切りでなく自然な終端になる)。
走査幅は cap でなく**円錐の届きの実測**から出す。山王では超過の段が **0 枡**になり、
社地の外へも出ず、増えた土は 288m³(敷地全体の土工の 6%)だった。

⚠ **段を「隣の枡との落差」で数えない。** 格子 1m に対し 1:1.5 の法は 0.667m/枡 落ちるので、
**法そのものが段に数えられる**(山王では 448 枡のうち真の欠陥は 56 枡だけだった)。
正しくは **超過 =(隣との落差)− max(設計の法の一枡ぶん, 現地形自身の落ち)**。

⚠ **実装の地形の刻み(Unity では 2m テクセル)より細かい土は建たない。** 幅 1m の畝を図の格子で
消しても、建つ地面は変わらない。図の分解能で辻褄を合わせない。

⚠ **土留めは「段差があるから置く」のではなく、実測してから置く。** 松江松平の表郭の西縁は
図の上では 15間の石垣が要るように見えたが、実測すると段差は北端 1.89m・中ほど 0.91m・
**v12 でゼロ**・その先は逆に切土だった(ユーザー指摘:「TW_OmoteW が必要なのか疑問です」)。
**縁の段差を 1.5間刻みで測って表にしてから**、土留めか法面かを決める。

## 断面の「何を切るか」は手で書かない ★(2026-08-23 是正)

**断面の note に交差リスト(「西斜面→西庭→役所→…」)を手で書くと、棟を動かすたびに腐る。**
松江松平で **8本中6本**が旧配置のままになり、断面Dの note は「奥台所の脇→長局二列」と書いて
いたのにその2棟は断面の軸上に無い、という状態で検図に出た。

**構造で防ぐ**: json の断面は **軸(u/v)・位置(at)・目的**だけを持ち、
**何を切るかは生成器が毎回算出して図の見出しに出す**。

```python
def section_crossings(d, sec):
    ax, at = sec["axis"], sec["at"]
    hit = []
    def add(nm, a, b, c, e):
        if ax == "u":
            if a <= at <= c: hit.append((b, e, nm))
        else:
            if b <= at <= e: hit.append((a, c, nm))
    for m in d["munes"]:   add(MUNE_JA.get(m["name"], m["name"]), m["u0"], m["v0"], m["u1"], m["v1"])
    for x in d["service"]: add(x.get("label", x["name"]), x["u0"], x["v0"], x["u1"], x["v1"])
    for x in d["gardens"]: add(x.get("label", x["name"]), x["u0"], x["v0"], x["u1"], x["v1"])
    hit.sort(); return [h[2] for h in hit]
```

**同じ原理を他にも当てる** — 図に出す数値・名前は**すべて設計値から組む**。
生成器の legend/caption に `"■ 表郭 25.8"` と直書きしていたために、正典が 26.7 になっても
図だけ 0.9m 古いままだった(同じ回に発覚)。

### 棟を動かしたら追随を要するもの(チェックリスト)
棟の矩形だけ動かして周辺が取り残される事故が繰り返し起きている。**動かしたら必ず全部見る**:

| 追随先 | 症状 |
|---|---|
| `rooms`(室の座標は**絶対グリッド**) | 室名だけが旧位置に残る(庭の中に「奥台所48畳」が浮く) |
| 断面の note と軸 | 上記 |
| `routes` の折れ線 | 移設先の室内を貫く |
| `wells` | 「厩脇の井戸」が厩から87m離れる / 湯殿の水が61m先になる |
| `links` の両端 | 削除した廊下がシーンに孤児として残る |
| `kaidans` の位置 | 存在しない帯の上に石段が乗る |
| 文章(kosho)と `_pending` | 消滅した郭の名が残る |

**「動かしたのに追随していない参照」は機械検査に落とす。**検査の無い不変条件は必ず壊れる。

## §3c. 断面 — 数を惜しまない ★

- **東西・南北の格子で通す。** 込み入った地形なら**片方向3本では足りない**
  (土井邸は 3本 → 東西5本+南北6本に増やして初めて、過大な土留め2本と
  受け無しの段差1箇所が見つかった)。各節の頭に**切り位置のキープラン**を置く
- **造成前の現地形を破線で重ね**、その間を §3b と同じ配色で塗る。実線との差が切土/盛土
- **無造成の区間は地盤線に太い帯**を敷いて明示する。
  色が無いのが「反映漏れ」なのか「触っていない」のかを、図の上で区別できるようにする
- **土留めは設計高さの矩形で描かない。** 天端は面の高さで一定でも法尻は地形なりに上下するので、
  **その位置の地盤まで**描き、露出高を数字で入れる。設計高さで描くと落差の小さい区間で
  壁が土に埋もれ、要らない壁が図に残る
- 断面に**石段を踏面/蹴上のギザギザで描く**。垂直な壁が並ぶだけの図は §1f を満たさない

## §3d. 動線図 — 「どういう動きをする想定か」を必ず示す ★

ユーザーの要求(2026-08-23)。平面と断面だけでは、**建てた後に人がどう動くか**が読めない。

- 系統を分けて色を変える: **表向(客・使者)/ 役方(日勤)/ 勝手(賄・物資)/ 奥向**
- 折れ線を設計値 `routes`(grid 座標)に持ち、生成器が**延長・昇り・越える石段の段数**を算出する
- **石段の位置を図に重ねる** — どこで段を越えるかが動線の質を決める
- **勝手の動線を必ず引く。** 裏門・勝手門が無い屋敷では、米も薪も表門から石段を登ることになる。
  これは図に引いて初めて分かる欠陥で、門を増やすかは格式に触れるので**ユーザーの裁定**に回す

## §3e. 全体設計と詳細設計 — 粒度を分ける ★★

**指図は二段で描く。混ぜると必ず隙間が空く。**

| | 全体設計 | 詳細設計 |
|---|---|---|
| 決めるもの | 区画・面(段)の高さ・棟と郭の並び・動線・開口の位置 | **部材どうしがどう接するか** |
| 単位 | 間・m(1間刻みでよい) | **面の座標(cm 単位)** |
| 図 | 敷地図・現況図・切盛図・断面・動線図 | **取り合い図(接する面を描いた詳細)** + 取り合い表 |
| 誰が使うか | 考証・検図・建蔽率 | 実装(棟梁)。ここが空だと実装者が発明する |

⚠ **全体設計だけ描いて実装へ渡すと、実装者は「中心を合わせる」しかできない。**
それが 2026-08-29 に松平邸で起きたこと — 門は開口の芯に、長屋は run の頭から丸ごと並べていて、
**同じ門の左右で 1.66m の食い込みと 0.96m の隙間が同時に起きた**。
ユーザーの言葉: 「オブジェクト同士の位置関係は常に**どの点同士を接するか**を厳密に考えないと隙間が空く」。

## §3f. 取り合いは**面**で決める ★★

**隣り合う物は、必ず「Aのどの面」と「Bのどの面」が接するかを書く。**中心・芯・ピボットで合わせない。
部材の実寸は差し替えで変わるので、**芯で合わせた設計は部材を替えた瞬間に破れる**。

### 取り合い表に書く項目

| 欄 | 意味 | 例 |
|---|---|---|
| A / B | 接する二者 | `NE_Nagaya_1`(長屋) / `Kuramon`(門) |
| Aの面 / Bの面 | **どの面か**を名前で | Aの東妻面 / Bの西の門柱の外面 |
| 納め | 突き付け / 差し込み / 被せ / 見切り | 突き付け |
| 寸法 | 目標値と許容 | 0.00m(+0.05 / −0.00。**隙間は不可、めり込みは0.05まで**) |
| どちらが動くか | **可動側を必ず決める** | 長屋(門は開口の芯に固定) |

- **可動側を決めないと両方が動かず、あるいは両方が動いて振動する。**
  門・櫓・石段のように位置が意味を持つ物を固定側、run(長屋・塀・石垣)を可動側にするのが既定。
- **run の端は「丸ごとの部材が並んだ成り行き」にしない。** 開口の縁に端を合わせ、
  端数は run の中で吸う → [run の端数は「棟の間隔」で吸う](perimeter.md)
- 閉じの許容は **「隙間 > めり込み」**(memory `gate-wall-closure-rule`)。
  0 を狙い、外すなら**めり込む側**へ外す。

### 実装側の作法 — 置き方の4手(2026-09-20 施主指示: 検査を足さず、置き方で起きなくする)

```
1. 固定側を先に置く(門構え=門柱・隅部材・櫓)
2. 可動側は、前の相手と**触れる所**まで寄せる — 番所→袖塀→表長屋→練塀 の連鎖。
   相手に取るのは「名指しした面」ではなく**相手の駒そのもの**(`EdoBuild.Abut(駒, 相手, 向き, 隙)`)。
   長屋は長さ固定なので平行移動だけ。端数は鎖の末端の**伸縮側(練塀)**へ流す
3. 高さは**触れている箇所**を測って据える — 囲いは石垣の天端(`EdoBuild.SeatOnCrest`)、
   御殿・廊下・石段は造成後の段の格子点の中央値(`EdoBuild.PadY`)、木・石・柵は `EdoBuild.Contact`/`SeatOnGround`。
   ⛔ 「底」「地面」で済ませない — 触れる所は底とは限らず(斜面の上手側・石の据え面の縁・根張り)、複数あり得る。
   指図の y は使わない
4. 事後に寄せる関数を持たない(`CloseKadoSeams` / `AlignGateFace` 型)。寄せる関数があるほど置き方の欠陥が隠れる
```

⛔ **4手の前提: 部材の基準点(ピボット・原点・bounds の中心)で位置を決めない。絶対に。**横も高さも、
**何かと何かが接するなら、触れている箇所を測って**決める(2026-09-20/09-21 施主指摘
「実物の底や地面では漏れる。接地箇所を測れ」「地面だけでなくオブジェクト同士も。接する場合は接触している箇所を測れ」)。
⛔ **相手は地面だけではない** — 部材どうし・屋根と塀・隅と塀・庇と縁も同じで、触れる所は名指しした面の外
(庇の裏・基壇の縁・留め継ぎの先端)にあり得る。面が合っていることを「納まった」と読まない。

道具は `Assets/Edo/Scripts/Editor/EdoBuild.cs`「据え付けの技法」節:
`Face`/`FaceSpan`(帯で面を測る)・`FaceOut`/`AlignFace`(線からの張り出し・法線方向へ寄せる)・
`Abut(駒, 向き, 帯, …)`(名指しした面へ突き付け。`gap` は `joints[].gap`)・
`Contact(駒, 相手, 向き)`/`Abut(駒, 相手, 向き, 隙)`(**相手の駒そのもの**と触れている箇所を測って寄せる)・
`EdgeAlong`/`StretchEnd`(末端の駒の伸縮)・
`PadY`/`GroundGrid`(格子点の中央値・最寄り格子点)・`CrestY`/`SeatOnCrest`(石垣の天端に据える)。

⛔ **指図の s・y を座標として置かない。**設計値どおりに置いたつもりでも、部材のピボットが芯に無い・
軒が出ている・スケールが掛かっている・腕の実寸が宣言と違う、のどれかで面はずれる
(松江松平 2026-09-20: 門の隙 0.42m・隅の穴 1.18m・御殿の浮き 0.93m・番所の区画外 3.35m は
すべて「指図の数値を信じて置き、実メッシュは測って⚠を出すだけ」の型)。
⛔ **帯を揃える** — 建てる側と検める側が別の高さで測ると、同じ物が「閉じている」と「穴」に分かれる。

## §4. 作図の作法

- 柱間は**江戸間 1間 = 6尺 = 1.818m**。建物は桁行×梁間の間数、部屋は**畳数**(1間² = 2畳)
- **部屋名を図中に書き入れる** — 甲良家伝来「江戸城本丸御殿図」(重文646点)や「江戸御殿之図」は
  部屋名・広さ・畳の種類・井戸や水盤の位置まで記入し彩色を使い分ける
- **表向 / 中奥 / 奥向**を区分し、境に**御錠口**を置く([西川1959] 表向→中奥→奥向が一列に順次連続)
- **大台所は敷地のほぼ中心**([福井図]、[西川1959] 御殿中央部の北かつ中奥付近)
- **柱間を問う前に、史料の総長がその柱間で割り切れるかを当たる。**「6尺5寸で割り切れないが許容するか」と
  先に問うと、答えが返ってから総長を当て直すことになる。山王の透塀は候補を当て違えて**部材25点を全数焼き直し**
  (2026-09-18)。⛔ 割り切れる柱間が一つしか無いなら、それは裁定ではない
- 方位は「街路の位置が方位より優先」。原図に方位盤が無ければ**図面相対**(上辺/左辺)で記す
- 座標は**世界座標(Unity のシーン座標)から直に変換**する。図面と実装がズレない
- **矩形の重なりは機械検査してから出す**(総当たりで0件を確認。目視では必ず見落とす)

## §5. 原図を読むときの落とし穴(2026-08-14 に全部踏んだ)

- **辺長の対応を取り違えると面積が半分になる。** 福井図を「130/77/113/105 の四角形」と読んで
  「最大3,300坪にしかならない、注記の6,600坪と矛盾する」と報告したが、実際は
  **上辺130・下辺105・左辺190(右辺は77+113の段違い)の台形**で 6,617坪。合っていた。
  → **面積が注記と合わないときは、自分の辺の対応を疑う。**
- **文字記録から起こした「推定復元」を原図の写しのように扱わない。** 確度を明記し、
  原図が手に入ったら差し替える。
- 原図が手元にないなら**ユーザーに原図を求める**。推定で進めて後から全部やり直すより速い。

## §6. 書き起こしの回し方 — 一度に一章、長引いたら途中で返す ★★(2026-09-20 日誌)

書き起こしは**この普請でいちばん時間を食う工程**。2026-09-18 は 7 回で 790 分(実働の 88%・最長 233 分)、
2026-09-19 は 9 回で 976 分(実働の 65%・最長 489 分 = 8 時間)。1 回が一日を占めると、その間
**施主には何も出ず、裁定も止まる**。

- **一度の依頼は一章まで。**「屋根と軒」「廊下の取り合い」「外周」を 1 通で渡さない。章が跨るなら通を分ける
- **90 分を超えたら、途中でも書けた所までを返して一旦戻す。**残りは次の通で続ける。
  途中で返せば、施主はその間に裁定を打てる
