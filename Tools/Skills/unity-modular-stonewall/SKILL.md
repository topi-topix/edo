# Modular stone-wall (石垣) authoring in Unity

**この SKILL.md は原則と索引。** 根拠データ・コード・個別ケースは `references/` にある。

**正典はユーザーの手組みであって、私が発明した式ではない。** 以下の数値はすべて
`Edo_Yashiki_Ota / _Kano / _Matsudaira → Ishigaki`(赤坂、ユーザーが手で組み直した commit `038a07d`)
から実測し、ユーザーが却下した機械生成版2つ(`f9bd701`, `a3f5187`)と突き合わせたもの。
生の実測値と差分は `references/yashiki-enclosure-baseline.md`。

⚠ **三屋敷の3軒目は「鍋島」— 松江松平(出羽守)邸ではない。**
シーンのグループ名は `Edo_Yashiki_Matsudaira` だが、正体は**佐賀鍋島家の溜池中屋敷**
(切絵図の「松平備前守」は「松平肥前守」の誤読)。江戸には松平が非常に多く、
edo-unity のシーンだけで7家ある。**「松平」だけで呼ばない** — 出羽守(松江)・大和守(川越)・
日向守・美濃守・主水正・肥前守(=鍋島)は別家で、区画も石垣の作法も違う。
当プロジェクトの当該邸は **松平出羽守定安(出雲松江藩)上屋敷 = `matsudaira_dewa`**。

**Golden rule: 本物の石積みは水平で、辺はまっすぐで、コーナーはコーナーに建つ。**
生成された壁の3つの兆候(ユーザーが気づく順):

1. 出隅ブロックが、接する両方の壁のどちらとも面一でない
2. ほとんど見えない折れで辺が2 run に割れ、その折れ目に出隅ブロックが挟まっている
3. 天端が地形に追従している

**折れ角を決め打ちしてはならない。** コーナーの角度は現地が決めるもので毎回違う。
「コーナーはN°で曲がる」という形のルールはすべて誤り。コーナーは**面と端点**(R1/R2)で置く。

## §1. 出隅 — 最初に判定されるのはここ

### R1 — 片方の面を、隣の石垣の面と完全に一致させる
接する2つの壁のどちらかを選び、コーナーの対応する面をその壁の外面と**同一平面**にする
(近いではなく同一平面)。実測: 12コーナーで面の角度 **0.00°**、面のオフセット **0.04m 以内**。
どちらの壁を選ぶかは自由(ユーザーは12中10で出ていく run を選んだ)。
**許されないのは「どちらとも面一でない」「両者の中間を取る」** — 継ぎ目が0本でなく2本になる。

### R2 — もう一方の辺は、コーナーのもう一方の面の**端点**に合わせる
もう一方の壁の外面が、コーナーのもう一方の面の**apex でない側の端点**を通るようにする。
面一の面に沿ってブロックをスライドさせ、そこに乗ったら位置が決まる。
実測: 12中10が **0.06m 以内**。

これが角度を自由にする仕組み — **コーナーは次の壁に「方向」ではなく「点」を渡す**。
次の壁はそこから現地の必要な方位へ出て行き、2つの面はその固定端点まわりにV字に開閉する。
**コーナーから次の壁の方向を導出しない。直角に近いことを要求しない。**

⚠ **apex ではなく端点で測る。** apex から隣接面までの距離は同じ12コーナーで ±0.85m ばらつく。
機械生成版はこれを間違えて apex を境界頂点に固定し、全ブロックが **3.40m**(=√2×2.4)
内側にずれた — 2.4mの石の立方体が庭に立ち、囲いの角は開いたままだった。

**生成器向けの閉形式**: 出ていく run(方位θ)を面一側に選ぶなら `yaw = θ − 90°`、`position = 境界頂点`。
この −90 はブロック自身の正方形の幾何であって折れ角の仮定ではない(どの折れ角でも成立)。
**必ず R1/R2 で結果を検算する。**

### R3 — 辺はまっすぐ通す。同じ面に見えるものは1本の辺
2つの run が1つの連続した面に読めるなら、それは**1本の run**(1方位・1直線・間にブロック無し)。
判定は**角度でなく距離**: run のピボットに直線をフィットして横方向のばらつきを見る。
ユーザーの run は153mで **≤0.077m**。**0.1m を超えたら2方位が1本のふりをしている。**

凸な区画には**出隅だけ**でよい。`Castle Wall Corner 2_2x2`(入隅)は凹の接合に使う。
横矢掛かり/矩形の折れは 出隅×2 + 入隅×2。

### R4 — 両側の直線を出隅に食い込ませる。突き合わせない
コーナーのピボットから最寄りの直線ピースまでの実測距離: 出ていく run **0.84–1.97m**、
入ってくる run **0.19–1.81m**(いずれもブロックの奥行より小さい)。
両 run をコーナーのフットプリントの**中へ**運び込む。中に埋まった直線ピースは詰め物として残してよい。
**継ぎ目は重なりより常に悪い。**

→ キットの寸法表・12コーナーの実測値・機械生成版の失敗の詳細は
`references/corner-and-pivot.md`(**ピボットが mesh 中心にない罠**もここ)

## §2. 直線区間

- **ピッチ 1.800m**(2.0mモジュール)→ 継ぎ目ごとに **0.20m 重なる**。
  加納+鍋島で 450継ぎ目中423(94%)が 1.800±0.005。残りは run 端の短い閉じピース(1.25–1.42m)
- **完全に共線**。run 線に対するピボットの横ばらつき **≤0.077m**(最長153m)
- **巻き方向: yaw が増える=上から見て時計回り。躯体は進行方向の左=ピボット多角形の外側に来る。**
  つまり**author する多角形は壁の内面**で、2.4mの厚みはそこから外へ張り出す
- run の端は必ずサブモジュール間隔の1枚を足して閉じる

## §3. 高さ — 丸い数字で一直線

ユーザーはすべて丸める。「なめらか」でも「±5cm」でもなく、**1つの壁に1つの値、人が打つ数字**。

| group | `position.y` | `scale.y` | coping(天端) |
|---|---|---|---|
| 太田 | **-21.000**(×137) | **1.500**(×137) | **-15.00** |
| 加納 | **-19.000**(×154) | **2.000**(×154) | **-11.00** |
| 鍋島 | **-19.000**(×312) | **2.000**(×312) | **-11.00** |

`coping = position.y + 4.0 × scale.y`。壁全体で distinct な `position.y` は **1**、`scale.y` も **1**。
コーナーは接する run と**同じ** `position.y` / `scale.y` を取る(天端がコーナーで揃う)。

> 地面が波打つなら**地面を壁に合わせて均す**。壁を地面に合わせない(§5)。
> ピースごとの `scale.y = (SampleHeight − baseY)/meshH` は生成壁の最大の兆候
> (60–80種類の高さとノコギリ天端になる)。

**隣り合う壁が本当に高さ違いのとき**: 段にせず、ばらつかせず、**25〜30ピースかけてランプ**する。
1ピースの段差 ≤0.15m、段差の符号は**反転させない**、最後のピースの `scale.y` は隣グループと**完全一致**。
平坦run→ランプ→平坦run。折れ角で高さが変わるなら**コーナーで変え、高い方の `scale.y` をコーナーに与える**
(コーナーの段は石積みに読めるが、run 途中の段は破損に読める)。

## §3b. 駒は伸縮させない — 端数は重なりで、高さは埋まりで ★★★

**2026-08-29 ユーザー裁定。**

> 1つの石垣オブジェクト自体のXYZ方向の長さは変えない。
> runの長さは石垣の重なり具合で調整する。
> 石垣の高さは地面への埋まり具合で調整する。

⛔ **run の高さに合わせて駒を等倍で拡大縮小してはいけない。**
石の寸法は実物で決まっている。壁が低いのは石が小さいからではなく、**石が地中に埋まっている**から。

松江松平邸の実害(2026-08-29・ユーザーのブックマーク #14/#15 で9箇所指摘):
run ごとに `scale = (s,s,s)` を掛けていたため、

- 隣り合う run で石の大きさが **0.26m 〜 1.90m(7.3倍)**。テクスチャの目が段ごとに変わる
  (辺3 `S1e`→`S2` で 2.3倍、辺12 `W3`→`N_Nagaya_W` で 2.1倍)
- ずれ量が駒の大きさに比例するので、**隣の run との間に隙間か重なりが必ず出る**
  (実測 隙間 0.68m / 重なり 0.70m)

### 割り付け(閉形式)

駒の走り長 `W`、ピッチ上限 `pitchMax`(= W − 重なりの下限)として、区間 `L = s1 − s0` を:

```
N     = (L <= W) ? 1 : ceil((L − W) / pitchMax) + 1
pitch = (N > 1) ? (L − W) / (N − 1) : 0
i 枚目のピボット s = s0 + pitch·i     // 箱は [s, s + W]
```

`pitch ≤ pitchMax` が保証されるので **重なりは常に下限以上 = 隙間は原理的に出ない**。
最後の駒の端が `s1` にちょうど乗る。⛔ 仕舞いに `pos = s1` の駒を足さない(丸ごとはみ出す)。
`L < W` の区間は1枚が隣へはみ出す — **隙間より重なりを採る**のが正典。

### 高さ

`position.y = 天端 − (駒の丈)`。駒の天端が run の座に来て、余りは地中へ。
露出(座 − 地盤)が駒の丈を超える区間は run を割る(松江松平は `exposeSplit = 2.50m`。
実測の最大露出は 2.48m で駒の丈 4.00m の内側)。

### Castle Wall の実寸(scale=1・2026-08-29 実測)

ローカル箱 **X −2.40〜0 / Y 0〜4.00 / Z −2.00〜0**、ピボットは (0, 0(底), 0) の角。
据えると**外向きの面がピボット**(厚み 2.40m は内側へ)、走りは **[pos, pos+2.00]**。

### 検査

- 駒の `lossyScale` が (1,1,1) か(≠1 を挙げる)
- 据えた実メッシュの s の端が run の s0/s1 に乗っているか
- 隣り合う run の端面どうしに隙間が無いか
- 露出が 0 〜 駒の丈 に収まるか

**感度試験を必ず付ける。** 松江松平の指図側は 8 probe(駒を伸縮/run に規模を持たせる/
ピッチ上限を駒より長く/重なり下限を上げる/座を上下/地盤を消す/重なり上限を下げる)で
全部鳴ることを確認している。

## §4. 開口(門・石段)

### ⛔ skip では開口の縁を狙えない — 縁を起点に並べる

**駒のピボットは走り方向の**端**にある。**

⛔ **どちらの端かは、置くたびにその場で測ること。** ここに長く
`[pos − 2.0×s, pos]` と書いてあった(実測 2026-08-16: pos z=1047.20 の駒が箱 Z[1044.20, 1047.20])が、
**yaw の取り方が変われば向きは逆になる。** 松江松平邸(2026-08-29)は
`psi = atan2(-n.y, n.x)` で据えており、実測すると箱は **`[pos, pos + 2.0×s]`**。
この記述をそのまま信じて `t0 + 2.0×s` から並べていたため、**石垣が run ごと丸ごと1駒ぶん
s の増える向きへずれ**、s0 側が裸・s1 側がはみ出していた(ユーザー指摘
「石垣と塀の端があってません」の正体)。

**確かめ方**(1回・10秒):1枚置いて `transform.position` を辺沿い s へ射影し、
実メッシュの頂点の s の最小・最大と比べる。`[pos, pos+w]` か `[pos−w, pos]` かがその場で出る。

いずれにせよピボットは端なので、pos を駒の**中心**とみなして `|t − gapT| < 半幅` で skip すると:

- 開口が **1.0×s ずれる**(走りの向きで左右どちらへずれるかが変わる)
- 開口の縁が**ピッチ 1.8×s の格子にしか来られない**
- s が run ごとに違えば、ずれ方も run ごとに違う

実害(岡部邸 2026-08-16): 東の参道は開口の芯が 1.70m ずれて片側 1.62m かぶり・反対側
1.78m の隙間。西は開口が 5.10m しか空かず(必要 7.63m)、**石段の上9段が駒に 1.39m 食い込み**、
残り 0.59m が階段廊下に押し付けられていた。ユーザー指摘「石階段と木階段がかぶっている」の正体。

**正しい据え方** — 壁を「開口の南側」「北側」の**2本に割り**、それぞれの区間を
**§3b の閉形式**で埋める。両端が縁にちょうど乗り、端数は重なりが吸う。

```csharp
// 区間 [t0, t1] を駒で埋める。W=駒の走り長 / PITCH_MAX=ピッチ上限
int PlaceCW(..., float t0, float t1, ...) {
    float L = t1 - t0;
    int   N = (L <= W) ? 1 : Mathf.CeilToInt((L - W) / PITCH_MAX) + 1;
    float pitch = (N > 1) ? (L - W) / (N - 1) : 0f;
    for (int i = 0; i < N; i++) {
        float t = t0 + pitch * i;                  // 箱は [t, t + W](向きは実測して確かめる)
        Place(..., EdgePt(edge, t), yaw, Vector3.one, ...);
    }
    return N;
}
```

⛔ **撤回した旧版**(2026-08-29 まで):`t0 + 2.0×s` から並べ、仕舞いに `pos = t1` の駒を足す。
起点も仕舞いも**箱の向きの取り違え**で、run 全体が1駒ぶんずれ、仕舞いの1枚は丸ごとはみ出していた。

**検査**: 開口の端面 と 相手(門の躯体・坂の土留めの外面)の差が **0.00m**。
「2.2m 超の隙間はバグ」だけでは足りない — **位置と幅の両方**を数値で見ること。

### 門の開口

囲いに1つ、実際の門の寸法で。実測の開口: 太田15.52m / 加納29.01m / 鍋島17.07m。

## §6. 手直し済みの石垣は絶対に作り直さない

ユーザーはこの壁を手で組んでいる。再生成は黙ってそれを捨てる。
生成器は**既存の `Ishigaki` 子を残す**のが既定(`f8f9209`)で、広げた門に干渉するピースだけ削る。
新しい生成器でもこの挙動を保つ — 作り直しは**明示的な確認の後だけ**、「全部ビルド」の副作用では絶対にしない。
→ メモリ `handbuilt-assets-are-canon`
