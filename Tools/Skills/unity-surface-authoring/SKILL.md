# Unity Surface Authoring (via MCP)

**この SKILL.md は原則と索引。** 手順とコードは `references/` にある。

このユーザーの Unity プロジェクト(edo-unity / edo-assets、URP、Unity 6000.x)で実際に成果が出た
技術のカタログ。Unity-MCP の一般的な操作(GameObject・シーン・テスト)は `unity-mcp-skill` を、
石垣の配置は `unity-modular-stonewall` を、屋敷の中身は `unity-buke-yashiki` を見る。
ここは**表面を正しく見せること**と、そのために必要な土台に特化している。

---

## 原則

**Golden rule: 見えない表面は作れない。** 視覚的な変更は必ずレンダしたスクリーンショットで確認する。
高価な塗りは、コミットする前にプレビューで検証する。

- **変更 → スクショ → 読む → 反復。** 塗りが効いたと仮定しない。見る。
- 全地形にかかる重い操作は、粗いグリッドかプレビュー画像でルールを試してから本番へ。
  1Mテクセルの逆投影を 65×65 の粗グリッド+バイリニアに置き換えても誤差はサブメートル、速度は桁違い。
- **ベイク・塗り・造成は「範囲限定」を既定にする。** 全域を対象にすると、無関係の場所を壊した事故が
  実際に起きた(`references/terrain-editing.md`)。
- **地形編集は `Undo` の対象外。** 触る前にハイトマップを `.bin` でスナップショットする。
  これが唯一の戻り道。
- **自分が起こす `SaveScene` / `SaveAssets` の前に `.unity` と `TerrainData.asset` を退避する。**
  `Scene.isDirty` は「メモリ==ディスク」の信号として信用できない(ドメインリロード直後は false でも
  中身が違うことがある)。保存するとユーザーの未保存編集も一緒にコミットされる — 無害だが検出して報告する。
- 再利用できるエディタ道具はプロジェクトの `Editor/*.cs` として残す。
  **このシーン固有の事実はメモリへ**、再利用できる技術はこのスキルへ(同じ事実を両方に書かない)。

## ⛔ 部材の基準点(ピボット)で位置を決めない — **触れている箇所**を測って据える ★★★

**部材の基準点(ピボット・原点・bounds の中心)で位置を決めない。絶対に。**ピボットの位置は部材ごとに違う
(根元 / 中心 / 天端 / 枝の付け根)。座標へ直に置くと、メッシュがピボットより下へ伸びている部材は
その分だけ地中へ潜り、上へ伸びている部材は宙に浮く。

**「実物の底を地面に」でも漏れる(2026-09-20 施主指摘)。据えるのは触れている箇所。**そこは底とは限らない:
斜面では**上手側の頂点**が先に着く(底の一点で据えると下手側が浮き上手側が埋まる)・据え面のある石は**面の縁**・
木は**根張りの端**・板塀の柱は**柱の足元**であって板の下端ではない。**触れる所が複数**のこともある(石の三点・柱の並び)。
だから「どこが着くか」を決め打ちせず、**全頂点の『高さ − 真下の地形』の最小**を測る(`EdoBuild.Contact(駒)`)。

**⛔ 相手は地面だけではない(2026-09-21 施主指摘)。**部材どうし・屋根と塀・石と土台・庇と縁も同じ作法。
→ **作法と道具の正典は `docs/oki-kata.md`**(4手・相手ごとの関数・許容0の数え方)。ここに書くのは
**地表と植栽に固有のこと**だけに留める(⛔ 二重に書かない)。

⚠ **2026-09-20 松江松平で実測**: 下草を「設計面へピボットを置く」だけで据えていたため、実メッシュの底が
地面から **1.90m** 下にあった。⛔ **レンダでは気づけない** — 葉は地表に見えているので絵は正しく、
数値の検めだけが「埋没 1.90m」と鳴る。施主から「なぜそんなことになるのか分からない」と指摘された。
景石も沈める量を **0.34m の決め打ち**にしており、大きい石は浮き、小さい石は沈んでいた。

⭕ **作法**:

```csharp
// 地面と触れている箇所を測る(全頂点の「高さ − 真下の地形」の最小。at=その箇所、n=同じ高さで着く頂点の数)
float gap = EdoBuild.Contact(go, out var at, out int n);   // 正=浮き / 負=埋没
// 相手が**駒**のとき(部材どうし・屋根と塀・隅と塀)。dir = go を相手へ押し付ける向き
float g2 = EdoBuild.Contact(go, other, dir, out var at2, out int n2);  // 正=隙 / 負=めり込み / n2=当たりの筋数
EdoBuild.Abut(go, other, dir, 0f, out at2, out n2);        // 触れる所で止める(隙 0)
// 触れている箇所が地面に着く高さへ据える
EdoBuild.SeatOnGround(go);                 // 木・低木
EdoBuild.SeatOnGround(go, sink: 0.05f);    // 下草は根元をわずかに埋める
// 丈に比例して埋める(景石の 1/3 埋め。個体差のある石でも埋まり方が揃う)
EdoBuild.SeatBuried(go, 1f/3f);
// 石垣の天端に据える(囲い)・段の格子点の中央値に据える(棟)
EdoBuild.SeatOnCrest(go, stones, 0.10f, out var crest);  EdoBuild.PadY(poly, 1.0f, out var spread, out var k);
```

- ⛔ **設計面(`DesignY`)へ置かない。**設計面と実際の地形は造成の残差ぶん食い違う(松江松平で 0.55〜0.60m)。
  据えるのは**実際の地形**(`EdoBuild.GroundGrid` — 双一次でなく格子点。⛔ `Terrain.SampleHeight` を
  任意座標で呼ぶと縁の擦り付けを拾って 0.1m が 2m に化ける)。
- ⛔ **沈める量を決め打ちしない。**`sink` は**意図して埋める量**であって、ピボットのずれを吸わせる物ではない。
  ずれは測って消す物で、決め打ちで隠すと部材を替えた瞬間に破れる。
- ⛔ **`bounds.min.y` を「触れている箇所」と呼ばない。**bounds は軸平行の箱で、斜面・据え面・根張りを知らない。
- ⛔ **「面どうしを合わせた」で済ませない。**名指しした面が合っていても、庇の裏や基壇の縁が先に当たっている
  ことがある。部材どうしも**触れている箇所を測る**(`Contact(駒, 相手, 向き)`)。
- ⚠ **`Renderer.bounds` / 頂点には billboard・LOD・当たり判定が混ざる部材がある。**触れている箇所が異様に低い
  部材に出会ったら、まず `EdoBuild.Contact` の `at` を刷って、どのメッシュのどの頂点が当たっているか名前で確かめる。
- 報告には**触れている箇所の隙(`Contact` の返り値)と当たりの数**を出す — 「置いた」「面を合わせた」ではなく
  **「どこで、どれだけの隙で触れているか」**を書く。

→ 置き方の正典は **`docs/oki-kata.md`**。屋敷の取り合いの指図は `unity-buke-yashiki`。原則は同じ
(**固定側を先に・可動側は相手と触れる所まで寄せる・高さは下の実物を測る・事後に寄せる関数を持たない**)。

## ⛔ 自作の低ポリゴンの木を置かない ★★★

**2026-08-30 ユーザー指示** — 「邸内に自作の低ポリゴンの木が配置されています。
**これは2度と使わないでください。見た目がしょぼすぎます。** assets のものを利用するから、
assets を参考にリアルに再現したものを利用してください」

⛔ `Assets/Edo/Terrain/details/BroadleafTree.prefab`(`EdoAssets.Own.Broadleaf`・**2,384三角**)は
使用禁止。在庫の木(Waldemarst FreeJapaneseGarden の黒松・桜・竹、Japanese Castle の Foliage、
NatureManufacture)と並べると、枝の分岐も葉のカードも粗さが一目で分かる。

**植栽は在庫のパックから採るのが既定。** 在庫の引き方は `docs/asset-catalog.md` §9 →
`docs/asset-index.tsv`(ポリ数・実寸つき)。⇒ 置く前に必ず在庫を引く。

**在庫に無い樹種がどうしても要るとき**(常緑広葉樹・梅など。JG パックには黒松・桜・竹しか無い)は、
**在庫の木の作りを参考にリアルに再現**する:

- 幹と主枝は**実ジオメトリ**で分岐させる(円錐を積まない)
- 葉は**カード(クロスした板)にアルファのテクスチャ**。在庫の木の葉テクスチャを流用する
  (材質を新規に作らない — キットの材質名を保つのが規約)
- **LOD を持たせる**。在庫の木は LOD 付きなので、無いと遠景でだけ浮く
- ポリ数は在庫の同格の木に合わせる(JG の黒松 Mid で数千〜1万三角)

⛔ **「遠景だから粗くてよい」で通さない。** ユーザーは邸内の近景で見ている。
