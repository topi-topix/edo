## 施主と決めた方針

1. **Unity の待ち時間は対象外**(施主指示)。縮めるのは「考えている時間」。
2. 考える時間の大半は**1往復ごとの固定費**(経緯と規則を読み直す → 数字を読んで判断 → 次の一手を決める → 命令を書く。1往復 1〜3分)。
   ⇒ **往復の回数を減らす**のが本命。次が「最初に読む量を減らす」「結果を合否で返して判断を要らなくする」。
3. 「寄せて測るを繰り返す道具」は**プログラム(`EdoBuild` の C# 関数)**であって、役への指示ではない。
   指示を工夫しても、繰り返しの中に役がいる限り時間は縮まない。
4. **関数の中の計算を速くする(二分探索など)は効かない** — 中の繰り返しは元々ミリ秒。縮むのは数秒。
   効く計算の工夫は二つだけ: ①多くは一度測って隙の分だけ動かせば閉じる(繰り返し不要) ②**解く順(門→石段→塀)をプログラムが持つ**と前へ戻る手戻りが無くなる。

| 何を変えるか | 縮む時間 |
|---|---|
| 繰り返しの中から役を外す(プログラム化) | 数十分 |
| 部材を解く順をプログラムに持たせる | 流し直しの分(十数分〜) |
| 関数の中の計算を速くする | 数秒(やる価値は薄い) |

## コンパイル待ちの実測と道具(2026-09-26 追記・票 EDO-0457)

Unity 自身のコンパイル+再読み込みは1回 **4〜7秒**(`Logs/Editor.log` の `Domain Reload Profiling`・作業場 `Koba.unity`)。
EDO-0437 の建てる役3回ぶんでは、コンパイル待ち約31分のうち Unity が要ったのは約2分。残りは待ち方から出ていた:

| 出所 | 1回 | 回数 |
|---|---|---|
| `refresh_unity` が戻るまで | 15〜20秒 | 毎回 |
| 手書きの `sleep 20〜60`・DLL の日付の見張り | 13〜60秒 | 毎回 |
| DLL が作り直されないのに上限(240・300秒)まで待つ空振り | 4〜5分 | 3回(理由は未確認) |
| 再読み込み直後に MCP が切れ `execute_code` が時間切れ | 約40秒 | 約6回 |

道具の要件(`Tools/Unity/` に一手):
1. 先に `Tools/Unity/cs_check.sh`(Unity 不要・3〜5秒)で `error CS` を行番号つきで返し、あれば Unity に触らず止める
2. refresh を依頼する
3. 待つ目印は Editor.log の再読み込み完了の行(`Tools/Unity/reload_cost.py` の読み方を流用・バイト位置で区間を切る)。固定 sleep を使わない
4. 作り直しが起きなければ、すぐ「作り直し無し」と返す
5. MCP の接続が戻るまで待ってから返す
6. 所要秒を返す

役の手順(`.claude/agents/edo-toryo.md`・`edo-fushin-qa.md`・`unity-mcp-skill` の該当節)に「この道具だけを使う・手書きの sleep/until/seq の見張りを禁じる」と書く。
完成の条件: 同じ作業場で C# を1行直す操作を5回回し、一手の中央値 10秒前後・最悪値併記・空振り0。次の建て直しでコンパイル待ちの合計を前後で比べる。

## ⚠ 踏まないこと

- **票1の関数を「事後に寄せる関数」にしない。**`docs/oki-kata.md` §2 の4手目は `CloseKadoSeams` / `AlignGateFace` 型を禁じている(置き方の欠陥が隠れる)。
  新関数は**置く時点の据え付けそのもの**として、固定側 → 可動側の順に「寄せる → 据える」を収まるまで回す物。建て終わった後に呼んで直す物ではない。

- 試しを速くするための縮小の試験台を作っても、**最後の確かめは本物の敷地で実メッシュを測る**(規則19「取り合いと境界の正の輪は実装」)。
