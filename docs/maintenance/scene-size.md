# シーンの重さを構造的に下げる（作業計画・指図）

作成 2026-08-15。**未実施 — この文書の承認を取ってから着手する。**
前段: `lfs-history-rewrite.md`（LFS履歴の掃除、実施済）
関連メモリ: `akasaka-scene-bloat` / `edo-github-repo` / `pond-snap-overlaps-in-scene`

---

## 1. 出発点

`Assets/Edo/Scenes/Akasaka.unity` は **102.5 MB**。LFS はバージョンごとに丸ごと保存するので、
**保存してコミットするたびに 102 MB が乗る**。無料枠 1 GiB に対して残りは約 440 MB＝**約4コミット分**。

### ⚠ 最初に立てた「地区ごとに additive scene へ分割する」案は、これ単独では答えにならない

ユーザー指摘（2026-08-15）: **「他の地区も今後岡部邸のような状況になります」**。
そのとおりで、分割案の前提が崩れる。

岡部邸は部材キット（`EdoGotenKit`）で棟を組んだ結果、**1屋敷で 11,859 個の
PrefabInstance = シーン全体の 48%** を占めている。同じ作り込みを他の屋敷にもやれば
**1屋敷あたり約30 MB ずつ地区シーンに積まれる**。地区あたり5〜8屋敷なので、
地区シーンは 150〜250 MB に育ち、**分割で稼いだ5倍は数屋敷ぶんで消える**。

→ **分割は「今の重さを割る」だけで、「重くなり続けること」を止めない。**
止めるには**重さの発生源**に手を入れる必要がある。

---

## 2. 何にバイトが使われているか（実測 2026-08-15）

シーンファイルを YAML ドキュメント境界で分解して集計した。

| 種別 | 個数 | 容量 | 割合 | 1個あたり |
|---|---:|---:|---:|---:|
| **PrefabInstance** | 24,699 | **64.9 MB** | **63.3%** | 2,756 B |
| Transform | 33,109 | 9.9 MB | 9.7% | 313 B |
| **MonoBehaviour** | **28** | **9.4 MB** | **9.2%** | **351 KB** |
| MeshRenderer | 7,157 | 8.9 MB | 8.7% | 1,304 B |
| GameObject | 8,416 | 3.7 MB | 3.6% | 455 B |
| MeshFilter | 7,157 | 1.9 MB | 1.8% | 275 B |
| その他 | — | 3.8 MB | 3.7% | — |

**わかったこと2つ:**

1. **PrefabInstance が 63%。** 1ブロック 2,756 B。ビルダーは全部
   `PrefabUtility.InstantiatePrefab` で部材を置いており（`EdoNishiTameikeBuilder.cs:86` ほか
   全ビルダー）、置いた部材1つにつき `m_Modifications`（位置・回転・名前の上書き）を持つ
   ブロックが1つ生える。**部材を置けば置くほど直線的に増える。**

2. **MonoBehaviour 28個で 9.4 MB。** 正体は **`WaterBody` 6個**（`WaterBody.cs:33` の
   `[HideInInspector] public float[] snap`＝地形の高さ配列）。最大の1個で 5.17 MB。
   メモリ `pond-snap-overlaps-in-scene` の「鍋島池の snap が三屋敷全域を含む」が
   そのまま容量に出ている。**池6個でシーンの9%。**

### 検証した「効かない案」

- **`Object.Instantiate` に変えてプレハブリンクを切る** → 効かない。
  単体プレハブなら 2,756 B が GameObject(455)+Transform(313)+MeshFilter(275)+MeshRenderer(1,304)
  = 2,347 B になるだけ（15%減）。**複数オブジェクトのプレハブでは逆に増える**
  （PrefabInstance は部分木まるごとを1ブロックで表すため）。

## 3. 方針 — 発生源に効く順に3つ

### B1. `WaterBody.snap` をシーンの外に出す（9.4 MB / 9%）

地形の高さ配列を YAML のテキストで持っているのが無駄。float 1個が10〜12バイトの文字列になる。

- 退避先はバイナリ資産（`.asset`）か `Library/`。**`EdoTerrainSnapshot` が既に
  `Library/` へ退避する仕組みを持っている**ので、それに寄せる
- 影響範囲が `WaterBody` 1クラスに閉じており、**作業手順は何も変わらない**
- 鍋島池の snap が三屋敷全域を含む件（`pond-snap-overlaps-in-scene`）も同時に見直す

### B2. 屋敷1つ ＝ プレハブ1つ（スケールの答え）

**ユーザー指摘への直接の回答がこれ。** 各屋敷を `.prefab` 資産として外に出し、
シーンには**配置の参照だけ**を残す。

実測（岡部邸を書き出して測った）: **`.prefab` = 31.2 MB / PrefabInstance 11,859**。
**総バイト数は減らない** — シーンからプレハブへ移るだけ。効くのは**粒度**のほう。

| | 今 | B2 のあと |
|---|---|---|
| 岡部邸を触る | 102 MB（シーン全体） | 31 MB（岡部のプレハブだけ） |
| 大和守を作り込む | 102 MB＋以後ずっと増える | その屋敷のプレハブだけ |
| 屋敷が増えたとき | シーンが単調に膨らむ | **他の屋敷のファイルは1バイトも変わらない** |

地区分割が「地区ごと」の粒度なのに対し、これは**屋敷ごと**。分割より細かく、
**屋敷が増えても劣化しない**。地区分割は B2 を入れれば不要になる（シーンが数MBまで落ちるため）。

⚠ **手順が1つ増える。** プレハブインスタンスの中を直接いじると、変更が
`m_Modifications` としてシーンに積まれて元の木阿弥になる。
**屋敷を触ったら最後に「プレハブへ適用」する**必要がある。
これは機械化できる（`Edo/屋敷/プレハブへ適用` メニュー＋ビルダー側の後始末に組み込む）。

### B3. 完成した棟を焼き固める（総バイト数を実際に減らす唯一の手）

棟1つが約800部材。**完成した棟のメッシュを1つに結合**すれば、
PrefabInstance 800個（約2.2 MB）が GameObject+MeshFilter+MeshRenderer 1組（約2 KB）＋
メッシュ資産（バイナリ）になる。岡部邸のプレハブは 31 MB → 数MB の見込み。

- **部材単位の編集ができなくなる**ので、**「完成した」と判断した棟にだけ**かける
- 元に戻せるよう、焼く前の部材構成は残す（別プレハブ or ビルダーで再生成できる状態）
- **B2 を入れてから、効果を測って必要なら**やる。先にやる必要はない

## 4. 進め方

**B1 → B2 →（測って必要なら）B3** の順。理由:

- B1 は影響が1クラスに閉じ、手順が変わらず、9% がすぐ取れる。**足慣らしとして最適**
- B2 は手順が変わる（プレハブへ適用）。1屋敷で試してから広げる
- B3 は不可逆性が高い。B2 の効果を見てから判断する

### B1 の手順

1. `WaterBody.snap` の退避先を決める（`.asset` か `Library/`）
2. 移行コードを書く。**既存の6個の snap を失わないこと**（`WaterBaker` の Recarve が
   snap に依存している。`waterbaker-ty-offset-bug` の復旧手順も確認）
3. 1つの池で試し、水面と地形が変わらないことをスクリーンショットで確認
4. 残り5個。シーンサイズを測って記録

### B2 の手順（1屋敷で試す）

**最初の1つは岡部邸**。理由: 単独で31 MB＝効果が最も大きく、失敗しても影響が1屋敷に閉じる。

1. `Edo_Yashiki_OkabeChikuzen` を `Assets/Edo/Prefabs/Yashiki/OkabeChikuzen.prefab` へ書き出し、
   シーン側をそのインスタンスに置き換える
2. シーンサイズを測る（102.5 MB → 約71 MB の見込み）
3. **ビルダーを試走させ、変更がシードに積まれず、プレハブ側へ適用されることを確認**
4. 「プレハブへ適用」をメニュー化し、`EdoOkabeYashikiBuilder` の末尾に組み込む
5. 問題なければ他の屋敷へ

### 検証（各段階でコミット前に必ず）

```bash
ls -l Assets/Edo/Scenes/Akasaka.unity          # シーンサイズ
python3 docs/maintenance/measure_lfs.py        # LFS 保存量
```

Unity 側:
- transform 合計が **192,556** のまま（オブジェクトを失っていないこと）
- 該当箇所のスクリーンショットが作業前と一致すること
- ビルダー試走で**二重のルートが生えない**こと

## 6. 地区分割について

当初案（`Base` / `Sanno` / `Sanbezaka` / `Tameike` / `Akasaka_Machi` / `Toranomon` の
additive scene）は **B2 を入れるなら不要**。シーンが数MBまで落ちるので分割する動機が無い。

調査で分かった前提だけ残しておく（将来やるとしたら要る）:

- **地区をまたぐオブジェクトは問題ない。** Unity のシーンに空間的な境界は無く、
  シーンは「どのファイルに保存されるか」を決めるだけ。またぐ地物は常時ロードの
  シーンに置けばよい
- **問題になるのは参照だけ。** シーンをまたぐオブジェクト参照は保存できない。
  2026-08-15 時点で **0 件**（シーン内の MonoBehaviour は `WaterBody`×6 /
  `GeoMarker`×6 / Player系のみで、いずれも閉じている）
- ⚠ **`Group()` の落とし穴**: ビルダー14本が持つ `Group(root, child)` は
  `GameObject.Find(root)` が空振りすると**アクティブなシーンに同名ルートを新規作成する**
  （`EdoNishiTameikeBuilder.cs:126` が正典、他13本がコピー）。
  分割するならルート名→シーンの対応表を持つルータを**同時に**入れること
- ビルダーが他地区の成果物を掴んでいる箇所: `EdoSanbezakaBuilder.cs:416` →`Edo_Sanno_Sha` /
  `EdoOkabeYashikiBuilder.cs:638` →`Edo_Sanno_Sha` / `EdoAzukarichiBuilder.cs:123` →`Edo_Tamachi_Bank` /
  `EdoTameikeKitaBuilder.cs:707` →`Water_KurodaKamoba`
- 地形 `ModernTerrain` は1つで全ビルダーが読み書きする。分割できない。
  なお `ModernTerrain.asset` は **15.5 MB / LFS** なので、**造成や splat を伴う作業は
  シーンと別に 15.5 MB が乗る**。これはどの案でも減らない
