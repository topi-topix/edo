# 掲示板(board)と司令塔 — セッション横断の報告・裁定・情報共有の作法

`edo_session.py`(claim)は**衝突を防ぐだけ**で、進捗・課題・裁定待ちは誰にも見えず、
横断影響の伝達をユーザーが人力でやっていた。それを解くのがこの体制。

- **掲示板** = `.git/edo-board/` の issue 登録簿(git 管理外・全 worktree 共有)。
  CLI は `Tools/Session/edo_board.py`。
- **司令塔(PM)** = 専任のセッションが定期巡回し、ダッシュボード更新・ユーザーへの翻訳・
  異常検知を行う。**セッション間の日常の伝達は司令塔を経由しない**(下記「直接メッセージ」)。

---

## 作業セッションの義務(これだけ守る)

### 1. post する契機は3つだけ

細かい報告は書かない。**コミットが報告を兼ねる**(司令塔が git log を読む)。
board に書くのは「コミットに現れない状態」だけ:

| 契機 | type | 例 |
|---|---|---|
| **節目** — 関門通過・レビュー待ち到達・実装ステージ完了 | `info` | 「検図3巡通過、レビュー待ち」 |
| **ブロッカー** — 資源待ち・史料待ち・他邸依存 | `blocker` | 「門戸部の間数は都立中央図書館の館内閲覧待ち」 |
| **ユーザー裁定が要る** | `decision` | 下記テンプレ必須 |

```bash
# worktree からは絶対パスで(自ブランチにはまだ CLI が無いことがある。board 実体は共有)
python3 /Users/toshio/project/edo-unity/Tools/Session/edo_board.py \
  post --estate doi --type blocker --title "…" --ref "docs/Sashizu/doi_sashizu.json#_pending.monsun"
```

⛔ **正典を写さない。** 未決の中身は各邸 `_pending` が正典のまま。issue は `--ref` で指す。

### 2. decision はテンプレ強制(ユーザーが判断できる形でしか裁定を仰げない)

```bash
python3 Tools/Session/edo_board.py post --estate sanno --type decision \
  --title "回廊の基壇の受け方" \
  --background "背景を2文以内で。専門用語の羅列にしない" \
  --options "A: 深い石垣で受ける(造成小)" "B: 平場を北へ補う(造成大)" \
  --recommend "A。理由を1文" \
  --impact "採ったときの影響。他邸への波及があれば必ず書く"
```

作事奉行がこれをユーザー向けに噛み砕いて上げる。テンプレが埋まらないなら、
それは**まだ裁定を仰ぐ段階ではない**(選択肢を整理してから来る)。

⛔ **一件一葉 — 1件に複数の裁定を詰めない。**独立に答えられる事柄は別の issue に分ける。
詰めると片方だけ裁定が下りたときに `status` を動かせず、巡回のたびに「未裁定が残っている」
ようにしか見えない(**実例 EDO-0057** — 其の一=隅部材 / 其の二=門の切り欠きで起票し、
両方に裁定が下りた後さらに「天端の段」が湧いて3つ積み上がった)。
`post` が**機械で弾く**: 選択肢の A/B/C 記号・詰め込み(其の一/其の二・丸数字・表題の「+」)。
→ 正典 **[reporting-protocol.md](reporting-protocol.md)** 規則6・規則8

### 3. 三巡則 — 自己検図・自己考証は**ユーザー入力なしに3巡まで**

3巡目を終えてなお指摘が出続けるなら、**4巡目に入らない**。`decision` か `blocker` を
post して手を止める(前例: 裁定なしに検図10→14巡が無停止で回った。巡数を重ねるほど
自作の関門に最適化していき、本質から離れる)。司令塔が git log の巡数で監視している。

### 4. 他邸に効く発見・変更は「起票+直接メッセージ」の両方

共有境界・parcels.json・base_dem.json・地形・基準面など、**他邸に影響すること**を
発見/変更したら:

1. **board に起票**(`--estate cross`)— これが記録。相手セッションが不在でも、
   次に立ち上がるセッションが greet の digest で拾える。
2. **影響先セッションへ直接メッセージ** — `ListAgents` で相手を探し(`edo_session.py status`
   の claim の `sashizu:<邸>` や cwd と突き合わせて同定)、`SendMessage` で送る。
   ⚠ **claim の短縮ID(例 `2927b194-c95`)と `ListAgents` の名前(例「松江松平邸セッション」)は
   別物で、突き合わせる自動の手段が無い。**「直前にやり取りしていた相手 = 資源を持っている相手」
   と思い込むと誤送信する(2026-08-31、資源の保持者への依頼を無関係のセッションへ送った実例)。
   資源(unity 等)の保持者へ連絡するときは、`status` の note や `sashizu:` に出る**屋敷名**を
   手がかりに、`ListAgents` の一覧からその屋敷を担当するセッション名を選ぶこと。

⛔ **メッセージは揮発、board が記録。** メッセージには必ず issue ID(EDO-xxxx)を添える。
board に無い伝達は「無かったこと」になる(司令塔も追えない)。
メッセージは短く: 「EDO-0012: 松平S辺の据え付け面を+0.4m動かした。土井の共有辺検査を
流し直してほしい」程度。長い経緯は issue の note へ。

### 5. 指図の Artifact を再公開するときは URL を渡す

⛔ **`url=` を渡さずに publish すると、更新ではなく新しい Artifact が生える。**
README がリンクしている方は古いまま取り残され、ユーザーには「デグレした」ように見える
(2026-08-26 に山王で実際に起きた — 正典は正常なのに、公開版が4日前の女坂=直線のままだった)。

```bash
# 指図を再公開するときは必ず docs/Sashizu/README.md の Artifact 列の URL を渡す
Artifact(file_path="docs/Sashizu/<屋敷>_sashizu.html",
         url="<README の Artifact 列の URL>")
```

指図を直したら**その場で再公開する**。直して公開しないと、ユーザーが見る図と正典がずれる。

### 6. セッション開始時

greet フックが board の digest(裁定待ち・ブロッカー・open)を自動表示する。
`edo_session.py start <屋敷>` もその邸+横断の open issue を出す。
**自分宛(owner=自邸)と cross の issue を読んでから作業に入る。**

## 作事奉行(差配役 / PM)

⚠ **2026-08-29 に「司令塔」から改名した。** 旧称は `edo_session.py` の claim 門番
(自動で衝突を止める機構)と**同じ名前で二つの別物を指していた**。人が担う差配役は
**作事奉行**、機構は**門番**と呼び分ける。古い board の記録・過去のコミットは
「司令塔」のまま残る(履歴なので書き換えない)。

**エージェント定義は `.claude/agents/edo-sakuji-bugyo.md`。** 本ファイルが手順の正典で、
エージェント側は薄い殻。

**専任セッションが1本**(作業はしない)。約30分間隔の self-paced loop で巡回する。
セッション間の伝達は上記4のとおり**当事者同士が直接**行い、作事奉行は中継しない。
作事奉行の仕事は4つ:

1. **ダッシュボード** — `Tools/Session/build_board_html.py` で生成し、Artifact に再公開
   (同一 URL)。URL は本ファイル末尾に1箇所だけ記す。
2. **ユーザーへの翻訳** — 変化があった巡回だけ、ダイジェストを報告。作業者の生文は出さない。
   ⛔ **書式は [reporting-protocol.md](reporting-protocol.md) に従う** — 冒頭1行で件数を宣言 →
   **【裁定1】【裁定2】【質問1】**(選択肢は A/B/C)→ `---` → **【報告1】【報告2】【共有1】**。
   裁定は**一通に最大3件**、各件は6点セット(どこ/背景2文/選択肢/推奨/影響/裁定図)。
   ⛔ **番号と題は報告・共有にも振る** — 返事の要らない項目にもユーザーはコメントする
   (2026-08-30 指示)。⛔ **「■注意」「■進捗」のような箱の名前を見出しにしない** —
   見出しだけ読んで中身が分かる題にする。
   ⛔ **地の文の末尾に問いを埋めない**(2026-08-30 に実際に「何を確認すれば良い?」と差し戻された)。
3. **異常検知** — 停滞(心拍だけ続きコミットも board も60分無音)/ 三巡則違反
   (git log の巡数がユーザー裁定なしに+3。「十一巡目」の漢数字も拾う)/
   要裁定の滞留(awaiting-user が2巡回残留)。
4. **バックストップ** — 横断影響が board に記録されていない・宛先セッション不在・
   メッセージに反応が無い、という**取りこぼしたときだけ**作事奉行が起票・伝達する。

⛔ **各邸の指図・実装の中身を評価・裁定しない。** 「この設計は妥当か」を作事奉行が言うと、
考証方・検図方・普請検査という独立した検査軸が潰れる(EDO-0042)。下読みを添えるときは
**必ず「当家が一次情報から検め直すこと」と明記**する。

### 巡回1サイクルで読むもの

① `edo_session.py status` ② `edo_board.py list --json` ③ `git log --all --since=<前回>`
(**`--all` 必須** — worktree ブランチのコミットは main に居ない)
④ `_pending`×4 のハッシュ比較 → 変わった邸だけ読む ⑤ セッション↔邸の対応更新。
状態は `.git/edo-board/_pm/state.json` に永続化する。

⭐ **⑥ `edo_session.py sync-tools` を打つ。** main の運用ファイル(門番のツール・CLAUDE.md・
各作法)を全 worktree の作業ツリーへ配る。**打たないと各 worktree が古い不変則と古い門番で
動き続ける** — 2026-08-31 に、外堀の worktree が基準年次「嘉永期」のまま、全 worktree の
`edo_session.py` に `wait`/`unwait` が無いまま動いていた(EDO-0076/0077)。⚠ コミットはしない
設計なので、各邸のブランチを汚さない。**main の運用ファイルを直した直後にも打つこと。**

⭐ **⑦ `python3 Tools/Sashizu/wiring_gate.py` を打つ。** 全邸を静的に読み、**書いたのに
`main()` から呼ばれていない産物**(図・表・検査)を鳴らす。⛔ これは目視では見つからない —
松江松平は同じ型を3度見逃した(規則19)。⚠ 巡回で拾うのは**新しく孤立が出た邸**だけでよい
(既知のものは各邸の宿題)。⛔ **0件は「合格」ではない** — 恒真の検査・検査の欠落・
建てないと見えない不良はこの道具では見えない(`docs/verification-loops.md`)。

### 作事奉行の起動・引き継ぎ・止め方

作事奉行は**使い捨て可能**。記憶はすべてディスクにある(board 本体・`_pm/state.json`・
本ファイル)。

- **引き継ぎ**: 新しいセッションで「**作事奉行をやって**」(旧称の「司令塔やって」も通じる)。
  本ファイルと `_pm/state.json` を読み、下記 URL の Artifact へ再公開しながら巡回を再開する。
- **止める**: 「**巡回を止めて**」と言う(次の wakeup を予約せず終了)。
  セッションを閉じても止まる。「1時間止めて」「巡回を再開して」も一言で効く。
- 止めても board・ダッシュボード・state.json は残る。いつ再開しても続きから。

⚠ **巡回が途切れやすい。** self-paced loop は「毎回自分で次を予約し直す」方式なので、
途中で別の依頼が入ると予約を忘れて鎖が切れる(2026-08-29 に実際に二度切れた)。
長時間ダッシュボードが古いままなら、誰でも `edo-sakuji-bugyo` を呼んで回し直してよい。

## ⛔ 裁定を求めるときは「どこ」を必ず書く

`--type decision` / `blocker` を立てるときは、**相手が図の上で指させる場所**を本文の先頭に置く。
図版番号(其◯)・辺と s・グリッド(u,v)・世界座標・隣接物のうち最低1つ。
名前だけ(「隅の詰め」「袖塀が長くなる」)では裁定できない — 2026-08-29 にユーザーから
「どこのことを指してるのか分からない」と差し戻された実例がある。
**図がまだ無いなら、先に図を出してから起票する。**
