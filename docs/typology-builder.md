# 類型ビルダー — 区画の形と類型から、まず建てる(設計)

**2026-09-19 施主裁定1=A の実装設計。** 88 区画を**まず全部**、区画の形と類型の既定値から建てる。
そのうえで、史料が取れた欄から一つずつ上書きしていく。
裁定の記録: https://claude.ai/artifact/EouMVDWUjrGCaDuZ4tUHVW ／ 新しい輪の図 §2: https://claude.ai/artifact/NLH516uX8qR8XnSxPE4Rnh

⛔ **「手作りにする敷地」と「類型で済ませる敷地」という区別は無い**(2026-09-19 施主指摘)。
> 「手作り層とそうでない敷地なんてものは存在しません。本当は時間をかけずに立てたいけど、時間がかかっている
> だけです。今後、他の邸も全部同じように史実を調べながら立てていく予定です。もちろん類型でサクッと作れるに
> 越したことはありません。」

つまり**類型は層ではなく、どの区画も通る最初の姿**である。区画は「類型か手作りか」ではなく、
**欄ごとにどれだけ史料で埋まっているか**(確度 S/A/B/P/U・規則7)で違うだけ。時間が経つほど U が減る。
⛔ したがって、この文書に区画を二つに仕分ける表は無い。

⭐ この文書は**設計**であって実装ではない。数値は例で、正典になるのは `docs/Sashizu/typology.json`(§3)だけ。

## 2. 輪 — 類型の区画には指図も検分の輪も無い

```
普請奉行 ──類型表を起こす──▶ 考証方(表を一度に検める・同定と格式の誤りだけ)
   │                                    │ pass
   ▼                                    ▼
類型ビルダー(区画の形 + 類型表 → 生成) ──▶ 普請検査(隙・境界・埋没・浮きを機械的に測る)
   ▲                                    │
   └── 欠陥はビルダーを直す(同じ類型の全区画に効く) ◀──┘
                                        ▼
                          施主が一括レンダを見る → 承認で「まず建った」
                                        │
                     史料が出た欄を上書き ─┘(何度でも。確度が U → B → A と上がる)
     施主が「図から起こせ」と言った区画だけ図を起こす ──▶ `"built": "hand"`(以後の直しも欄の上書き)
```

- 施主が見るのは**類型表と一括レンダの 2 つ**だけ。区画ごとの図・裁定・検分の残は出さない。
- ビルダーの直しは一区画でなく**同じ類型の全区画**に効く。直すほど速くなる。
- 一度建った区画は**建ったまま**。史料が出たら欄を直して建て直すだけで、作業の順番待ちに入らない。

## 3. 類型表 `docs/Sashizu/typology.json` — 唯一の正典

**区画 × 類型 × 径数。** 区画の形は `parcels.json` が正典(規則11)なので**座標は持たない**。
径数は「史料で読める値」だけで、読めない物は `null` にして**類型の既定値**(§4)で埋め、`cert` に確度を書く
(規則7。U のまま既成事実にしない)。⛔ 表を書いたら `python3 Tools/Sashizu/typology_check.py`(挨拶フックが毎回呼ぶ)。

**表門の向きは `front` に8方位で書く**(`"E"` / `"WNW"`)。`null` なら**ビルダーが接道辺から採る**
(道は敷地割の間に残った領域そのもの)。⛔ 辺番号も座標も書かない — 取り合いは実メッシュから解く(規則5)。

| `chisen` 池泉 | 5(8,871〜22,333坪) | 屋敷林の帯 + 座敷面の前の主景 + **池代地** + 前庭の白洲 | 屋敷林=周長÷40 箇所の塊(上限80本)。主景は面長×奥行25 の扇 |

⭐ **28区画の実測は面積で 100 倍・周長で 12 倍の開きがある。**固定本数を配ると `ura` は木に埋まり `chisen` は禿げる。

⛔ **覆さない線**:
1. **前庭は空けるのが既定。**参道の帯(gateC → 棟の門側の面、片側 = 門の実開口幅/2 + 1.5)に木・石・刈込・灯籠を置かない。埋めると格が落ちる。検査で「帯に入った駒 = 0」を刷る。
2. **塊は必ず奇数**(3/5/7)、外形は不等辺。**乱れは4つ全部**(芯々・yaw・等方スケール・個体)に掛ける。1つ欠けると並木に見える。
3. **常緑:落葉 = 7:3。**落葉に寄せると冬に骨組みが消える。
4. **池は類型の既定では掘らない**(§4.5a)。
5. ⛔ 類型ビルダーから**地形(高さ・アルファマップ)を書かない**。池も築山も splat もここでは書かない。

### 4.5a 池を類型で掘らない理由(覆すなら施主の裁定が要る)

(a) 掘削は地形の書き換え=**造成**で、類型は地形を書かない(規則3・9・13。造成前の正典は `base_dem.json`)。
(b) `WaterBaker` の snap 矩形は輪郭 bbox+余白150m。該当 5 区画は溜池・外堀・隣接屋敷と重なり、
   重なった snap はどれか 1 つの Recarve で他の造成が消える(既知の事故 → memory `pond-snap-overlaps-in-scene`)。
   79 区画の一斉再生成と両立しない。
(c) **水源が区画ごとに違う。**上水の給水範囲内でも利用 73%・併用 56%([内藤2024]A)で、水源は屋敷ごとに
   列挙される性質の事実。水源を書けない池は典拠のない装置になる。

⇒ 代わりに `chisen` へ **池代地**(木を置かない不定形の空地)を確保し、後から木を動かさずに掘れるようにする。
⇒ 溜池・外堀に**接する**区画は、庭を汀へ寄せ塊と刈込を水面へ向けて開く(**借景の水**)。
⚠ [山本図] は 200 坪の御家人屋敷に瓢箪形の小池を描く。「小屋敷に池はありえない」のではなく
**「類型の既定にはできない」**が正確な言い方 — 区画側に明記したときだけ掘る道は残す。

### 既定値はどう効くか(2026-09-21・EDO-0304)

`defaults` の鍵は型ごとに違う — **buke は `rank_yashiki`**(`daimyo_kami`)、無ければ `rank`(`hatamoto_mid`)。
**jisha は `kind`**(`bo`/`temple`/`shake`)。**machiya と kouyuu は入れ子が無く、塊そのもの**が既定。
`EdoTypologyBuilder.LoadTable()` が区画を読む前に `Fill()` で差し、**区画に書いてある値が必ず勝つ**。
⛔ 格が表に無いときは既定を当てない(別の格の値を借りると、書いていない物が建つ)。

⚠ **2026-09-21 まで `LoadTable()` は `parcels` しか読んでいなかった** — 表の `_` は「区画の欄が null の
ときビルダーがここから採る」と約束していたのに、その約束は一度も効いていなかった。だから
`defaults` へ欄を足しても建つ姿は変わらず、表を見た者には効いているように見えた(EDO-0304)。
今は `Tools/Sashizu/typology_check.py` が **ビルダーのソースから「実際に読む欄」を引いて**
既定と突き合わせ、読まれない欄を毎回 ⚠ で名指しする(規則19。手で写した一覧にしない)。

### 欄が効かない三つの型(2026-09-21・EDO-0317)

`typology_check.py` は **三つの別の盲点**を見ている。どれも「表を見た者には効いているように見える」ので、
0 件でなく**毎回名指しで刷る**(規則19)。

| 型 | 何が起きるか | 見つけ方 |
|---|---|---|
| `inert_defaults` | `defaults` に欄を足しても、C# が読まないので建つ姿は変わらない(EDO-0304 の正体) | 既定の鍵 − ビルダーが読む鍵 |
| `read_but_unused` | `Spec` へ読み込んではいるのに、建てる側が一度も参照しない(`inari` が実際にそう) | 左辺の識別子の出現数 − 宣言と代入 |
| `unread_fields` | **区画にだけ在る欄**で、ビルダーがその名を読みもしない。上の二つの網に掛からない | 区画の鍵 − ビルダーが読む鍵 |

⭐ 三つ目は 2026-09-21 に足して、はじめて `kamiyui`(髪結床・24区画)`tanagari`(店借)`hoshiba`(干場)
`shimatuya`(仕舞屋)`tacchu`(塔頭)`tokinokane`(時の鐘)が見えた — **史料から起こして表へ書き込んだのに、
誰にも建てられていなかった** 6 欄。欄は 15 件ではなく **19 件**だった。

⭕ `source` と `koku` は `NOT_SHAPE`(建つ姿に効かなくて当たり前の欄)として破れの列から外してある —
典拠と史料値は姿を決めず、**決めてはいけない**(石高から棟数を引く鎖は史料で切れている・§4)。
⛔ この集合を静かに増やさない。増やすなら理由を `typology_check.py` へ書く。

|---|---|---|
| 0 面 | 区画内の**自然地形の中央値**を面に採る(規則3・`base_dem.json`)。造成は既定で**しない**。傾きが大きい区画だけ段を 1 つ切り、土留めは `unity-modular-stonewall` の run | 面の高さは地形から。設計値を先に決めない |

⛔ 手組み資産(`Ishigaki` / `Nagaya` / `Omotemon`)のある区画は、その資産を**避けて**建てる(規則1)。

### 1区画 = 1プレハブ(EDO-0296)

**Stage 7 を飛ばすと 79 区画が `Akasaka.unity` へ生で載る。** LFS は1コミットで書き換わったファイルを
丸ごと保存するので、生で載っていればどの1区画を直してもシーン全量が保存量に乗る
(手組みの屋敷・町・寺社 83 本は既に1軒1ファイルに割ってある → `EdoYashikiPrefab`)。

⚠ **切り出しはビルダーの側でやる。** 保存時の自動書き戻し(`EdoYashikiPrefabAutoSave`)は
**既にプレハブ資産があるルートしか書き戻さない**ので、新しく生えたルートは何度保存しても生のまま残る。
⛔ 逆に「大きい新ルートは全部プレハブにする」を保存側へ入れない — 手組み資産や検分用の仮ルートまで
勝手に焼き付く(規則1)。

⛔ **寝ているルートを `GameObject.Find` で探さない。** 撤去は `SetActive(false)` の決まり(規則1)なので、
Find では見落として同名の2本目が生え、プレハブ資産がどちらの姿で焼かれたか分からなくなる
(→ `EdoTypologyBuilder.FindRoot`)。
